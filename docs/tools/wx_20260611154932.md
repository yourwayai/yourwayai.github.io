# 像写代码一样写业务系统？实测 TypeScript 驱动的 Twenty CRM

* **原文链接**: [https://mp.weixin.qq.com/s/cf5iizzTyu-umsXlBe7rwA](https://mp.weixin.qq.com/s/cf5iizzTyu-umsXlBe7rwA)
* **作者**: YourwayAI

---

传统的商业 CRM（客户关系管理）系统通常是一套庞大且封闭的 SaaS 平台。业务人员喜欢它们提供的拖拽式表单和报表，但对于负责二次开发的技术团队而言，在复杂的图形界面中维护几十个自定义字段和回调钩子，不仅难以进行版本控制，还经常导致线上线下的配置脱节。

今天我花了一些时间在本地测试了近期在开源圈讨论度很高的项目——Twenty。它的核心产品理念非常极客：让技术团队像构建、发布和进行版本控制日常代码一样，去管理 CRM 系统的底层结构。

### 📌 把 CRM 装进开发者的终端

官方提供了开箱即用的云端版本（Cloud），但为了验证其主打的“高度可定制性”，我直接选择了本地 CLI 脚手架构建。这个过程和我们初始化一个普通的 Node.js Web 项目几乎没有区别。

首先，在终端通过官方的 CLI 工具拉取并初始化一个专属应用：

```
npx create-twenty-app my-app
```

Twenty 的核心亮点在于它允许我们将 CRM 的数据对象（Objects）、字段（Fields）甚至视图（Views），全部通过 TypeScript 代码进行定义。在生成的工程目录下，我们可以看到类似下面这样的配置文件：

```
import { defineObject, FieldType } from 'twenty-sdk/define';  
  
export default defineObject({  
  nameSingular: 'deal',  
  namePlural: 'deals',  
  labelSingular: 'Deal',  
  labelPlural: 'Deals',  
  fields: [  
    { name: 'name', label: 'Name', type: FieldType.TEXT },  
    { name: 'amount', label: 'Amount', type: FieldType.CURRENCY },  
    { name: 'closeDate', label: 'Close Date', type: FieldType.DATE_TIME },  
  ],  
});
```

在这个文件里，你不再需要去系统的后台页面点来点去。新增了一个 `Deal`（交易）对象以及对应的金额和日期字段后，只需在终端执行发布指令，这些变动就会被推送到你的工作空间中：

```
npx twenty app:publish --private
```

### 💻 核心亮点

在通读了官方文档并跑通了基础的数据流转后，我认为 Twenty 有两个值得关注的技术设计：

**1. 万物皆代码（CRM as Code）的工程化思维**  
上述的测试过程证明了它的最大优势。对于复杂的 2B 业务来说，需求是不断迭代的。使用 TypeScript 来声明对象结构，意味着你的 CRM 数据模型可以顺理成章地接入 Git 工作流。每一次字段的增删改都可以经过严格的 Code Review（代码审查），在 CI/CD 流水线中进行测试，彻底告别了传统 CRM 中“不知道谁在后台改了配置导致接口报错”的痛点。

**2. 极为现代且硬核的底层技术栈**  
很多老牌开源业务系统往往还在使用陈旧的 PHP 或沉重的 Java 框架。而 Twenty 完整拥抱了现代全栈 TypeScript 生态：

* • **后端**：基于 NestJS 构建，利用强大的依赖注入系统管理复杂的业务逻辑；同时使用 BullMQ 配合 Redis 处理异步任务和定时工作流，数据库则选用了稳健的 PostgreSQL。
* • **前端**：采用了 React，结合 Jotai 处理轻量级状态管理，使用 Linaria 实现零运行时的 CSS-in-JS，保障了大型表格和看板的渲染性能。
* • **工程化**：通过 Nx 实现了 Monorepo（单体仓库）管理，保证了前后端类型的高度复用。

### ⚠️ 避坑指南与总结

尽管 Twenty 描绘了一个对技术团队极其友好的业务系统蓝图，但在实际落地前，有几个现实的门槛需要考量：

**1. 陡峭的非技术人员学习曲线**  
这套系统将极大提升开发人员的体验，但代价是将配置权从“业务管理员”手中转移到了“研发”手中。如果你的销售团队习惯了自己随时在后台拖拽增减字段，Twenty 的这种代码定义模式会让跨部门协作变得繁琐，因为每一个小的改动都需要通过提交代码 PR 来实现。

**2. 私有化部署的运维成本**  
如果你不打算使用官方云服务，而是选择完全自己接管数据（Self-hosting），你必须具备一定的基础设施维护能力。它的 Docker Compose 编排文件里包含了 Node 服务、PostgreSQL、Redis 以及消息队列组件，保障这些组件在高并发场景下的稳定运行并不是一件轻松的工作。

如果你所在的技术团队正在为公司自研一套复杂的内部管理系统，且苦于从零手写增删改查和权限管理，Twenty 提供了非常优质的底层基建。但如果你的公司完全由销售业务驱动，且缺乏专门的全职研发人员来维护系统，那么开箱即用的传统商业 SaaS 依然是更稳妥的选择。
