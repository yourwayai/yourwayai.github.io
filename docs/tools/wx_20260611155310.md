# 纯本地快照与自动 Rebase：Jujutsu 极客体验与避坑指南

* **原文链接**: [https://mp.weixin.qq.com/s/Wz_J5h_qc-cuTJWGTVS9fQ](https://mp.weixin.qq.com/s/Wz_J5h_qc-cuTJWGTVS9fQ)
* **作者**: YourwayAI

近期在梳理本地开发环境和评估各类效率工具时，我将目光锁定在了一个相对年轻但在极客圈讨论度颇高的开源项目：Jujutsu（命令行简称 `jj`）。这是一个由前 Google 工程师主导开发的版本控制系统。

与我们常见的各类 Git GUI 包装壳不同，Jujutsu 是一个完全用 Rust 重写底层逻辑的全新系统。它的核心架构将用户界面、版本控制算法与物理存储层进行了完全解耦。这意味着它的底层可以接入任何存储后端。

目前，Jujutsu 提供了一个高度兼容的 Git 存储后端。这种设计使得你可以无缝对接 GitHub 等现有的远程仓库，同时在本地享受一套完全不同的版本管理逻辑。今天，我将完整记录这款工具在本地环境的部署过程与核心技术亮点。

### 📌 在 macOS 上的编译与初始化

在我的 MacBook Pro 上配置 Jujutsu 的过程十分直观。由于项目底层基于 Rust，你可以直接通过系统包管理器或 Cargo 进行编译安装。为了保证依赖树的稳定，我选择了带锁定的编译方式：

```
cargo install --locked jujutsu
```

编译过程大约需要几分钟。Jujutsu 的 Git 后端依赖于 `gitoxide`（一个纯 Rust 实现的 Git 核心库），这保证了它在处理本地存储时的极高执行效率。如果你不想通过源码编译，macOS 用户也可以直接使用 `brew install jujutsu`。

安装完成后，我们可以在任意目录下初始化一个新的仓库。这里需要注意一个版本更迭的坑：在 0.14 版本之前，大家习惯使用 `jj init --git`。但在最新的版本中，该命令已被弃用，你需要显式地调用新命令：

```
jj git init
```

如果你有一个现成的 Git 仓库，Jujutsu 也支持“共存模式”（Colocated Workspace）。你可以在同一个目录下混合使用 `jj` 和 `git` 命令，两者共享底层的 `.git` 数据。

### 📌 重构版本控制的三大机制

在实际跑通了几个分支合并与代码提交的工作流后，Jujutsu 的以下三个核心机制令我印象最深。

**1. 工作区即提交**

这是 Jujutsu 解决 Git 使用痛点的最核心思路。在 Git 中，工作区、暂存区（Index）和提交记录是严格分离的。一旦你需要临时切换分支，通常只能依靠 `git stash` 来隐藏未提交的脏代码。

Jujutsu 抹除了这种心智负担。在它的逻辑里，你的当前工作目录本身就是一个真实的、匿名的 Commit。每一次保存文件，系统都在静默修改（Amend）这个工作区快照。这意味着命令行永远不会因为“工作区存在未提交的更改”而报错阻拦你。

**2. 冲突也是一等公民**

如果你在 Git 中遇到合并冲突，整个工作流会被迫中断，你必须先解决文本差异才能继续进行 Rebase 或 Merge 操作。

Jujutsu 借鉴了 Darcs（一个基于补丁理论而非快照理论的古早版本控制系统）的设计理念，将冲突直接记录在 Commit 对象中。即使发生冲突，合并操作也会显示“成功”。你可以带着这些冲突继续进行其他操作，等思路清晰时再去解决它。

得益于这一机制，Jujutsu 实现了真正的**自动化 Rebase**。当你通过 `jj diffedit` 修改了历史记录中的某一个 Commit，系统会自动将其所有下游的子节点重新 Rebase 到新的节点上。如果在传导过程中产生了冲突，冲突会被静默向下传递，绝不会破坏你的命令执行链路。

**3. 全量操作日志与绝对安全的并发**

Git 虽然有 `reflog` 可以找回丢失的指针，但界面不够直观。Jujutsu 引入了全量的操作日志机制，它记录了每一次 Commit、Pull 或 Push 操作，并绑定了当时的仓库状态快照。如果你误删了分支或搞砸了 Rebase，只需一个 `jj undo`，就能让整个仓库的时空倒流。

此外，由于其底层的分布式并发设计，Jujutsu 是可以在 Dropbox 或通过 `rsync` 备份时安全使用的。传统的 Git 仓库在遭遇非原子性的文件同步时极易损坏，而 Jujutsu 在最坏的情况下，也只是暴露本地与远程状态的冲突供你手动解决，确保了数据层的绝对安全。

### 📌 值不值得花时间折腾？

必须客观指出，虽然 Jujutsu 的 Git 兼容性已经达到了生产可用级别，但它仍处于 1.0.0 正式版发布前的实验阶段，存在一些明确的局限性。

首先是功能缺失。目前它对 Git Submodules（子模块）的支持尚未完全竣工，如果你的项目是依赖大量子模块的 C++ 库或巨型 Monorepo，现阶段迁移会遇到阻碍。其次，Jujutsu 暂不支持原生基于邮件的工作流，且在超大规模仓库下可能会遇到个别性能瓶颈。

但这并不妨碍它成为一个极具潜力的工程工具。Jujutsu 通过抽象底层存储、引入快照式工作区和自动化历史重写，极大降低了代码合并与回溯的门槛。如果你平时深受复杂的 Git 冲突排查所困扰，或者经常需要高频地切分、压缩（Squash）历史提交，利用周末的时间在个人项目里跑通并体验一下 Jujutsu，是一件极具极客浪漫且收益明确的事情。
