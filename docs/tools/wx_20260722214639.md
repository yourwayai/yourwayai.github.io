# Rust 重写 Postgres 18.3：pgrust 解决底层修改痛点的初步实测

修改一个拥有数十年历史、数百万行 C 语言代码的开源关系型数据库，是一件高风险的事情。这也是为什么绝大多数基于 Postgres 的技术创新都选择以外挂扩展（Extension）的形式存在，而非直接修改内核。今天在本地跑通的 pgrust 项目试图走一条新路：用 Rust 将 Postgres 18.3 完整重写一遍。

我的核心关注点不在于“用 Rust 重写”这个动作本身，而是它试图达成的最终目的：通过 Rust 严格的内存安全机制，让 Postgres 的深层源码变得更易于修改。它不是一个简单的套壳客户端，而是一个能够与标准 Postgres 18.3 保持底层磁盘级兼容的数据库引擎。

### 部署实录与编译代码解析

官方提供了一个高度封装的 Docker 镜像，但我更倾向于从源码进行本地编译。这是观察一个底层重构项目工程规范的最佳切口。在不同操作系统下，编译 pgrust 需要首先解决繁琐的 C 语言生态底层依赖。

如果是 macOS（M 芯片）环境，需要通过 Homebrew 安装基础组件，并手动向 Rust 编译器暴露环境变量。具体的终端配置代码如下：

```
# 安装基础依赖，包括 Unicode 支持库 icu4c 和底层加密库 openssl  
brew install icu4c openssl@3 libpq  
  
# 显式指定动态链接库与 pkg-config 的寻址路径  
export LIBRARY_PATH="$(brew --prefix openssl@3)/lib:${LIBRARY_PATH:-}"  
export PKG_CONFIG_PATH="$(brew --prefix openssl@3)/lib/pkgconfig:$(brew --prefix icu4c)/lib/pkgconfig:${PKG_CONFIG_PATH:-}"  
export PATH="$(brew --prefix libpq)/bin:$PATH"
```

如果是在 Debian 或 Ubuntu 生产服务器上进行测试，则需要通过 `apt` 包管理器补充完整的构建工具链与带有特定版本号的客户端：

```
# 更新源并安装基础构建链、LDAP、PAM 以及原生 PG 18 客户端  
sudo apt-get update  
sudo apt-get install -y build-essential pkg-config libicu-dev libssl-dev libldap2-dev libpam0g-dev postgresql-client-18
```

完成环境依赖配置后，即可进入 Rust 源码的编译阶段。这里有一个关键的环境变量 `PGRUST_PGSHAREDIR`，必须指向项目内置的 Postgres 资源目录：

```
# 锁定依赖版本并以 Release 模式编译指定的二进制目标  
PGRUST_PGSHAREDIR="$PWD/vendor/postgres-18.3/share" \  
cargo build --release --locked --bin postgres
```

编译完成后，不能直接拉起服务，必须先创建并初始化专属的数据目录。pgrust 实现的原生参数能够完美对应原版 PG 的行为：

```
# 使用编译生成的二进制文件执行数据库初始化  
target/release/postgres --initdb \  
  -D /tmp/pgrust-data \  
  -L "$PWD/vendor/postgres-18.3/share" \  
  --no-locale \  
  --encoding UTF8 \  
  -U postgres
```

上述代码中，`-D` 参数指定了数据存储的真实路径，`-L` 则是关键的共享资源路径。为了确保回归测试的准确性，这里显式声明了 `--no-locale`（不使用区域特定的排序规则）以及 `UTF8` 编码。

紧接着是启动数据库服务。这也是本地实测中最容易踩坑的地方。由于 Rust 与 C 语言的执行模型在栈空间分配上存在差异，普通的启动命令会导致复杂的查询直接崩溃。必须在宿主机和运行时同时放宽限制：

```
# 临时提升系统单进程的栈空间上限  
ulimit -s 65520  
  
# 显式设定 Rust 最小栈空间，并传入内核参数运行 pgrust  
RUST_MIN_STACK=33554432 target/release/postgres \  
  -D /tmp/pgrust-data \  
  -F \  
  -c listen_addresses= \  
  -k /tmp \  
  -p 5432 \  
  -c io_method=sync \  
  -c max_stack_depth=60000
```

在这里，`RUST_MIN_STACK` 被强制设定为约 32MB，同时通过 `-c max_stack_depth=60000`告知 PG 内部解析器放宽深度限制。这样可以有效防止在解析包含多层嵌套的复杂语法树时，发生严重的栈溢出（StackOverflow）错误。

服务正常驻留后台后，我们可以使用标准的原生 `psql` 客户端工具进行连接测试，验证其行为是否对齐：

```
# 通过本地 Unix Socket 路径连接测试库，并执行版本与基础运算查询  
psql -h /tmp -p 5432 -U postgres -d postgres \  
  -c "select version(), 1 + 1 as two"
```

如果需要验证其完整的正确性，pgrust 还在源码中提供了一套自动化回归测试脚本。它会直接调用内部集成的 4.6 万条真实查询用例进行逐行比对：

```
# 指定编译出的二进制路径，启动原生的回归测试集  
PGRUST_BIN="$PWD/target/release/postgres" \  
scripts/run-regression
```

### 磁盘兼容与架构重构

把代码跑起来并拆解完内核参数后，我重点评估了它的设计哲学。它没有急于去发明一套全新的 SQL 语法，而是先建立了一个极其坚固的对照基准。

**1. 磁盘级的数据目录兼容**  
这是 pgrust 最吸引人的技术决策。它通过 `--initdb` 生成的存储目录，其底层的页结构（Page layout）、WAL 日志（预写式日志，用于崩溃恢复）格式与原生的 Postgres 18.3 完全一致。这意味着你甚至可以直接把一个原生 PG 生成的数据文件夹喂给 pgrust 启动，中途不需要做任何逻辑导表。这种设计大幅降低了后续的迁移试错成本。

**2. 预言机模式的测试对齐**  
在验证准确性上，pgrust 跑通了原生项目自带的 4.6 万条回归测试查询。它将原生 Postgres 作为“预言机（Oracle）”——即输入相同的 SQL，严格比对两者在抽象语法树解析、执行计划生成和最终结果输出上是否做到字节级一致。这种看似笨重但严谨的测试覆盖，是它能自称“Postgres 重写版”的底气所在。

**3. 下一代并发模型：从进程到线程的跃迁**  
虽然当前公开的 v0.1 版本并未彻底完成性能优化，但其尚未发布的内部分支透露了一个关键架构变更：Thread per connection（每个连接分配一个线程）。原生 Postgres 至今仍采用 Process per connection（每个连接分配一个独立进程）模式，这导致在高并发场景下上下文切换和内存开销极大，必须依赖 PgBouncer 等外部连接池。基于 Rust 重写后，pgrust 能够更安全地在内存中实现线程级并发调度，试图从根源上甩掉外部连接池的包袱。

### 避坑与个人判断

客观来看，pgrust 距离真正进入生产环境还有极长的路要走。首先是扩展生态的断层：当前版本暂不兼容 PL/Python、PL/Perl 等严重依赖 C 运行时的过程语言扩展。如果你现有的业务强依赖这些高级语言扩展写存储过程，现阶段根本无法迁移。

其次，官方团队预告的“内部分支在分析型（AP）负载下比原生 PG 快 300 倍，接近 Clickhouse 水平”这一说法，目前仅停留在文字宣称阶段。在开源社区，任何未合入主干并接受第三方 TPC-H 跑分验证的性能大饼，都需要保持合理的怀疑。此外，该项目采用了 AGPL-3.0 协议，这对很多期望将其云端化或闭源商业化的团队来说，也是一道法务红线。

**使用建议**：目前的 pgrust v0.1 完全不适合应用层开发者或 DBA 在生产环境使用。但如果你是一名数据库内核研发人员，或者正试图通过 AI 辅助探索新的存储结构（如官方 路线图提及的无 Vacuum 设计），pgrust 是一个极佳的实验沙盒。它提供了一个被 Rust 强类型和内存安全约束过的干净内核，大大降低了修改数据库底层代码的门槛。
