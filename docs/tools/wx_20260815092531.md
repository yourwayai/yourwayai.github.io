今天我们来实测一个专为「重度 AI 编程助手用户」打造的 macOS 原生菜单栏工具：**`ClaudeBar`**（GitHub: `tddworks/ClaudeBar`）。

随着 Claude Code、Codex、Gemini CLI、GitHub Copilot、Grok Build 等 AI 编程助手在日常开发流中的渗透率飙升，一个极其现实的痛点浮出水面：**每个工具都有独立的配额窗口、计费周期与速率限制，且大多只在 CLI 或 Web 端零星展示剩余量**。

你需要在 Terminal 里反复敲 `claude /usage`、`codex usage`、`gemini quota`，或者频繁切换浏览器查看账单页面，才能拼凑出一个「我还能不能继续跑 Agent」的判断。这种上下文切换的认知负荷，恰恰是 AI 本该帮我们消除的。

`ClaudeBar` 给出的答案极其直接：一个常驻 macOS 菜单栏的原生 SwiftUI 应用，**聚合 13 家主流 AI 服务商的配额数据，通过彩色进度条（绿/黄/红/灰）在一眼之间完成健康度扫描**。更硬核的是，它的名字里带着 `TDD`——全程以「芝加哥学派 TDD」（Chicago School TDD）驱动开发，测试覆盖率在 CI 中强制门槛，探针新增流程甚至内置了 `.claude/skills/add-provider` 技能文档指导贡献者。

#### 部署实录

在 macOS 15.2 (24C101) / Apple Silicon M3 Max 环境下，我们分别验证了 **Homebrew 安装** 与 **源码构建** 两条路径。

**路径一：Homebrew（推荐普通用户）**

```
# 直接安装已公证的 DMG  
brew install --cask claudebar
```

安装完成后，在「系统设置 → 隐私与安全性」允许「ClaudeBar」运行，点击菜单栏图标即可进入主界面。首次启动会引导完成 **Claude CLI / Codex CLI / Gemini CLI 等探针的自动检测**。

**路径二：源码构建（验证开发者工作流）**

```
# 1. 克隆仓库  
git clone https://github.com/tddworks/ClaudeBar.git  
cd ClaudeBar  
  
# 2. 安装 Tuist（Xcode 项目生成器）  
brew install tuist  
  
# 3. 安装依赖并生成 Xcode 工作区  
tuist install  
tuist generate  
open ClaudeBar.xcworkspace
```

在 Xcode 15.4 中 `Cmd+R` 运行，App 会在菜单栏启动。构建日志显示：

```
# Tuist 生成的项目结构  
ClaudeBar.xcworkspace  
├── App                # SwiftUI 入口、菜单栏托管、设置面板  
├── Domain             # QuotaMonitor、Provider 模型、Repository 协议  
├── Infrastructure     # 各 Provider Probe 实现、Keychain 存储、UserDefaults 设置  
└── Tests              # 单元测试 + 集成测试（覆盖率门槛 85%+）
```

**关键依赖检查**：为了让探针正常工作，必须预装对应 CLI 工具并完成认证：

| Provider | CLI 安装命令 | 认证方式 |
| --- | --- | --- |
| **Claude** | 官网下载 `claude` | `claude auth login` |
| **Codex** | `brew install codex` | `codex auth login` |
| **Gemini** | `brew install gemini-cli` | `gcloud auth application-default login` |
| **Kimi** | `uv tool install kimi-cli` | `kimi` 交互式登录 |
| **Kiro** | `uv tool install kiro-cli` | `kiro-cli` 登录 |
| **OpenCode Go** | 官网下载 `opencode` | 自动读取本地 SQLite |
| **Oh My Pi** | `brew install omp` | `omp auth login` |
| **Grok Build** | 官网下载 `grok` | OAuth 流程 |

#### 核心亮点

##### 亮点一：`QuotaMonitor` 单一事实源与「协议依赖注入」架构

阅读 `docs/ARCHITECTURE.md` 与源码后，最令工程师折服的是其**分层架构的纯粹性**：

| 层级 | 职责 | 关键类型 |
| --- | --- | --- |
| **App** | SwiftUI 视图直接消费 Domain，无 ViewModel/AppState | `MenuBarView` 、`SettingsView`、`ProviderRow` |
| **Domain** | 富模型、`QuotaMonitor`（单一事实源）、Repository 协议 | `QuotaMonitor` 、`Provider`、`UsageProbe` 协议 |
| **Infrastructure** | 具体探针实现、Keychain 凭据存储、UserDefaults 设置持久化 | `ClaudeUsageProbe` 、`CodexUsageProbe`、`KeychainCredentialRepository` |

`QuotaMonitor` 持有所有 Provider 的实时配额状态，**视图层零逻辑、零状态**，仅绑定 `QuotaMonitor.providers` 发布的 `@Published` 数据流。这种「单向数据流 + 单一事实源」设计，彻底杜绝了「设置页改了 Provider 开关，菜单栏没刷新」这类状态不同步 Bug。

更妙的是**基于 `@Mockable` 宏的协议依赖注入**：每个 `UsageProbe`、`CredentialRepository`、`SettingsRepository` 均定义为协议，测试时通过 `Mockable` 自动生成 Mock，生产环境注入真实实现。**新增 Provider 只需实现 `UsageProbe` 协议并在 `ProviderRegistry` 注册一行**，零侵入既有代码。

##### 亮点二：13 家 Provider 探针的「异构适配」工程细节

不同 AI 服务商的配额接口五花八门，ClaudeBar 为每家编写了专用 Probe，体现了极强的工程落地能力：

| Provider | 数据来源 | 解析策略 | 特殊处理 |
| --- | --- | --- | --- |
| **Claude** | `claude usage --json` | 解析 `session`/`weekly`/`model` 字段 | 自动检测 CLI 版本兼容性 |
| **Codex** | `codex usage --json` | 读取 `remaining_requests`/`reset_timestamp` | 支持多账户切换 |
| **Gemini** | `gemini quota --format=json` | 解析 `daily_limit`/`remaining` | 需 `gcloud` ADC 认证 |
| **GitHub Copilot** | REST API (`api.github.com/copilot_internal/...`) | OAuth Token + GraphQL 查询 | 需在设置页配置 PAT |
| **OpenCode Go** | 本地 SQLite (`~/Library/Application Support/opencode/usage.db`) | 直接 SQL 查询 `usage_windows` 表 | 免 CLI 调用、零延迟 |
| **Oh My Pi** | `omp usage --json` | 聚合多账户、解析 `rate_limit_window`/`capped_usd` | 支持「封顶美元卡」与「无上限」两种模式 |
| **Grok Build** | `grok credits --format=json` | 解析周窗口 + 子产品限额 | 需 OAuth 本地凭据 |

实测中，**OpenCode Go 与 Oh My Pi 的「免 CLI、直读本地存储」策略响应最快（< 200ms）**，而 GitHub Copilot 受限于网络 API 延迟（约 1.2-2.5s），ClaudeBar 为此在 `QuotaMonitor` 层实现了**并发探针调度 + 独立超时 + 降级缓存**，保证菜单栏渲染永不阻塞。

##### 亮点三：TDD 驱动的「新增 Provider 技能化」流程

项目内置 `.claude/skills/add-provider/SKILL.md`，将「新增一个 Provider」标准化为四步 TDD 闭环：

1. 1. **Parsing Tests** — 先写解析 JSON/CLI 输出的纯函数测试（无副作用、极易覆盖边界）。
2. 2. **Probe Tests** — 用 Mock HTTP/CLI 编写探针集成测试，验证错误重试、超时、熔断。
3. 3. **Implementation** — 实现 `UsageProbe` 协议，注册到 `ProviderRegistry`。
4. 4. **Registration** — 在 `Settings` 中新增开关、在 `Credits` 列出贡献者。

这种**将架构守则显性化为可执行技能文档**的做法，极大降低了贡献者的认知门槛，也解释了为何项目能在短时间内集成 13 家 Provider 且测试覆盖率不降反升。

#### 避坑与总结

在两周日常开发场景（Claude Code + Codex + Gemini 并行）中实测，有几个**必须前置知晓的限制**：

* • **macOS 15+ 硬性门槛**：项目采用 Swift 6.2 语法（`@Observable` 宏、严格并发检查），**最低 macOS 15 (Sequoia)**。Intel Mac 与 macOS 14 及以下用户无法运行，只能等待或自行回滚至 Swift 5 兼容分支（目前官方无维护计划）。
* • **Kimi API 模式需「完全磁盘访问权限」**：若不装 `kimi-cli` 走 API 模式，ClaudeBar 需读取浏览器 Cookie (`~/Library/Cookies/`)，必须在「系统设置 → 隐私与安全性 → 完全磁盘访问权限」添加 ClaudeBar 并重启 App。建议直接 `uv tool install kimi-cli` 走 CLI 模式，零权限、零脆弱性。
* • **GitHub Copilot 探针依赖 Personal Access Token（PAT）**：需在 Settings 页粘贴 `ghp_...` Token（需 `read:user`、`read:org`、`copilot` 权限）。Token 存储在 Keychain，但轮换提醒需自行留意。
* • **菜单栏图标在「刘海屏」极窄状态下可能被遮挡**：当菜单栏项目过多（> 12 个）时，ClaudeBar 图标会被系统隐藏。建议配合 `Bartender` / `Ice` / `Hidden Bar` 等管理工具固定显示。
* • **Christmas 主题仅 12/1-12/25 自动启用**：硬编码日期判断，无法自定义节日。想要万圣节/春节主题需自行导入 `.itermcolors` 或改代码重编译。

对于每天在 Claude Code、Codex、Gemini 之间横跳、且极其在意「配额还能跑多久」的 macOS 开发者，这是**装机必备、零犹豫**的生产力工具。MIT 协议、代码签名公证、Homebrew 分发、Sparkle 自动更新，商业级交付标准在开源项目中极罕见。
