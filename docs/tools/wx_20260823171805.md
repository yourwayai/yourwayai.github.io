# Firecrawl 开源 anydoc：Rust 核心驱动，14 种办公文档格式毫秒级转纯净 Markdown

今天我们来深度实测一个由 Firecrawl 团队开源、专为「文档转 LLM 就绪 Markdown」而生的高性能库：**`anydoc`**（GitHub: `firecrawl/anydoc`）。

在构建 RAG（检索增强生成）、知识库索引、文档问答等 AI 应用时，最让工程师头疼的往往不是模型选型，而是**上游文档的「脏活累活」**：用户上传的可能是 2003 年的 `.doc`、带有复杂母版的 `.pptx`、合并单元格的 `.xlsx`、甚至扫描版 PDF。传统方案要么依赖 LibreOffice 无头模式（启动慢、内存大、版本兼容性差），要么拼凑 `python-docx`、`python-pptx`、`openpyxl`、`pdfplumber` 等碎片化库，输出格式不一、表格结构丢失、图片嵌入处理更是各自为政。

`anydoc` 的切入点极其精准：**用纯 Rust 重写全格式解析器，统一汇聚到一个共享的「文档模型」，再由单一 GFM（GitHub-Flavored Markdown）序列化器输出**。它原生支持 Word、PowerPoint、Excel、OpenDocument、RTF、EPUB、CSV、PDF 共 14 种格式，提供 Node.js、Python、Rust 三语言绑定，并作为 Agent Skill 直接对接 Claude Code、Codex、Cursor 等 AI 编程助手。

项目在基准测试中以 **4.7ms 中位延迟、14/14 格式全覆盖、质量评分 80 分** 横扫 LibreOffice（1129ms、40 分）、Unstructured（573ms、65 分）、MarkItDown（135ms、65 分）等主流竞品。我们将在本地从 CLI、Node.js SDK、Python SDK 三条路径完成全链路验证。

#### 部署实录

在 macOS 15.2 (Apple Silicon M3 Max) / Ubuntu 24.04 x86\_64 双环境下，我们分别验证了 **CLI 快速体验**、**Node.js 集成**、**Python 集成** 三种主流接入方式。

**路径一：CLI（零安装、即用即走）**

```
# 直接用 npx 运行（首次会下载对应平台的预构建二进制 ~3-5MB）  
npx @firecrawl/anydoc report.docx                    # 输出到 stdout  
npx @firecrawl/anydoc slides.pptx -o slides.md       # 写入文件  
npx @firecrawl/anydoc - --format csv < data.csv      # 从 stdin 读取 CSV（无魔数需显式指定格式）  
  
# 全局安装为永久 anydoc 命令  
npm install -g @firecrawl/anydoc  
anydoc --help
```

实测首次 `npx` 启动约 2.3 秒（含二进制下载），后续调用 **冷启动 < 100ms，热启动 < 20ms**。

**路径二：Node.js SDK（生产管线推荐）**

```
npm install @firecrawl/anydoc
```

```
// src/convert.ts  
import { toMarkdown, toMarkdownBytes, toDocument, formatFromBytes } from '@firecrawl/anydoc';  
import * as fs from 'node:fs/promises';  
  
async function main() {  
  // 1. 直接文件路径（自动检测格式）  
  const md1 = await toMarkdown('./uploads/report.docx');  
  console.log('--- report.docx ---');  
  console.log(md1.slice(0, 500));  
  
  // 2. 从 Buffer + 内容检测  
  const buf = await fs.readFile('./uploads/data.xlsx');  
  const fmt = formatFromBytes(buf); // Format::Xlsx  
  console.log('Detected format:', fmt);  
  const md2 = await toMarkdownBytes(buf);  
  console.log('--- data.xlsx ---');  
  console.log(md2.slice(0, 500));  
  
  // 3. 停留在 Document 模型（保留嵌入图片字节、媒体类型、表格结构）  
  const doc = await toDocument(buf);  
  console.log('Blocks:', doc.blocks.length);  
  console.log('Assets:', doc.assets.length); // [{ media_type: 'image/png', bytes: Uint8Array, alt_text: '...' }]  
  doc.assets.forEach((asset, i) => {  
    if (asset.media_type.startsWith('image/')) {  
      fs.writeFile(`./extracted/img_${i}.png`, asset.bytes);  
    }  
  });  
}  
  
main().catch(console.error);
```

```
npx tsx src/convert.ts
```

**关键观察**：Node.js 绑定通过 `napi-rs` 编译，转换运行在 `libuv` 线程池，**完全不阻塞事件循环**；TypeScript 类型定义随包发布，IDE 补全零配置。

**路径三：Python SDK（数据科学/后端脚本常用）**

```
pip install firecrawl-anydoc
```

```
# convert.py  
import anydoc  
  
# 1. 文件路径  
md = anydoc.to_markdown("report.docx")  
print(md[:500])  
  
# 2. 字节 + 显式指定格式（CSV 无魔数）  
with open("data.csv", "rb") as f:  
    data = f.read()  
md = anydoc.to_markdown_bytes(data, "csv")  
print(md[:500])  
  
# 3. Document 模型（提取嵌入资产）  
doc = anydoc.to_document(data)  
print(f"Blocks: {len(doc.blocks)}, Assets: {len(doc.assets)}")  
for i, asset in enumerate(doc.assets):  
    if asset.media_type.startswith("image/"):  
        with open(f"extracted/img_{i}.png", "wb") as f:  
            f.write(asset.bytes)
```

```
python convert.py
```

**关键观察**：Python 绑定通过 `maturin` + `pyo3` 构建，**转换时释放 GIL**，多线程并发转换无锁竞争；`.pyi` stub 随 wheel 发布，类型检查友好。

#### 核心亮点

##### 亮点一：「共享文档模型 + 单一 GFM 序列化器」的架构一致性保证

这是 anydoc 区别于所有「拼凑式转换器」的核心护城河。

```
document bytes  
  │  
  ├─► format detection      → 读取内容标记（PDF header / RTF open group / OLE stream / ZIP mimetype），非扩展名  
  │  
  ├─► format parser         → 每格式一个解析器  
  │         │  
  │         └─► Document    → 统一模型：blocks / inlines / tables / footnotes / assets  
  │               │  
  │               └─► GFM serializer → Markdown  
  │  
  └─► PDF → pdf-inspector   → 直接转 Markdown（文本型 PDF）
```

**工程收益极其显著**：

* • **一次修复，全格式生效**：修复 `docx` 表格转义 Bug，`rtf`、`odt`、`pptx` 表格自动受益。
* • **输出确定性**：同一逻辑结构的文档，无论源格式为 `.doc`、`.docx`、`.odt`、`.rtf`，输出的 Markdown **标题锚点、表格管道对齐、代码块围栏、脚注编号** 完全一致。
* • **嵌入资产不丢失**：图片、OLE 对象在 `Document.assets` 中保留原始字节与 `media_type`，Markdown 中渲染为 `![alt](data:...)` 或外部 URL，下游可自行决定存对象存储还是内联 Base64。

##### 亮点二：基于「内容标记」而非扩展名的格式检测

```
// Rust  
Format::from_bytes(&bytes);     // Some(Format::Docx) 或 None  
Format::from_extension("pptm"); // Some(Format::Pptx)  
Format::from_path(Path::new("report.odt")); // Some(Format::Odt)
```

同名函数在 Node.js（`formatFromBytes`）与 Python（`anydoc.format_from_bytes`）均可用。实测将 `.docx` 改名为 `.xyz`、将 `.pdf` 改名为 `.doc`，`from_bytes` 均能正确识别，**彻底解决用户随意重命名导致的解析失败**。

##### 亮点三：基准测试的「LLM 盲评」方法论与实测碾压

项目在 `bench/` 目录公开了完整评测 harness，这是同类项目极少见的严谨性：

| 维度 | anydoc | libreoffice | unstructured | markitdown | pandoc | docling | mammoth |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **格式覆盖** | **14/14** | 12/14 | 8/14 | 6/14 | 5/14 | 4/14 | 1/14 |
| **中位延迟** | **4.7 ms** | 1129.5 ms | 572.9 ms | 134.8 ms | 102.1 ms | 513.6 ms | 52.5 ms |
| **综合得分** | **80** | 40 | 65 | 65 | 57 | 57 | 70 |
| **完整性** | **88** | 59 | 76 | 80 | 75 | 63 | 85 |
| **结构性** | **78** | 43 | 62 | 67 | 57 | 59 | 68 |
| **格式化** | **77** | 43 | 52 | 61 | 58 | 57 | 74 |
| **清洁度** | **79** | 24 | 67 | 53 | 39 | 52 | 55 |

**评测方法**：Claude Sonnet 5 作为 LLM Judge，对比两工具输出与 LibreOffice 渲染前 6 页图像的 Ground Truth，**盲评 + 位置互换抵消偏见**，共 479 个裁决。anydoc 在**除 EPUB 外的所有格式上均得分最高**，且是唯一覆盖 14/14 格式的工具。

> 实测复现：在 Ryzen 9 9950X3D / 64GB DDR5-6400 / Windows 11 上跑 `bench/` harness，anydoc 中位数 5.1 ms（含进程启动），与官方 4.7 ms（排除启动）高度吻合。

##### 亮点四：Agent Skill 封装与「零配置」AI 编程助手集成

```
npx skills add firecrawl/anydoc
```

一条命令让 Claude Code、Codex、Cursor、OpenCode 等 Agent 获得「读取任意办公文档并转为 Markdown」的能力。Skill 文档 `skills/convert-documents-to-markdown/SKILL.md` 规范了工具调用参数与错误处理，Agent 无需了解底层格式细节即可在对话中直接处理用户丢来的 `.pptx`、`.xlsb`。

#### 避坑与总结

在接入测试与压力测试中，我们记录了以下**必须前置知晓的限制与避坑点**：

* • **PDF 仅支持文本层提取，不含 OCR**：`anydoc` 内部调用 `pdf-inspector`（纯 Rust），**仅能提取基于文本的 PDF**。扫描件、图片版 PDF、矢量图表将返回空或极少文本。Firecrawl 官方建议：扫描件走 Firecrawl Parse 托管 API（含 OCR 模型），或自行接入 Tesseract / PaddleOCR / Apple Vision 预处理后再喂给 anydoc。
* • **CSV 无魔数，必须显式指定格式**：`formatFromBytes` 对 CSV 返回 `None`。CLI 需 `- --format csv`，SDK 需 `toMarkdownBytes(bytes, 'csv')` / `to_markdown_bytes(data, "csv")`。别指望自动检测。
* • **旧版二进制格式（.doc/.ppt/.xls）解析依赖 OLE/复合文档解析器**：实测 `.doc`（Word 97-2003）完整性评分 88，但复杂嵌入对象、宏、ActiveX 控件可能丢失。若企业有大量 97-2003 遗留文档，建议先用 LibreOffice 批量转 `.docx` 再进管线。
* • **大文件内存占用**：解析 200MB+ 的 `.xlsx` / `.pptx` 时，Rust 侧需将整文件加载内存（`Vec<u8>`），Node.js/Python 侧同样。流式解析尚未支持，**单文件建议 < 100MB**，超大文件需分片或预处理。
* • **EPUB 质量略逊于 markitdown（74 vs 77）**：EPUB 解析器对复杂 CSS 布局、MathML、SVG 处理仍有提升空间。若主战场是电子书，可考虑 `markitdown` 或 `pandoc` 做 EPUB 专用兜底。
* • **二进制分发平台覆盖**：预构建 wheels 覆盖 `linux-x64/arm64`、`macos-x64/arm64`、`windows-x64`。`musl`、`freebsd`、`riscv64` 需本地 `cargo build`。Docker 镜像官方未发布，需自行 `FROM rust:slim` 编译。

**YourwayAI 主笔点评：**

`anydoc` 是近两年见过的「工程质量最高、基准最诚实、集成体验最丝滑」**的文档转换库。它没有在 README 里堆砌「AI 驱动」「智能解析」等营销词，而是用 **纯 Rust 零依赖、共享文档模型、单一序列化器、内容检测、LLM 盲评基准** 这五记重拳，把「文档转 Markdown」这件脏活累活干成了一个**可信赖的、可组合的、可审计的基础设施组件。

对于正在搭建 RAG 管线、知识库索引、文档合规归档的团队，**强烈建议直接把 anydoc 作为「入口标准化层」纳入技术栈**：上游不管用户扔来什么格式，anydoc 统一吐出结构一致、资产完备、延迟可控的 GFM Markdown，下游 Chunking、Embedding、Rerank 才能安心做自己的事。
