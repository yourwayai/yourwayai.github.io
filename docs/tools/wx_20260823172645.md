上周末在 GitHub 上看到 Cloudflare 悄悄推了 `@cloudflare/computer`，标题是 "Give your agent a computer 👾"。7.2k star、MIT 协议、三种可插拔后端、README 里加粗写着 "PREVIEW ONLY"。作为一个关注 AI Agent 基础设施的人，这项目正好卡在我的关注列表里：如何让大模型在真实的文件系统、真实的 Shell、真实的网络环境里干活，而不是只能在沙箱里输出文本。

今天在本地把核心包跑通了，记录一下部署过程、核心架构理解、性能实测数据，以及一个绕不开的商业化陷阱。

#### 部署实录

**环境**：MacBook Pro M3 Max / macOS 15.5 / Node.js 22.12.0 / pnpm 9.14.0

```
git clone https://github.com/cloudflare/computer  
cd computer  
pnpm install
```

Monorepo 结构很清晰，五个核心包：

```
packages/  
├── computer/              # 主入口 @cloudflare/computer  
├── dofs/                  # @cloudflare/dofs - Durable Object 虚拟文件系统  
├── rpc/                   # @cloudflare/computer-rpc - Cap'n Web 协议  
├── computerd/             # @cloudflare/computerd - FUSE 守护进程  
└── computer-computerd-linux-x64/  # 预构建的 Linux x64 二进制
```

构建没报错，但要跑通 `examples/container` 需要 Cloudflare 账号、wrangler 登录、且开通 Containers 权限（目前仍在私有 Beta）。为了验证核心逻辑，我改跑了 `examples/worker-shell` —— 纯 Worker 端，无需容器。

```
cd examples/worker-shell  
pnpm install  
pnpm dev
```

`wrangler dev` 启动后，本地跑起一个 Worker，通过 `just-bash` 在 Dynamic Worker 里执行 Shell 命令，读写 Durable Object 后端的虚拟文件系统。真正的 FUSE 挂载只能在 Linux 容器里跑，Mac 上只能走 isolate 后端。

**坑点**：

* • `pnpm install` 会拉取 `@cloudflare/computerd-linux-x64` 这个可选依赖，非 Linux 平台会跳过，但 TypeScript 类型定义里仍引用了它的类型，需在 `tsconfig.json` 里显式 `exclude` 或安装 `@types/node` 补全
* • `just-bash` 目前不支持交互式命令（如 `vim`、`top`），只能跑单次执行命令
* • Durable Object 存储上限 10 GB，含 SQLite 文件系统元数据，跑大模型训练 checkpoint 直接会爆

#### 核心架构：三个后端，一个统一入口

Cloudflare Computer 的核心抽象是 **Workspace** —— 一个活在 Durable Object 里的虚拟文件系统，状态存在 SQLite，通过 `workspace.runtime.exec(source, { backend })` 统一执行入口。

| 后端 | 运行环境 | 适用场景 | 计费 |
| --- | --- | --- | --- |
| **Container** | Cloudflare Container (Linux) + `computerd` FUSE 挂载 | 需要 `npm install`、原生二进制、完整 userland | Container 标准计费，**无 Dynamic Workers 要求** |
| **Isolate Shell** | Dynamic Worker 运行 `just-bash` | 文件读写、git 操作、数据清洗、轻量 Shell 脚本 | **需 Workers Paid Plan ($5/月起)** ，按唯一 Worker/天/百万请求/百万 CPU-ms 计费 |
| **Isolate JavaScript** | Dynamic Worker 运行 ESM 模块 | 纯 JS/TS 计算、结构化数据处理、调用 `node:fs/promises` | 同上，需 Paid Plan |

**关键设计**：

* • **Cap'n Web** 作为 RPC 协议，`computerd` 与 Durable Object 之间同步文件变更。这是 Cloudflare 自研的 Cap'n Proto 变体，支持能力式访问控制
* • **R2 预挂载**：Workspace 创建时可指定只读 R2 bucket，Agent 启动即拥有真实数据集，无需从头下载
* • **AI SDK Tool Calling 原生支持**：`workspace.runtime.exec` 直接兼容 Vercel AI SDK 的 `tool` 格式，Agent 调用无需适配层

#### 实测亮点：computerd FUSE 的性能画像

官方 `docs/19_performance.md` 给出的基准测试环境：Cloudflare Containers `standard-2`（1 vCPU, 6 GiB, 12 GB 磁盘），对比 `tmpfs`（内存盘）与容器根目录 `ext4`。跑的是 `script/fs-bench.sh` + `cloudflare/sandbox-sdk` 全量 `npm install`（854 包、36,675 文件）。

**核心数据（Ratio = computerd / baseline，< 1.0 表示 computerd 更快）**：

| 场景 | computerd | tmpfs | tmpfs ratio | ext4 disk | disk ratio |
| --- | --- | --- | --- | --- | --- |
| create 1000 files | 560.6 ms | 83.2 ms | **6.7x** | 303.2 ms | **1.85x** |
| stat 1000 files | 1971.9 ms | 1324.2 ms | **1.49x** | 2659.3 ms | **0.91x** ✅ |
| rm 1000 files | 827.7 ms | 322.7 ms | **2.56x** | 1281.8 ms | **0.66x** ✅ |
| mkdir tree (10×10×10) | 1597.5 ms | 1585.7 ms | 1.01x | 3034.7 ms | **0.74x** ✅ |
| find tree | 1813.6 ms | 1819.9 ms | 1.00x | 3542.1 ms | **0.51x** ✅ |
| npm install (全量) | 2m 34s | 1m 12s | **2.13x** | 3m 41s | **0.70x** ✅ |

**读法**：

* • **元数据密集型操作**（stat、rm、mkdir、find、npm install 的文件系统阶段）上，computerd **打败 ext4 磁盘**，甚至接近或优于 tmpfs
* • **小文件创建**是明显短板：6.7x 慢于 tmpfs，1.85x 慢于 ext4 —— FUSE 层的 `create` 系统调用开销大
* • **大文件顺序读写**未在表中给出，但文档明确说明 "trails it on large sequential I/O"

这个性能画像决定了适用场景：**Agent 频繁做文件检索、git diff、目录遍历、删除临时文件、跑构建脚本** —— computerd 是加速器；**Agent 需要大量写入小文件、频繁创建临时文件** —— 可能成为瓶颈。

#### 避坑与总结：值不值得折腾？

**值得折腾的场景**：

1. 1. 你在构建 **需要持久化工作目录、跨会话保留状态的 AI Agent**（如代码生成、数据分析、文档生成）
2. 2. 你已经在用 Cloudflare Workers/Containers，**愿意接受 Vendor Lock-in** 换取零运维的 Stateful Compute
3. 3. 你需要 **R2 预加载大数据集** 让 Agent 秒级启动
4. 4. 你接受 **PREVIEW 级 API 变更风险**，且不打算明天上生产

**劝退的场景**：

1. 1. **追求极致性价比**：Isolate 后端强绑定 Dynamic Workers，$5/月地板价 + 按量计费，跑高频 Agent 任务账单不可控。Container 后端虽无此限制，但需申请 Container Beta 资格
2. 2. **需要离线/自托管**：核心依赖 Durable Object + Cap'n Web，想完全跑在自己 Kubernetes 上需自行实现 DO 兼容层 + Cap'n Web 服务端 —— 工作量不小
3. 3. **Windows 原生开发**：`computerd` 仅提供 Linux x64 二进制，Windows 需 WSL2 或远程容器
4. 4. **生产级稳定性要求**：README 明写 "APIs are unstable and the design is subject to change"

**一个没在文档里写明的细节**：Durable Object 的 10 GB 存储上限是**硬限制**，包含 SQLite 数据库文件本身 + WAL 日志 + 文件系统元数据。跑 `npm install` 产生的 `node_modules` 会以极快速度吃光配额。官方建议用 R2 存大文件、Workspace 只存元数据，但这又引入了额外的架构复杂度。

#### 个人判断

Cloudflare Computer **不是一个通用的 "给 Agent 装电脑" 库，而是 Cloudflare 生态内的 Stateful Agent Runtime**。它的技术路线极其清晰：Durable Object 做状态、Cap'n Web 做同步、Dynamic Workers 做弹性计算、Containers 做重负载。每一层都是 Cloudflare 自家基础设施的原子能力组装而成。

如果你已经在 Cloudflare 生态里（Workers、R2、D1、Queues、Containers），这个项目是 **目前最原生、最低集成成本** 的 Agent 基础设施选择。但如果你在 AWS/GCP/自建 K8s，引入它意味着**为了用好 isolate 后端不得不买单 Dynamic Workers，为了用 Container 后端不得不等 Container GA** —— 这是个平台决策，不是库选型。

我会继续关注 `computerd` 的 FUSE 优化（特别是小文件创建路径），以及 `just-bash` 的交互式支持进度。但下一个 Side Project 里，我大概率仍会先用 `firecracker-microvm` + `gVisor` 自己拼一套 —— 至少计费模型我自己说了算。
