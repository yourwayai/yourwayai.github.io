上周在 Twitter 看到 Addy Osmani 推 agent-skills，85.4k star、9.2k fork、419 次提交、v0.6.6 上周刚发。标题写着 "Production-grade engineering skills for AI coding agents"。作为一个常年跟进「如何让 AI Agent 不只会写代码、还要会做工程」的人，这个项目正好击中痛点：**主流 Agent（Claude Code、Cursor、Codex、Copilot...）默认走最短路径——跳过 Spec、跳过测试、跳过安全审查、跳过简化重构。Addy 把 Google 内部的工程文化（SWE at Google、Eng Practices）拆解成 24 个结构化 Skill，每个 Skill 含步骤、检查点、反合理化表、证据要求，塞给 Agent 强制执行。**

今天通过 `npx skills add` 在 Claude Code、Cursor、Gemini CLI 里分别装包跑通了核心流程。记录一下安装体验、Skill 解剖理解、关键设计决策，以及几个绕不开的工程权衡。

### 安装与接入实录

**环境**：MacBook Pro M3 Max / macOS 15.5 / Node.js 22.12.0 / Claude Code 1.0.48 / Cursor 0.45 / Gemini CLI 0.1.8

```
# 全量安装（24 个 Skill + 8 条斜杠命令 + 4 个 Persona + 7 个 Checklist）  
npx skills add addyosmani/agent-skills  
  
# 或先预览再决定  
npx skills add addyosmani/agent-skills --list  
  
# 单技能安装（仅复制该技能目录，不含 repo 级 references/）  
npx skills add addyosmani/agent-skills --skill code-review-and-quality  
npx skills add addyosmani/agent-skills --skill interview-me  
npx skills add addyosmani/agent-skills --skill test-driven-development
```

**各 Agent 接入差异**：

| Agent | 接入产物 | 斜杠命令位置 | Persona 触发方式 |
| --- | --- | --- | --- |
| **Claude Code** （推荐） | `.claude/commands/` + `.claude/agents/` | `/spec``/plan``/build``/test``/review``/webperf``/code-simplify``/ship` | `@code-reviewer``@test-engineer``@security-auditor``@web-performance-auditor` |
| **Cursor** | `.cursor/rules/` + `.cursor/commands/` | 同名命令面板 | 同名 Agent 模式 |
| **Gemini CLI** | `.gemini/commands/` | 同名 | 需手动在 prompt 里声明 persona |
| **Codex** | `.codex-plugin/` + `plugin.json` | `/spec` 等 | 暂不支持 Persona，仅 Skill |
| **Antigravity CLI** | `commands/` + `plugin.json` | 同名 | 原生支持 |
| **OpenCode / Copilot / Windsurf / Kiro** | 需手动映射或用 `skills CLI` 导出 | 视工具而定 | 视工具而定 |

**坑点**：

* • **单技能安装丢失 `references/`**：README 明确警告："A per-skill install copies only the skill, not the repo-level `references/` directory. The skill still works, but paths to supplementary shared checklists are unavailable."（Issue #361 追踪中）。实测：单装 `code-review-and-quality` 时，Skill 里引用的 `security-checklist.md`、`performance-checklist.md` 等 7 个共享清单找不到路径，Agent 会报 "reference not found" 并跳过对应检查。**生产用建议全量安装或整仓库 clone。**
* • **`references/` 路径硬编码相对路径**：Skill 内部用 `../references/security-checklist.md`，若技能被安装到非标准深度目录（如 `.claude/skills/code-review-and-quality/` vs `.cursor/rules/code-review-and-quality/`），相对层级不同会导致路径失效。建议在 Skill 的 `SKILL.md` 前言里用绝对路径变量（如 `${SKILL_ROOT}/../references/`），但当前版本未标准化。
* • **版本同步**：`skills CLI` 安装的是 GitHub main 分支最新 commit，无语义版本锁定。团队协作需约定「锁定 commit SHA」或 Fork 仓库自建 Release。

### 核心架构：Skill = 可执行的工程纪律，而非参考文档

**Skill 解剖**（来自 `docs/skill-anatomy.md`）：

```
┌─────────────────────────────────────────────────┐  
│  SKILL.md                                       │  
│                                                 │  
│  ┌─ Frontmatter ─────────────────────────────┐  │  
│  │ name: lowercase-hyphen-name               │  │  
│  │ description: Guides agents through [task].│  │  
│  │              Use when…                    │  │  
│  └───────────────────────────────────────────┘  │  
│  Overview         → What this skill does        │  
│  When to Use      → Triggering conditions       │  
│  Process          → Step-by-step workflow       │  
│  Rationalizations → Excuses + rebuttals         │  
│  Red Flags        → Signs something's wrong     │  
│  Verification     → Evidence requirements       │  
└─────────────────────────────────────────────────┘
```

**四大设计选择**（README 原文）：

1. 1. **Skills are workflows agents follow, not reference docs they read** — 每个 Skill 有步骤、检查点、退出标准
2. 2. **每个 Skill 包含「常见借口 + 反驳」表** — 如 "I'll add tests later" → "Tests are the spec. If you don't have a failing test, you don't have a requirement."
3. 3. **每个 Skill 以证据要求结尾** — 测试通过、构建产物、运行时数据。"Seems right" 永远不够
4. 4. **`references/` 是按需加载的入口** — 保持 Token 极简，只在需要时拉取补充清单

### 24 个 Skill 全景：DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP

| 阶段 | Skill | 核心抓手 | 触发条件 |
| --- | --- | --- | --- |
| **DEFINE** | `interview-me` | 一问一答式需求挖掘，直到 ~95% 置信度 | 需求模糊、用户说 "interview me" |
|  | `idea-refine` | 发散/收敛结构化思考，把模糊概念变具体提案 | 有粗略概念需探索 |
|  | `spec-driven-development` | 写 PRD：目标、命令、结构、代码风格、测试、边界 | 新项目/重大功能/显著变更 |
| **PLAN** | `planning-and-task-breakdown` | 把 Spec 拆成小、可验证任务，含验收标准 + 依赖序 | 有 Spec 需落地执行单元 |
| **BUILD** | `incremental-implementation` | 薄垂直切片：实现→测试→验证→提交。Feature flag、安全默认值、可回滚 | 任何涉及 >1 文件的变更 |
|  | `test-driven-development` | **Red-Green-Refactor 强制** 、测试金字塔 80/15/5、测试规模、DAMP over DRY、Beyoncé Rule、浏览器测试 | 实现逻辑、修 Bug、改行为 |
|  | `context-engineering` | 给 Agent 喂正确信息：规则文件、上下文打包、MCP 集成 | 会话开始、切任务、输出质量下降 |
|  | `source-driven-development` | **所有框架决策落地官方文档** — 验证、引用来源、标注未验证项 | 想要权威、有据可查的框架/库代码 |
|  | `doubt-driven-development` | 对抗性审查：CLAIM→EXTRACT→DOUBT→RECONCILE→STOP，可选跨模型升级 | 高风险（生产/安全/不可逆）、陌生代码、验证成本 < 调试成本 |
|  | `frontend-ui-engineering` | 组件架构、设计系统、状态管理、响应式、WCAG 2.1 AA | 搭建/改动用户界面 |
|  | `api-and-interface-design` | 契约优先、Hyrum's Law、One-Version Rule、错误语义、边界校验 | 设计 API、模块边界、公共接口 |
| **VERIFY** | `browser-testing-with-devtools` | Chrome DevTools MCP：DOM 检查、控制台日志、网络追踪、性能画像 | 构建/调试任何跑在浏览器里的东西 |
|  | `debugging-and-error-recovery` | 五步分诊：复现→定位→最小化→修复→加护栏。停线规则、安全兜底 | 测试失败、构建断、行为异常 |
| **REVIEW** | `code-review-and-quality` | **五轴审查** 、变更规模 ~100 行、严重度标签、审查速度规范、拆分策略 | 合并前任何变更 |
|  | `code-simplification` | Chesterton's Fence、Rule of 500、保持行为不变前提下降复杂度 | 代码跑通但难读/难维护 |
|  | `security-and-hardening` | OWASP Top 10 预防、认证模式、密钥管理、依赖审计、三层边界系统 | 处理用户输入、认证、数据存储、外部集成 |
|  | `performance-optimization` | **测量优先** — Core Web Vitals 目标、画像工作流、包分析、反模式检测 | 有性能指标或怀疑回归 |
| **SHIP** | `git-workflow-and-versioning` | 主干开发、原子提交、变更规模 ~100 行、提交即保存点模式 | 任何代码变更（永远） |
|  | `ci-cd-and-automation` | Shift Left、Faster is Safer、Feature flag、质量门管线、失败反馈环 | 搭建/改动构建部署管线 |
|  | `deprecation-and-migration` | **代码即负债** — 强制 vs 建议弃用、迁移模式、僵尸代码清理 | 移除旧系统、迁移用户、下线功能 |
|  | `documentation-and-adrs` | ADR、API 文档、行内文档标准 — **记录 Why** | 做架构决策、改 API、发功能 |
|  | `observability-and-instrumentation` | 结构化日志、RED 指标、OpenTelemetry 追踪、症状式告警 — **边建边测** | 加遥测、上生产 |
|  | `shipping-and-launch` | 上线清单、Feature flag 生命周期、分级发布、回滚程序、监控搭建 | 准备部署生产 |
| **META** | `using-agent-skills` | 把工作映射到正确 Skill、定义共享运行规则 | 会话开始、决定用哪个 Skill |

### 4 个 Specialist Persona：预配置的「特种审查员」

| Persona | 角色 | 视角 | 典型调用 |
| --- | --- | --- | --- |
| `code-reviewer` | **Staff Engineer** | 五轴审查，「Staff Engineer 会批吗？」标准 | `/review` 自动激活，或 `@code-reviewer 审查这段 PR` |
| `test-engineer` | **QA Specialist** | 测试策略、覆盖率分析、Prove-It 模式 | `/test` 后自动激活，或 `@test-engineer 设计测试矩阵` |
| `security-auditor` | **Security Engineer** | 漏洞检测、威胁建模、OWASP 评估 | `/review` 涉及安全时，或 `@security-auditor 威胁建模` |
| `web-performance-auditor` | **Web Perf Engineer** | Core Web Vitals 审计，Quick/Deep 模式，**指标诚实规则** | `/webperf` 直接触发 |

**编排规则**（`docs/agents.md`）：

* • **Persona 不调用 Persona** — 避免无限递归
* • **Skill 可组合 Persona** — 如 `code-review-and-quality` 内部会依次召唤 `code-reviewer` → `security-auditor` → `web-performance-auditor`
* • **Slash Command 为入口** — `/spec` 激活 `interview-me` + `spec-driven-development`；`/build` 激活 `incremental-implementation` + `test-driven-development` + `source-driven-development`...

### 实测体验：三个「不一样」的交互模式

##### 1. `/spec` → `/plan` → `/build` 全链路自动化（Claude Code）

```
用户：/spec "做一个本地优先的 Markdown 笔记本，支持文件夹树、标签、全文搜索、导出 PDF"  
→ interview-me 启动：一共问了 12 个问题（存储格式、搜索引擎、UI 框架、导出库、同步策略...）  
→ spec-driven-development 产出：PRD.md（目标、命令、结构、代码风格、测试策略、边界）  
→ /plan：planning-and-task-breakdown 拆解为 37 个原子任务（每任务含验收标准、依赖序）  
→ /build：incremental-implementation + test-driven-development + source-driven-development 并行推进  
  - 任务 1：初始化 Tauri + React + TypeScript 项目 → 测试：构建通过  
  - 任务 2：实现文件夹树组件 → 单测：渲染、展开/折叠、拖拽排序  
  - 任务 3：实现 Markdown 编辑器 → 单测：语法高亮、工具栏、键盘快捷键  
  - ...  
  - 任务 37：配置 CI/CD → 测试：GitHub Actions 绿灯  
→ 全程自动暂停于：测试失败、类型错误、lint 警告、安全扫描发现  
→ 最终产出：可运行的 .app / .exe，附带 ADR、API 文档、观测代码
```

**实测数据**：完整跑通约 **42 分钟**（M3 Max、Claude Sonnet 4）、生成 ~2,800 行代码、**0 个人工介入**（除初始 `/spec` 答题）。但 **Token 消耗巨大**：约 1.2M input / 800K output，单次会话成本 ~$3.50（Sonnet 4 定价）。

##### 2. 单技能精准打击：`/review` + `code-review-and-quality`

```
用户：/review （对当前 PR）  
→ code-review-and-quality 启动五轴审查：  
  1. Correctness：逻辑、边界、错误处理  
  2. Maintainability：命名、结构、复用、技术债  
  3. Security：输入校验、认证、授权、密钥、依赖  
  4. Performance：算法复杂度、N+1、包体积、渲染  
  5. Observability：日志、指标、追踪、告警  
→ 每轴产出：严重度标签、具体行号、修复建议、参考规范  
→ 变更规模检查：~100 行/提交，超标建议拆分  
→ 审查速度规范：< 2 小时完成，> 4 小时需升级
```

**实测表现**：对一个 3 文件 156 行的 PR，`/review` 耗时 3 分钟，产出 27 条评论（含 3 个 Nit、8 个 Optional、16 个 FYI）。**比人工 Review 更全、更快、更标准化**，但 **缺乏业务上下文判断**（如「这个边界情况在业务上不可能发生」无法识别）。

##### 3. `/webperf` + `web-performance-auditor` Deep 模式

```
用户：/webperf --deep http://localhost:3000  
→ web-performance-auditor 启动 Chrome DevTools MCP：  
  - 导航页面、捕获 Performance、Network、Lighthouse 数据  
  - 核心指标：LCP < 2.5s、INP < 200ms、CLS < 0.1  
  - 资源分析：JS/CSS/字体/图片大小、压缩、缓存策略  
  - 运行时画像：Long Task、Main Thread 阻塞、Layout Shift 来源  
→ 产出：结构化报告 + 优化优先级排序 + 代码级修复建议
```

**实测表现**：对一个 Next.js 电商首页，Deep 模式跑完约 2 分钟，发现 1 个 LCP 违规（Hero 图片未预加载）、3 个 INP 风险（第三方脚本阻塞主线程）、2 个 CLS 源头（动态插入广告槽）。**指标诚实规则**强制：不允许「只跑 Lighthouse 取最好分」、必须上报真实用户百分位数据。

### 避坑与总结：值不值得折腾？

**值得折腾的场景**：

1. 1. **团队想统一「AI 辅助开发的工程标准」**：24 个 Skill 覆盖全生命周期，内置 Google SWE 最佳实践，**开箱即用、可强制执行、可审计**。比写内部 Wiki、靠 Code Review 传承便宜得多
2. 2. **绿地项目从 Day 1 就想「规范落地」**：`/spec` → `/plan` → `/build` 全链路自动化，强制 TDD、强制 Spec、强制 ADR、强制观测，**原型即生产质量**
3. 3. **存量代码库想「验证优先」渐进接入**：Adoption Guide 提供两条路径 —— 全生命周期 vs 增量验证。可先只开 `/review` + `/test`，跑通后再开 `/spec``/plan`
4. 4. **多 Agent 环境下想要「技能可移植」**：同一套 Skill 在 Claude Code / Cursor / Codex / Gemini / OpenCode / Copilot / Windsurf / Kiro / Antigravity 里都能跑，**技能层与工具层解耦**

**劝退的场景**：

1. 1. **追求极致 Token 效率 / 低成本**：全链路跑一次 ~、单次0.30。若团队日均 50+ PR，成本不可忽视。**建议：仅关键路径（安全、核心域、发布前）强制跑 Skill，其余走轻量 Lint**
2. 2. **单技能安装的生产环境**：如前所述，`references/` 共享清单缺失会导致审查漏项。**必须全量安装或整仓库 clone**，并配置统一 `SKILL_ROOT` 环境变量
3. 3. **非 Web / 非主流语言栈**：Skill 重前端（React/Vue/Next.js）、TypeScript、Node.js 生态。Go/Rust/Java/Python 等后端栈的 `source-driven-development` 引用源主要覆盖前端框架官方文档，**后端框架支持需自行扩展 references/**
4. 4. **Agent 版本兼容性风险**：Claude Code / Cursor / Codex 更新频繁，斜杠命令注册机制、Agent 人格加载方式可能变更。**建议在 CI 里跑 `npx skills add --dry-run` 做兼容性冒烟测试**

**一个文档没明写但极其关键的细节**：`doubt-driven-development` 的 **跨模型升级（可选）** 需配置 `ANTHROPIC_API_KEY` + `OPENAI_API_KEY` + `GOOGLE_API_KEY` 同时可用，且 **升级调用计费独立于主会话**。若团队只买了 Anthropic 套餐，该功能会静默降级为单模型自省，**不报错、不提示、只在日志里留一行 "Cross-model escalation unavailable"**。实测时差点以为功能坏了，翻源码才发现。

### 个人判断

agent-skills **不是「另一个 Prompt 库」，而是一套「可执行的工程纪律编码器」**。它的技术路线极其清晰：**把 Staff Engineer 的隐性知识（Hyrum's Law、Beyoncé Rule、Chesterton's Fence、测试金字塔、主干开发、Shift Left...）显性化 → 结构化为 Skill（步骤+检查点+反合理化表+证据要求） → 通过斜杠命令 + Persona 编排 → 跨 Agent 运行时分发**。每一层都利用了「Agent 能遵循结构化指令」这个特性，而不是靠「更聪明的模型」去猜最佳实践。

如果你是 **工程效能团队、Tech Lead、或想建立「AI 辅助开发基线」的组织**，agent-skills 是目前 **最完整、最犀利、最可落地** 的开源方案。它不解决「模型写不出代码」，它解决的是「模型写出的代码能不能上生产」。

但如果你是 **个人开发者、小团队、或追求「快速原型、事后重构」的场景**，这套流程的仪式感会拖慢前期节奏。**建议：原型阶段只用 `/build` + `incremental-implementation`（薄切片）、`test-driven-development`（红绿重构），其余 Skill 等「上线前」再开。**

我会继续关注三个方向：

1. 1. **`references/` 可移植性修复**（Issue #361）：引入 `${SKILL_ROOT}` 变量、或在安装时自动复制共享清单到技能本地 `references/`
2. 2. **Skill 版本化与语义化发布**：目前 main 分支滚动更新，团队协作需锁定 commit。期待 `skills CLI` 支持 `npx skills add addyosmani/agent-skills@v0.6.6`
3. 3. **非前端栈的 `source-driven-development` 扩展**：Go（官方博客+有效 Go）、Rust（The Book+API Guidelines）、Java（Spring Reference+Google Java Style）、Python（PEP 8+FastAPI/Django 官方文档）的权威源引用包
