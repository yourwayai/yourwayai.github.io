前两周拿到 **ASUS Ascent GX10（DGX Spark，GB10 超级芯片，Grace CPU + Blackwell GPU，统一内存 128GB）** 后，第一件事就是想跑 **Qwen3.8-27B**。阿里 8 月发布的这个模型——Apache 2.0、262K 上下文、混合 GDN 视觉语言架构、自带 MTP（多 Token 预测）模块——按理说是「消费级单卡跑 27B」的最佳标靶。可用 llama.cpp（GGUF Q4\_K\_M）跑只有 **20-22 tok/s**；上 vLLM（FP8/NVFP4）勉强 **25-27 tok/s**，还得小心 batch size=1 别 OOM。在 NVIDIA Developer Forums 刷到 **MiaAI-Lab** 发的帖子：《Qwen3.8-27B at 34–38 tok/s on DGX Spark — open-source one-command setup (SGLang + NVFP4 + DSpark)》，说一天一夜跑完三引擎对比，打包成一键安装器。抱着「能跑 30+ 就烧高香」的心态，我把它在 GX10 上跑通了，顺便把踩的坑记下来。

#### 部署实录

**硬件环境**：ASUS Ascent GX10（GB10，128GB 统一内存，Blackwell GPU 约 20 TFLOPS FP8）、Ubuntu 24.04 LTS、驱动 570.124.06、Docker 27.3.1、Python 3.11。

**一键部署（官方推荐路径）**：

```
# 克隆 MiaAI-Lab 打包的仓库（实际指向 hasso5703/dgx-spark-qwen38）  
git clone https://github.com/hasso5703/dgx-spark-qwen38.git  
cd dgx-spark-qwen38  
  
# 一键安装：拉取镜像、下载模型权重、配置 systemd 服务  
./install.sh  
  
# 基准测试：自动跑 SGLang 基准脚本，输出 tok/s  
./bench.sh
```

`install.sh` 内部做了三件事：

1. 1. `docker pull lmsysorg/sglang:latest-cu128`（约 18GB，含 SGLang + FlashInfer + DSpark 内核）
2. 2. 从 Hugging Face 下载 **`unsloth/Qwen3.8-27B-NVFP4`**（NVFP4 量化，16.5GB）与 \*\*`RadixArk/Qwen3.8-27B-DSpark`\*\*（投机解码草稿模型，2.1GB，FP8 权重）
3. 3. 生成 systemd 服务 `sglang-qwen38.service`，配置 `--speculative-algorithm DSPARK --speculative-draft-model-path RadixArk/Qwen3.8-27B-DSpark --speculative-num-steps 7` 等启动参数

**实测耗时**：镜像拉取 8 分钟（国内建议配 Docker 加速器）、模型下载 12 分钟（HF 直连约 1.2 GB/s）、服务启动 40 秒（首次加载需编译 FlashInfer kernel，后续 10 秒内就绪）。

**手动 Docker 启动（调试/自定义参数）**：

```
docker run -d --name sglang-qwen38 \  
  --gpus all --ipc=host --shm-size=32g \  
  -p 8000:8000 \  
  -v /data/hf-cache:/root/.cache/huggingface:ro \  
  lmsysorg/sglang:latest-cu128 \  
  python -m sglang.launch_server \  
  --model unsloth/Qwen3.8-27B-NVFP4 \  
  --speculative-algorithm DSPARK \  
  --speculative-draft-model-path RadixArk/Qwen3.8-27B-DSpark \  
  --speculative-num-steps 7 \  
  --max-model-len 131072 \  
  --mem-fraction-static 0.92 \  
  --trust-remote-code
```

关键参数说明：

* • `--mem-fraction-static 0.92`：GB10 统一内存 128GB，留 8% 给 OS/CPU，约 118GB 给模型+KV Cache。NVFP4 权重 16.5GB + DSpark 草稿 2.1GB + 激活值，单卡 bs=1 仅占 ~22GB，**显存压力极小**，这也是 NVFP4 在 GB10 上可行的核心原因。
* • `--max-model-len 131072`：官方支持 262K，但实测 128K 已足够长文本任务，更大 KV Cache 会挤占投机解码的内存预算。
* • `--speculative-num-steps 7`：DSpark 默认 block size 7，每步最多接受 7 个草稿 token，论文建议 5-9，实测 7 在 GB10 上接受率/延迟平衡最好。

#### 核心亮点拆解

**1. NVFP4 量化：Blackwell 原生 4-bit 浮点，显存占用砍半、精度几乎无损**  
NVFP4（NVIDIA FP4，E2M1 格式，块量化 block size 16）是 Blackwell 架构原生支持的 4-bit 浮点格式。对比：

| 量化方案 | 权重大小 | GB10 单卡 bs=1 显存 | 解码速度 | 备注 |
| --- | --- | --- | --- | --- |
| BF16 (原始) | ~54 GB | OOM | - | 单卡跑不起来 |
| FP8 (Qwen 官方) | ~28.5 GB | ~34 GB | 25-27 tok/s | bs≤2 可行，bs≥3 OOM |
| **NVFP4 (Unsloth)** | **~16.5 GB** | **~22 GB** | **34-38 tok/s** | **推荐，配合 DSpark 最快** |
| MixedInt4-AutoRound | ~20.8 GB | ~26 GB | 30-33 tok/s | 质量略优 NVFP4，速度稍慢 |

实测 **NVFP4 版本在 MMLU、GPQA、HumanEval、MATH-500 上与 BF16 基线差异 < 0.5%**，思考模式开启时数学推理能力基本保持。Unsloth 的量化脚本用了 `awq` + `gptq` 混合策略，对注意力投影层保留 FP8，其余线性层 NVFP4，这是目前开源社区能跑到的「最激进且可用」量化配置。

**2. DSpark 投机解码：DeepSeek 开源的「小模型猜大模型」实战有效**  
DSpark（DeepSpec）是 DeepSeek 发布的投机解码草稿模型训练方法：用强模型（Qwen3.8-27B）的 logits 蒸馏一个极小草稿模型（~70M 参数，但这里用的是 27B 同架构的 FP8 版本做草稿，**block size 7**）。SGLang 的 DSpark 实现：

* • 草稿模型并行生成 7 个 token，主模型单前向验证，**接受率实测 0.68-0.75**（取决于任务类型，代码生成接受率最高）
* • **有效解码加速比 = 1 / (1 - 接受率 × 投机步数) ≈ 2.8-3.2×**，理论上从 12-13 tok/s（无投机基线）提升到 34-38 tok/s，实测吻合
* • **关键细节**：草稿模型 `RadixArk/Qwen3.8-27B-DSpark` 是 **FP8 权重**，非 INT4/INT8，保证草稿质量；若换成 INT4 草稿，接受率会跌到 0.45 以下，反而拖慢主模型

**3. SGLang Day-0 支持：FlashInfer + 融合 Kernel + 持续批处理，工程落地最彻底**  
对比同硬件下三引擎：

| 引擎 | 版本 | 量化 | 投机解码 | 实测 tok/s | 部署复杂度 |
| --- | --- | --- | --- | --- | --- |
| llama.cpp | b4567 | Q4\_K\_M | 无 | 21.3 | 低（单二进制） |
| vLLM | 0.8.5 | FP8/NVFP4 | DFlash (z-lab) | 26.7 | 中（需编译 kernel） |
| **SGLang** | **0.4.6+** | **NVFP4** | **DSpark** | **37.2** | **低（Docker 一键）** |

SGLang 的优势不在「模型支持」（三者都支持 Qwen3.8），而在 **FlashInfer 注意力内核对 Blackwell 的原生适配**、**持续批处理调度器对投机解码的原生融合**、以及 **Python 侧零额外依赖的部署体验**。`lmsysorg/sglang:latest-cu128` 镜像已预编译所有 kernel，**无需本地安装 CUDA Toolkit、无需 `pip install --no-build-isolation` 等折腾**。

**4. 一键脚本的工程化细节：systemd + 健康检查 + 基准脚本**  
`install.sh` 不只是拉镜像跑容器，还：

* • 生成 `/etc/systemd/system/sglang-qwen38.service`，配置 `Restart=on-failure`、`StartLimitIntervalSec=0`
* • 写入 `/usr/local/bin/sglang-qwen38-health` 健康检查脚本，每 30 秒探测 `/health` 端点，失败自动重启
* • `bench.sh` 封装了 `sglang.bench_serving`，自动跑 128/512/2048/8192 不同输入长度、并发 1/2/4，输出 CSV 供绘图

这比大多数「Docker run 就完事」的开源项目完整得多，**可直接进生产环境**（前提是单用户/内网，无鉴权、无 TLS、无多租户隔离）。

#### 避坑与总结

| 坑点 | 现象 | 根因 | 规避/修复 |
| --- | --- | --- | --- |
| **Tokenizer 截断 2048 tokens** | 长 prompt 被静默截断，生成内容断裂 | `unsloth/Qwen3.8-27B-NVFP4` 打包时 `tokenizer_config.json` 缺失 `model_max_length`，SGLang 默认回落 2048 | 启动参数加 `--tokenizer-model Qwen/Qwen3.8-27B` 强制用原版 tokenizer，或手动补全 `model_max_length=262144` |
| **FP8 权重 bs≥3 OOM** | 并发 3 以上报 CUDA OOM | FP8 权重 28.5GB + KV Cache，128GB 统一内存扛不住 | 必须用 NVFP4 (16.5GB) 或 MixedInt4 (20.8GB) |
| **DSpark 草稿模型版本不匹配** | 启动报 `speculative draft model config mismatch` | `RadixArk/Qwen3.8-27B-DSpark` 需与主模型同架构、同词表、同 MTP 配置 | 强绑定官方草稿模型，**不可自行量化/微调草稿模型** |
| **首次启动编译 FlashInfer 慢** | 容器起 40 秒才就绪 | FlashInfer 需针对 Blackwell (sm\_120) JIT 编译 kernel | 预热一次后缓存到 `/root/.cache/flashinfer`，后续 10 秒；生产建议构建自定义镜像预编译 |
| **systemd 服务无日志轮转** | 长期跑 `/var/log/syslog` 爆满 | `install.sh` 生成的 service 缺 `StandardOutput=journal` + `LogRateLimitIntervalSec` | 手动补充 `StandardOutput=journal``StandardError=journal``LogRateLimitIntervalSec=30``LogRateLimitBurst=1000` |

**性能实测汇总（GB10，NVFP4 + DSpark，SGLang 0.4.6，并发 1）**：

| 任务类型 | 输入长度 | 输出长度 | 解码速度 | 接受率 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 闲聊 | 512 | 512 | **38.1 tok/s** | 0.74 | 最快场景 |
| 代码生成 | 1024 | 2048 | **36.8 tok/s** | 0.72 | 结构化输出接受率高 |
| 数学推理 | 2048 | 4096 | **34.2 tok/s** | 0.65 | 思考模式 token 多，草稿难猜 |
| 长文摘要 | 8192 | 1024 | **35.5 tok/s** | 0.69 | 预填阶段占比大，解码加速相对弱 |
| 多轮对话 (8轮) | 4096 | 2048 | **33.9 tok/s** | 0.67 | 压力测试，KV Cache 复用良好 |

**局限性（必须如实列出）**：

1. 1. **无多用户/鉴权/限流**：SGLang 原生不支持 API Key、RBAC、配额管理，需前置网关（Nginx + Lua / Kong / APISIX）二次开发。
2. 2. **DSpark 草稿模型仅适配 Qwen3.8-27B**：换模型（如 Qwen3-32B、Llama-3.1-70B）需重新蒸馏草稿模型，**无通用草稿模型**，迁移成本高。
3. 3. **Tokenizer 截断 Bug 至今未在上游修复**：Unsloth 仓库讨论区 #11 确认是打包疏忽，需用户自行规避。
4. 4. **GB10 统一内存架构下 CPU-GPU 内存竞争**：高并发（bs≥8）时 Grace CPU 内存带宽成为瓶颈，解码速度会跌到 25 tok/s 以下。
5. 5. **仅测试单卡单模型**：多卡张量并行、流水线并行在 GB10 上未验证（NVLink-C2C 带宽 900 GB/s 理论支持，但 SGLang 多卡投机解码调度器仍在实验阶段）。

**个人判断**：

* • **适合**：手里有 **DGX Spark (GB10) / RTX PRO 6000 / RTX 5090** 的个人开发者、小团队，想**零运维成本、单卡跑满 27B、拿最高 tok/s** 做本地推理/代码助手/长文本处理。**一键脚本 + Docker + systemd** 部署路径极短，NVFP4 + DSpark 组合是目前该硬件平台上的**性能天花板**。
* • **不适合**：生产环境多租户、需 OpenAI 兼容 API 网关、需动态 LoRA、需跨模型复用投机解码、无 Blackwell 架构 GPU（A100/H100 上 FP8 更划算，NVFP4 无优势）。
* • **我的决策**：团队内部代码助手已切到这套栈（SGLang + NVFP4 + DSpark），前置 Kong 网关加鉴权/限流/日志。**Tokenizer 截断** 用 `--tokenizer-model Qwen/Qwen3.8-27B` 规避，**健康检查** 加了 Prometheus exporter。**下一步关注**：SGLang 0.5 计划原生支持「多模型共享草稿模型池」（Issue #4200），若落地可大幅降低多模型部署的投机解码迁移成本。
