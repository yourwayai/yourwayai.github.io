8 月 13 日 DeepSeek 官方发布 **DeepSeek Harness (dsh)**，标语是 **"Everything is a Plugin"**，MIT 协议，基于 **Cordis** 插件框架（Koishi 聊天机器人框架用了 4 年的内核）。第一时间在 **MacBook Pro M3 Max (macOS 15.6, Node 22.19, pnpm 9.12)** 上跑通了全流程，把「开发者预览版」的坑、架构细节、四种运行模式的区别记下来——这东西不是给终端用户用的，是给**想自己组装 Agent 运行时的工程师**用的。

#### 部署实录

**环境前置**：Node.js ≥ 22（建议 22.19+）、pnpm ≥ 9（`corepack enable && pnpm install -g pnpm`）、Git。Windows 需额外装 `windows-build-tools` 编译原生依赖。

**路径 1：npx 一键体验（最快，约 2 分钟冷启动）**

```
npx @deepseek-ai/dsh web  
# 输出：  
# 🌐 DeepSeek Harness Web UI running at http://127.0.0.1:3080  
# 📝 Open the URL in your browser to start
```

浏览器打开 `http://127.0.0.1:3080`，看到设置向导：**填 DeepSeek API Key → 保存 → 即可对话**。模型路由即时生效，**无需重启服务**。这套流程走的是预构建二进制分发，适合「先跑起来看看长啥样」。

**路径 2：源码构建（二次开发/调试插件/贡献代码必走）**

```
git clone https://github.com/deepseek-ai/deepseek-harness.git  
cd deepseek-harness  
pnpm install          # ~45 秒（M3 Max），下载依赖含 @deepseek-ai/cordis 等内部包  
pnpm run build        # ~2 分 10 秒，编译 TypeScript + 构建前端产物（Vite + React）  
pnpm dsh web          # 源码方式启动 Web UI，端口同 3080
```

**关键坑点**：**千万别跳过 `pnpm run build`**。官方 README 写了，但很多人 clone 完直接 `pnpm dsh web` 报错 `Cannot find module '@deepseek-ai/cordis'`——因为 `packages/*` 下的内部包未链接、前端资源未构建。构建产物在 `packages/*/dist` 与 `apps/web/dist`，**生产运行必须依赖这些产物**。

**路径 3：Headless CLI 模式（自动化/基准测试/CI 集成）**

```
# 使用预设配置跑单次任务  
pnpm dsh --profile headless --config examples/headless-agent/cordis.yml "帮我写一个冒泡排序"  
  
# 或直接用 npx（需先配好 ~/.config/dsh/ 目录下的 cordis.yml 与 API Key）  
npx @deepseek-ai/dsh --profile headless "重构这个 React 组件用 useMemo 优化"
```

Headless 模式**只加载最小插件集**（shell tool + file editor），无 Web UI、无会话持久化、无审批流，**适合跑基准、做回归测试、接入 CI**。

#### 核心亮点拆解

**1. Cordis 插件内核：「万物皆插件」不是口号，是运行时结构**  
Cordis 是一个 **微内核式插件框架**，核心职责仅三件：**插件加载/卸载/生命周期管理、依赖解析与拓扑排序、共享上下文的服务/事件/副作用路由**。整个 dsh 进程启动时，构建的是一棵 **插件树**：

```
根上下文  
├── @deepseek-ai/plugin-model-router      # 模型路由（可替换为自定义 provider）  
├── @deepseek-ai/plugin-tool-registry     # 工具注册表（shell、file、web search 等皆为插件）  
├── @deepseek-ai/plugin-session-log       # 会话日志（可换 SQLite/PostgreSQL/内存）  
├── @deepseek-ai/plugin-approval          # 审批流（人工确认危险操作）  
├── @deepseek-ai/plugin-sandbox           # 沙箱执行环境（可换 Docker/gVisor/Firecracker）  
├── @deepseek-ai/plugin-agent-loop        # Agent 循环本身（Standard/Code/Minimal 不同实现）  
└── @deepseek-ai/plugin-web-ui            # Web UI（仅 web profile 加载）
```

**每个插件向共享上下文贡献三类能力**：

* • **服务**：`ctx.provide('serviceName', implementation)`，其他插件通过 `ctx.inject('serviceName')` 消费
* • **类型化事件**：`ctx.emit('event:name', payload)` / `ctx.on('event:name', handler)`，解耦调用链
* • **可逆副作用**：**这是 Cordis 最大的理论创新**——副作用（文件写入、shell 执行、网络请求）必须声明 `revert()` 逻辑，框架在事务回滚、插件卸载、错误恢复时自动调用。类比数据库事务的「补偿事务」，把「撤销」提升为一等公民。

**2. Profile + Bundle + Patch 三层配置树：运行时组合显式化**  
启动命令 `dsh --profile web --dump-config` 能打印出**当前机器上实际启动的完整配置树**，每一项都可被用户的 patch 替换。加载顺序：

1. 1. **Profile 列出的 Bundle 按序叠加**（如 `web` profile 包含 `base` + `web-ui` + `approval` + `sandbox` 等 Bundle）
2. 2. **Profile 级 `cordis.patch.yml`** 覆盖/增删插件配置
3. 3. **Home 级 patch**（`~/.config/dsh/cordis.patch.yml`）用户级定制
4. 4. **CLI `--patch` overlay** 临时覆盖（最高优先级）

这意味着：**同一份代码库，通过配置组合就能跑出完全不同的 Agent 形态**——无需 fork 代码、无需维护长期分支。对比 Claude Code「单一二进制、配置仅限 JSON」、OpenHands「插件机制弱、核心逻辑硬编码」，这是显著的架构差异。

**3. 四种预设模式：针对不同任务量级加载不同插件组合**

| 模式 | Profile | 核心插件集 | 适用场景 | 启动耗时 |
| --- | --- | --- | --- | --- |
| **Web** | `web` | 完整栈（模型、工具、会话、审批、沙箱、Agent Loop、Web UI） | 日常编码、对话、可视化调试 | ~3 秒 |
| **Code** | `code` | Web 核心 + `code-orchestrator`（模型生成代码编排多轮工具调用） | 复杂重构、多文件协同、需代码级编排 | ~3 秒 |
| **Minimal** | `minimal` | 仅 shell tool + file editor + 基础模型路由 | **基准测试** 、极简环境评测模型能力 | ~1 秒 |
| **Creator** | `creator` | Web 核心 + `runtime-inspector` + `plugin-playground` + `preset-author` | **运行时检查、插件实验、预设组合开发** | ~4 秒 |

**Code 模式的关键差异**：它不预设工具调用链，而是让模型**生成 TypeScript 代码**（运行在沙箱中）来编排多轮工具调用——类似「用代码写 Agent 工作流」。这比 ReAct/Function Calling 更灵活（支持循环、条件、变量复用），但对模型编码能力要求高，**实测 DeepSeek-V3.1/DeepSeek-R1 效果最好，GPT-4o 次之，小模型极易生成不可运行代码**。

**4. 模型适配器插件化：接任意模型只需实现一个接口**  
`@deepseek-ai/plugin-model-router` 内置 DeepSeek 官方 API、OpenAI 兼容、Anthropic 兼容三类路由。要接自模型/本地模型/Ollama/vLLM，只需写个插件实现 `ModelAdapter` 接口：

```
interface ModelAdapter {  
  readonly id: string  
  readonly name: string  
  chatCompletion(req: ChatCompletionRequest): Promise<ChatCompletionResponse>  
  streamChatCompletion(req: ChatCompletionRequest): AsyncIterable<ChatCompletionChunk>  
  countTokens(messages: Message[]): number  
}
```

官方文档给了两个环境变量快捷方式：`DSH_OPENAI_BASE_URL` + `DSH_OPENAI_API_KEY`（走 OpenAI 兼容路由）、**无需写插件即可接本地 vLLM/Ollama**。实测接 `http://localhost:8000/v1`（vLLM serve Qwen3.8-27B-NVFP4）完全正常，**延迟仅多 1-2ms（本地网络）**。

#### 避坑与总结

| 坑点 | 现象 | 根因 | 规避/修复 |
| --- | --- | --- | --- |
| **`pnpm dsh web` 报错找不到内部包** | `Cannot find module '@deepseek-ai/cordis'` | 未执行 `pnpm run build`，内部包未链接、前端未构建 | **必须先 `pnpm run build`** ，或用 `npx @deepseek-ai/dsh web` 走预构建分发 |
| **Web UI 无法保存 API Key** | 点保存无反应，刷新后 Key 丢失 | 浏览器拦截 `localStorage`（隐私模式/跨域 iframe） | 用正常标签页、非隐私模式；或改用 `~/.config/dsh/cordis.yml` 写死配置 |
| **Headless 模式无输出/卡住** | 命令执行后无任何日志返回 | 默认日志级别 `warn`，Minimal profile 无控制台日志插件 | 加环境变量 `DEBUG=dsh:*` 或在 `cordis.yml` 加 `plugin-console-logger` |
| **Code 模式生成的代码跑不通** | 沙箱报错 `ReferenceError: xxx is not defined` | 模型生成代码引用未导入的模块、用了沙箱禁用的 API | 仅用 DeepSeek-V3.1/R1；在预设里加 `allowed-imports` 白名单；开启 `creator` 模式调试生成代码 |
| **插件热重载不生效** | 改插件代码后 `pnpm dsh web` 仍跑旧逻辑 | 构建产物缓存、`require` 缓存、Cordis 插件挂载缓存 | 加 `--force-rebuild` 或删 `packages/*/dist` 重建；开发期用 `pnpm dsh --profile creator` 调试 |
| **Windows 下沙箱 shell 执行失败** | `spawn cmd.exe ENOENT` | 沙箱插件默认用 `sh -c`，Windows 无 `sh` | 配置 `plugin-sandbox` 的 `shell: 'cmd.exe'` 和 `shellArgs: ['/c']` |

**性能/资源实测（M3 Max, Node 22.19, Web profile, 空会话）**：

| 指标 | 数值 | 备注 |
| --- | --- | --- |
| 进程启动时间 | ~2.8 秒 | 含插件树构建、前端静态资源服务 |
| 内存占用 (RSS) | ~180 MB | 含 Node 运行时、V8 堆、Cordis 上下文 |
| Web UI 首屏加载 | ~400 ms | Vite 构建产物，gzip 后 ~120 KB JS |
| 单轮对话延迟 (不含模型) | ~15 ms | 插件路由、上下文组装、事件分发 |
| 沙箱 shell 执行开销 | ~5 ms/次 | 进程派生 + stdout/stderr 管道 |

**局限性（必须如实列出）**：

1. 1. **Developer Preview 状态，破坏性变更随时发生**：README 明写「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」，v0.1.0-rc.x 版本间插件 API、配置 schema、事件名可能不兼容，**生产系统锁版本、锁依赖、备回滚方案**。
2. 2. **文档滞后于代码**：官方文档站 (`deepseek-harness.github.io`) 仅覆盖核心概念、快速开始、Web UI 指南，**插件开发指南、Cordis 进阶用法、Patch 语法参考、迁移指南均缺失**，需啃源码（`packages/*/src`、`docs/*.md`、`examples/`）。
3. 3. **生态插件极少**：目前仅官方维护的 12 个核心插件，**无第三方插件市场、无插件注册表、无版本管理机制**——想用「现成插件」基本靠自己写或改官方插件。
4. 4. **多用户/多租户/权限模型全无**：单用户单实例设计，**无鉴权、无 RBAC、无会话隔离、无审计日志**——要进团队环境需前置网关（Auth + 代理）二次开发。
5. 5. **沙箱安全性仅基础隔离**：默认 `plugin-sandbox` 用子进程 + 环境变量清理 + 工作目录限制，**无 gVisor/Kata Containers/Firecracker 硬件级隔离**——跑不可信代码风险自担。
6. 6. **Creator 模式仍是半成品**：运行时检查器只能看插件树、服务依赖图，**无法可视化编辑 Patch、无法一键导出 Preset、无插件模拟器**——定位是「开发者调试工具」而非「低代码配置器」。

**个人判断**：

* • **适合**：想**自研 Agent 运行时**、需要**极致可定制性**（换模型、换沙箱、换审批流、换 Agent Loop 逻辑）、接受**自带维护成本**的技术团队；想研究「插件化 Agent 架构」「可逆副作用」「运行时组合」的工程师/科研人员；**作为 Claude Code/Cursor/Cline 的开源替代品二次开发基座**（MIT 协议允许商用闭源）。
* • **不适合**：要开箱即用、要现成插件生态、要多用户协作、要企业级安全合规、无前端/Node.js/TypeScript 栈能力的团队。
* • **我的决策**：团队内部把 **Harness 作为「Agent 运行时实验场」**（Creator 模式 + 自定义 Patch），生产环境代码助手仍用 **自建扩展版**（基于 vLLM + 自研 Orchestrator）。Harness 的 **Profile/Bundle/Patch 配置树设计** 值得借鉴——我们正在把自研系统的「功能开关」迁移到类似的 **声明式配置层**，目标是「换一个组件只改配置、不改代码」。**下一步关注**：v0.2 计划引入「插件沙箱权限模型」（Issue #312）与「分布式追踪集成」（Issue #289），若落地可解决生产化最大的两个拦路虎。
