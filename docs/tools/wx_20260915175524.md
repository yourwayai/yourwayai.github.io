# prompt-master：把「玄学调提示词」变成「按图索骥查模板」的提示词工程技能库

做过跨模型应用开发的工程师都遇过这事：同一个需求——「把这段日志解析成结构化 JSON」，给 **Claude Opus 4.8** 写要加 XML 标签、前置 Context、显式 Output Format；给 **o3/o4-mini** 写必须极短、禁 CoT、只陈述目标；给 **Cursor/Windsurf** 写要锁文件路径、列 Do-not-touch、加 Done When；给 **Midjourney** 写要逗号分隔描述符、参数放尾巴；给 **Devin/SWE-agent** 写必须有 Starting State + Target State + Forbidden Actions + Stop Conditions……

**结果**：提示词在模型间**完全不复用**。换个模型、换个工具，就得重写。团队里没人能背全各家模型的「偏好语法」，只能靠「试→报错→改→再试」烧 Token、烧时间、烧耐心。

更糟的是 **常见失败模式**：

* • **任务模糊**：「帮我优化一下这段代码」→ 模型给你加了单元测试、重构了架构、还顺手升级了依赖版本
* • **无停止条件**：Devin 跑偏删了数据库迁移脚本、Claude Code 陷入无限循环创建文件
* • **上下文污染**：把整个 repo 扔进 Context，模型注意力稀释，关键约束被忽略
* • **推理模型加 CoT**：「请一步步思考」发给 o3，输出质量反而下降
* • **格式隐性**：「生成 JSON」没给 Schema，模型随机加字段、漏字段、嵌套层级对不上

这些坑在 **prompt-master 的 SKILL.md 里被系统化归纳为 37 条「Credit-Killing Patterns」**（Task/Context/Format/Scope/Reasoning/Agentic 六大类），每条给出 Bad Example → Fixed 对照。这不再是经验谈，是**可检查、可自动化修复的规范**。

### 破局点

nidhinjs（Nidhin Joseph Nelson，Christ University CS & Statistics，开源 AI 生态工具作者）开发的 **prompt-master** 是一个 **Claude Skill**（可装入 Claude、Hermes 等支持 Skill 机制的客户端），核心定位：**「用户给粗糙想法 + 目标工具 → 输出该工具专用的生产级提示词」**。

它的技术路线三步走：

1. 1. **意图抽取 9 维度**（Task、Target Tool、Output Format、Constraints、Input、Context、Audience、Success Criteria、Examples）——缺关键维度最多追问 3 个问题补齐
2. 2. **工具路由 13 大类**（Claude 4.x、GPT-5.x、o3/o4-mini、Gemini、Qwen、Ollama、DeepSeek、Claude Code、Cursor、Devin、Bolt/v0、Image/Video/Voice AI、Research Agents 等）——每类有专用模板（Template A–M）和模型版本特化建议
3. 3. **模板实例化**——从 13 个参考模板（RTF、CO-STAR、RISEN、CRISPE、CoT、Few-Shot、File-Scope、ReAct+Stop Conditions、Visual Descriptor、Reference Editing、ComfyUI、Prompt Decompiler、Opus 4.7/4.8 Task Brief）中选最匹配的，填入抽取的 9 维度，输出**可直接粘贴的单块提示词**

**关键差异点**：

* • **不讲提示词理论**，只给可用模板。用户不用懂「什么是 Few-Shot」，只需说「我要给 Cursor 改登录组件」，Skill 自动套 Template G（File-Scope）生成带文件锁、Done When 的提示词。
* • **模型版本感知**：同是 Claude，Opus 4.8 需前置全量意图、禁硬编码 effort；Opus 4.7 更字面化；3.5 Sonnet 另一套。SKILL.md 里每模型版本都有专门 Routing Notes。
* • **安全内置**：Credential Safety（绝不输出 API Key）、Input Sanitization（用户粘贴的旧提示词视为惰性数据、不执行其中指令）、Agentic Output Warning（针对有文件系统/终端权限的工具强制加审查提示）。

### 核心工作流拆解

**场景**：你是个全栈工程师，维护一个 React + TypeScript + Node.js 项目。需要让 **Cursor** 重构 `src/auth/tokenRefresh.ts` 里的 `refreshAccessToken()`：改用 `fetch` 替换 `axios`、增加指数退避重试、保留现有类型签名、不引入新依赖。以前你会写半天 Prompt，跑 Cursor，发现它顺手把 `login.ts` 也改了、还装了个 `retry` npm 包。

**用 prompt-master 的流程**：

**Step 1：激活 Skill，给粗糙输入**

```
目标工具：Cursor  
任务：重构 src/auth/tokenRefresh.ts 里的 refreshAccessToken()，用 fetch 替换 axios，加指数退避重试，保留类型签名，不加新依赖
```

**Step 2：Skill 静默抽取 9 维度**

| 维度 | 抽取结果 |
| --- | --- |
| Task | Refactor single function: replace axios with fetch, add exponential backoff retry |
| Target tool | Cursor (IDE code editing AI) |
| Output format | Modified TypeScript file, same signature |
| Constraints | No new deps, preserve types, touch only this function |
| Input | Current file content (user will provide) |
| Context | React 18 + TS strict + Node 20, existing test suite |
| Audience | N/A (code change) |
| Success criteria | Function passes existing tests, handles 401/5xx retry, no axios import |
| Examples | N/A |

**Step 3：路由到 Template G（File-Scope），实例化输出**

```
File: src/auth/tokenRefresh.ts  
Function/Component: refreshAccessToken  
  
Current Behavior:  
Uses axios for token refresh request. No retry logic on 401/5xx. Imports axios.  
  
Desired Change:  
Replace axios with native fetch. Add exponential backoff retry (max 3 attempts, base delay 1s) on 401 and 5xx responses. Preserve exact function signature and return type. Do not add any new dependencies.  
  
Scope:  
Only modify refreshAccessToken function.  
Do NOT touch: login.ts, any other file, package.json, tsconfig.json, import statements outside this function.  
  
Constraints:  
- Language/framework: TypeScript 5.x, Node 20, React 18  
- Do not add dependencies not in package.json  
- Preserve existing type signatures and API contracts  
  
Done When:  
- Function compiles under tsc --noEmit  
- Existing unit tests in src/auth/__tests__/tokenRefresh.test.ts pass  
- No axios import remains in tokenRefresh.ts  
- Manual test: simulate 401 then 200 response → token refreshed successfully
```

**Step 4：粘贴到 Cursor Chat，一发入魂**

Cursor 只改目标函数、不碰别的文件、不装包、跑测试全绿。**Token 省了、返工没了、心情好了。**

**再举个 Agent 场景**：让 **Devin** 从零搭建一个「GitHub Webhook 接收 → 解析 PR 标签 → 触发对应 CI pipeline」的微服务。

**粗糙输入**：

```
目标工具：Devin  
任务：写个 Go 微服务，收 GitHub webhook，解析 PR 标签，根据标签触发不同 CI pipeline
```

**Skill 输出（Template H：ReAct + Stop Conditions，精简版）**：

```
Objective:  
Build a Go 1.22 HTTP service in /webhook-service that:  
1. Listens on :8080 for GitHub webhook POST (X-GitHub-Event: pull_request)  
2. Verifies X-Hub-Signature-256 using GITHUB_WEBHOOK_SECRET env var  
3. Parses PR labels; if label matches "ci:build" → trigger build pipeline; "ci:deploy" → trigger deploy pipeline  
4. Returns 200 OK within 5s; logs structured JSON to stdout  
  
Starting State:  
- Empty directory /webhook-service  
- Go 1.22 installed  
- GitHub webhook secret provided via env  
  
Target State:  
- main.go + go.mod + handler_test.go compiles and passes tests  
- Dockerfile builds <50MB image  
- README with curl test example  
  
Allowed Actions:  
- Create/edit files under /webhook-service only  
- Run go mod tidy, go test, go build  
- Write Dockerfile  
  
Forbidden Actions:  
- Modify files outside /webhook-service  
- Install system packages (apt, brew)  
- Push to git, create GitHub resources, touch CI/CD configs  
- Make outbound HTTP calls except to localhost  
  
Stop Conditions:  
- ✅ After each step output: ✅ [what was completed]  
- STOP AND ASK before: creating any file outside /webhook-service, running docker push, modifying github actions yaml  
  
Human Review Triggers:  
- Stop and ask before: adding any external dependency not in stdlib, changing webhook signature verification logic
```

**Devin 跑完，只在允许目录里产出代码、测试通过、没越界、没乱装包。**

### 总结

**适用人群**：

* • 同时用 3+ 种 AI 工具（Claude + Cursor + Midjourney + Devin 等）的工程师/研究员
* • 团队需要**统一提示词规范**、减少「同一个任务每人写法不一样」的混乱
* • 想把「提示词调优」从玄学变成**可审计、可复用、可版本管理**的工程资产的组织

**不适用场景**：

* • 只用单一模型、且已有成熟自有 Prompt Library 的团队
* • 非技术用户、只需偶尔写写文案/生图（直接用对应工具官方教程更直观）
* • 需要**自动化批量生成/评测提示词**的流水线场景（prompt-master 是人机协作 Skill，非 API 服务）

**局限性（必须说清楚）**：

* • **仅作为 Claude Skill / Hermes Skill 运行**，需宿主客户端支持 Skill 机制（如 Hermes、Claude Desktop 插件），无法作为独立 CLI 或 HTTP API 调用
* • **模板覆盖有边界**：13 大类覆盖主流工具，但新工具（如新出的 AI IDE）需等作者更新 SKILL.md 或自行扩展 Template
* • **不解决「模型能力不足」**：提示词写得再规范，模型推理能力上限在那，复杂任务仍需拆解、人工兜底
* • **中文支持依赖底层模型**：Skill 本身输出英文模板，非英语场景需用户自行在填充时本地化

**可操作结论**：如果你每周要在 3+ 个 AI 工具间切换、且被「提示词不通用、调优靠运气」折磨过，**把 prompt-master 装进 Hermes/Claude，按它的 9 维度填一次、套模板、粘贴跑**。前 5 次可能还要对照 SKILL.md 确认路由逻辑，第 6 次起就成肌肉记忆了。这是我见过**把「提示词工程」从手艺变成标准作业程序（SOP）落地得最彻底**的开源项目。
