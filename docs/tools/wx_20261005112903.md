# PDF 转 Markdown 还在用规则解析？MarkPDFDown 直接扔给视觉大模型，效果如何？

* **原文链接**: [https://mp.weixin.qq.com/s/-RTkKIYeHGUthgP16W4rkg](https://mp.weixin.qq.com/s/-RTkKIYeHGUthgP16W4rkg)

周末把 **MarkPDFDown v1.2.0**（`4b38fd8`，2025-08 发布）拉到本地跑了一遍。关注它的原因很直接：手头有几十份**扫描版论文、带复杂表格的财报、手写批注的合同**，传统工具（`pdfplumber`、`marker-pdf`、`nougat`、`pymupdf`）要么表格错位、要么公式乱码、要么手写体完全不识。MarkPDFDown 走的路子完全不同：**把每页 PDF 渲染成图片 → 扔给多模态视觉大模型（GPT-4o / Claude-3.5-Sonnet / Gemini-Pro-Vision / Llama-3.2-90B-Vision） → 让模型直接“读图写 Markdown”**。这套“视觉理解替代规则解析”的思路，正好卡在“非结构化、版面复杂、规则难覆盖”的痛点上。

### 部署实录

**环境与依赖清单**

| 项 | 要求 | 实测版本 |
| --- | --- | --- |
| Python | ≥3.9 | 3.11.9 (conda) |
| 包管理器 | uv（推荐）/ conda / pip | uv 0.4.30 |
| LLM 访问 | OpenAI API Key 或 OpenRouter API Key | 两者均测试 |
| 系统库 | 无强依赖（PDF 渲染用 `pdf2image` → 需 `poppler-utils`） | Ubuntu 22.04 `apt install -y poppler-utils` |

**三种安装方式实测**

**方式 1：uv（推荐，最快、隔离最干净）**

```
# 1. 装 uv（若无）  
curl -LsSf https://astral.sh/uv/install.sh | sh  
  
# 2. 克隆、同步依赖、装包  
git clone https://github.com/MarkPDFdown/markpdfdown.git  
cd markpdfdown  
uv sync                    # 创建 .venv、锁依赖  
uv pip install -e .        # 可编辑安装 markpdfdown 命令  
  
# 3. 配置环境变量  
cp .env.sample .env  
# 编辑 .env 填入 OPENAI_API_KEY 或 OPENROUTER_API_KEY
```

**方式 2：conda（习惯 conda 的用户）**

```
conda create -n markpdfdown python=3.9  
conda activate markpdfdown  
git clone https://github.com/MarkPDFdown/markpdfdown.git  
cd markpdfdown  
pip install -e .  
cp .env.sample .env  # 填 Key
```

**方式 3：Docker（无环境污染、CI/CD 友好）**

```
# 构建镜像（约 2 分钟，含 poppler、python、依赖）  
docker build -t markpdfdown .  
  
# 运行：管道模式（stdin/stdout），无需挂载卷  
docker run -i \  
  -e MODEL_NAME=gpt-4o-mini \  
  -e OPENAI_API_KEY=sk-xxx \  
  markpdfdown < input.pdf > output.md  
  
# 或挂载文件模式  
docker run --rm \  
  -v $(pwd):/data \  
  -e MODEL_NAME=openrouter/anthropic/claude-3.5-sonnet \  
  -e OPENROUTER_API_KEY=sk-or-xxx \  
  markpdfdown --input /data/doc.pdf --output /data/doc.md
```

**实测踩坑点**

1. 1. **`pdf2image` 依赖 `poppler-utils`** —— Dockerfile 已装，本地跑必须 `apt install poppler-utils` / `brew install poppler` / `conda install -c conda-forge poppler`，否则 `pdf2image.exceptions.PDFInfoNotInstalledError`。
2. 2. **模型名必须按 LiteLLM 规范写** —— `gpt-4o`、`gpt-4o-mini`、`openrouter/anthropic/claude-3.5-sonnet`、`openrouter/google/gemini-pro-vision`、`openrouter/meta-llama/llama-3.2-90b-vision`。写错报 `litellm.exceptions.BadRequestError: Model not found`。
3. 3. **大文件分页必加 `--start --end`** —— 单次请求受模型上下文窗口限制（GPT-4o 128k tokens ≈ 30-40 页），超范围直接报错。实测 100 页论文分 3 批跑，再 `cat *.md > all.md` 合并。
4. 4. **温度建议 0.1-0.3** —— 默认 0.3 还行，调 0.1 表格结构更稳，调 0.5 容易幻觉出不存在的列标题。
5. 5. **重试机制仅在 `RETRY_TIMES` 生效** —— 网络抖动、限流会自动重试，但模型返回格式错误（如未按 Markdown 输出）不会重试，需人工兜底。

**最小可行验证流**

```
# 单文件转换  
markpdfdown --input scan_contract.pdf --output contract.md  
  
# 指定页码范围  
markpdfdown --input large_report.pdf --output ch3.md --start 15 --end 28  
  
# 管道模式（Docker/CI 友好）  
cat paper.pdf | markpdfdown > paper.md  
  
# 批量转换  
for f in *.pdf; do markpdfdown --input "$f" --output "${f%.pdf}.md"; done
```

### 核心亮点

**1. 视觉大模型“所见即所得”：表格、公式、图表、手写批注一次性搞定**  
测了 5 类难点文档，对比基线（`marker-pdf` v0.1.7 / `nougat` 0.1.0 / `pdfplumber` 0.11 / `pymupdf` 1.24）：

| 文档类型 | 页数 | MarkPDFDown (GPT-4o-mini) | marker-pdf | nougat | 备注 |
| --- | --- | --- | --- | --- | --- |
| **扫描版中文论文** （双栏、脚注、跨页表格） | 12 | **表格对齐完美、脚注保留、公式 LaTeX 渲染正确** | 表格拆行、脚注丢失、公式乱码 | 双栏阅读序列错乱、表格识别率 < 30% | 视觉模型天然处理版面布局 |
| **财报 PDF** （合并单元格、斜线表头、小计行、跨页表格） | 8 | **CSV 可直接 `pd.read_csv` 入库、合并单元格用空单元格占位** | 合并单元格拆行、斜线表头丢 | 仅识别出纯文本、表格结构全丢 | 这是最大惊喜：GPT-4o-mini 对表格结构理解极强 |
| **手写批注合同** （红笔圈划、手写签名、盖章遮挡） | 5 | **手写文字识别准确、圈划区域用 `[手写批注: ...]` 标记、盖章处标注 `[盖章遮挡]`** | 完全识别不出手写 | 识别出部分手写但位置错位 | 视觉模型对手写体鲁棒性远超传统 OCR |
| **纯数字版技术文档** （代码块、Mermaid 图、数学公式） | 20 | **代码块保留缩进、Mermaid 源码原样输出、公式 `$...$`/`$$...$$` 完美** | 代码块缩进丢失、Mermaid 变乱码 | 公式识别较好但代码块全挂 | 视觉模型对代码/图表结构理解好 |
| **低分辨率手机拍照** （倾斜、阴影、畸变、模糊） | 6 | **自动纠偏、去阴影、文字识别率 ~85%** （模糊处标注 `[模糊不可辨]`） | 需预处理（透视变换、二值化）才能跑 | 需同等预处理 | 视觉模型自带鲁棒性，省去预处理管线 |

**成本核算（OpenAI 官方定价，2025-09）**

| 模型 | 单页成本（估） | 100 页成本 | 适用场景 |
| --- | --- | --- | --- |
| `gpt-4o-mini` | **$0.0018/页** | **$0.18** | 日常文档、表格、公式、手写——**性价比之王** |
| `gpt-4o` | $0.015/页 | $1.50 | 极复杂版面、关键合同、需最高准确率 |
| `claude-3.5-sonnet` (OpenRouter) | $0.003/页 | $0.30 | 长上下文、中文理解略优、备用链路 |
| `gemini-pro-vision` (OpenRouter) | $0.0005/页 | $0.05 | **最便宜** ，但表格/手写准确率略低 |
| `llama-3.2-90b-vision` (OpenRouter) | $0.0008/页 | $0.08 | **全本地/私有化部署** 可选，准确率次于闭源模型 |

**结论**：日常批量跑 **`gpt-4o-mini` 足够**，关键文档上 `gpt-4o` 或 `claude-3.5-sonnet`，成本在可接受范围内。

**2. LiteLLM 统一网关：换模型只改环境变量，代码零动**

```
# core/llm_client.py 核心逻辑极简  
from litellm import completion  
  
def vision_completion(model: str, messages: list, **kwargs):  
    return completion(model=model, messages=messages, **kwargs)
```

所有模型差异（鉴权、端点、参数、流式/非流式）全由 LiteLLM 吸收。**想加新模型（如 Azure OpenAI、本地 vLLM、Ollama 视觉模型）只需在 `.env` 按 LiteLLM 格式写对 `MODEL_NAME` 和对应 `*_API_KEY`/`*_BASE_URL`**。实测从 `gpt-4o-mini` 切到 `openrouter/anthropic/claude-3.5-sonnet` 仅改 2 行环境变量，重跑同一份 PDF，输出 Markdown 结构一致、仅措辞微调。

**3. 页面范围切片 + 管道模式：大文件、流式处理、CI/CD 集成全覆盖**

```
# 1. 只转第 5-15 页  
markpdfdown --input huge.pdf --output part.md --start 5 --end 15  
  
# 2. 管道模式：stdin 进、stdout 出，无临时文件  
cat huge.pdf | markpdfdown > huge.md  
  
# 3. Docker 管道：CI 流水线里直接跑  
docker run -i -e MODEL_NAME=gpt-4o-mini -e OPENAI_API_KEY=$KEY markpdfdown < in.pdf > out.md
```

**工程化细节**：

* • `--start/--end` 是**1-based 页码**，内部 `pdf2image.convert_from_path(pdf_path, first_page=start, last_page=end)` 直接切片，不渲染全文档，**大文件启动快、内存低**。
* • 管道模式读 `sys.stdin.buffer.read()` → 写临时文件 → 处理 → 删临时文件 → 吐 `sys.stdout.write()`，**无状态、可并行、可 Kubernetes Job 化**。

**4. 模块化架构：核心逻辑 < 500 行，极易二次开发/嵌入**

```
src/markpdfdown/  
├── cli.py          # argparse、参数校验、入口分发  
├── main.py         # 转换编排：PDF→图片→分批→LLM→拼接→写出  
├── config.py       # pydantic-settings 读 .env、环境变量、默认值  
└── core/  
    ├── llm_client.py      # LiteLLM 封装、重试、错误映射  
    ├── file_worker.py     # PDF/图片读取、渲染、分页、临时文件管理  
    └── utils.py           # 日志、进度条、Markdown 后处理（清理多余空行等）
```

**嵌入示例**：

```
from markpdfdown.main import convert_pdf_to_markdown  
  
md = convert_pdf_to_markdown(  
    pdf_path="doc.pdf",  
    model="gpt-4o-mini",  
    start_page=1,  
    end_page=10,  
    temperature=0.1  
)  
# 直接得到字符串，进 RAG 管线、存数据库、喂 LLM
```

无全局状态、无单例、无副作用，**作为库调用零负担**。

### 避坑与总结

| 优点 | 缺点/局限 |
| --- | --- |
| 视觉大模型对复杂版面（表格/公式/手写/图表）理解力碾压规则解析 | **强依赖外部 LLM API** ：断网/限流/额度用尽即不可用；本地模型（Llama-3.2-90B-Vision）需 48 GB+ 显存、推理慢 |
| 换模型只改环境变量，LiteLLM 吸收所有厂商差异 | **单页成本虽低但累积可观** ：1 万页/月 × GPT-4o-mini ≈ ，年216；企业级批量需评估 ROI |
| 页面切片、管道模式、Docker 支持，工程化完备 | **无增量/缓存机制** ：同一文档二次转换全量重跑，无“仅转修改页”能力 |
| 代码简洁（核心 < 500 行）、易审计、易二开 | **输出非确定性** ：同一 PDF、同一模型、同一参数跑两次，Markdown 措辞、换行、表格对齐可能微差（LLM 采样随机性） |
| Apache-2.0 许可、商业友好 | **无内置去重/去水印/去页眉页脚** ：扫描件页眉页脚会被模型当成正文转进 Markdown，需后处理清洗 |
| 支持图片直接转 Markdown（`--input img.png`） | **不支持加密 PDF** ：`pdf2image` 无法渲染加密文档，需先 `qpdf --decrypt` 或 `pikepdf` 解密 |

**个人判断**：

* • 如果你是**构建 RAG/知识库的工程师**，需要把**扫描件、手写件、复杂表格、公式密集型 PDF**批量转成**高质量 Markdown**，且接受“**按页付费、依赖外部 API**”——**MarkPDFDown 是当前开源界工程化最完善、效果最稳的选择**，uv/Docker/管道模式三管齐下，直接进生产管线。
* • 如果你是**个人用户、偶尔转几份 PDF**——**直接用网页版 ChatGPT/Claude 上传 PDF 让它输出 Markdown**，别自建 CLI，省钱省力。
* • 如果你是**数据不出境、必须全本地跑**的场景——**只能上 `llama-3.2-90b-vision`（需 2×A100/H100）或自建 vLLM 部署视觉模型**，成本门槛极高；此场景下传统 `marker-pdf`/`nougat`/`paddleocr` 组合仍是主流务实解。
* • **最大局限**：**非确定性输出**。同一输入跑两次得到的 Markdown 在字节级不完全相同（LLM 采样随机性），这对“需要可复现构建、Git diff 追踪文档变更”的场景是硬伤。缓解方案：`temperature=0.1` + `seed=42`（OpenAI 支持）+ 固定 `MAX_TOKENS`，但仍无法保证 100% 字节一致。建议：**把 MarkPDFDown 视为“一次性 ETL 任务”，输出结果落盘入版本库，后续不再重跑**。
