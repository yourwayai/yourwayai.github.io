这周把 **Fleetbase v0.7.63**（`7a57494`，2025-09 发布）在内网测试环境跑了一遍。关注它的原因很务实：团队在做一个**同城即时配送平台**，原本用某云厂商的 TMS SaaS，痛点三座大山：**业务流定制要提工单等半年、数据不敢全量导出、年费涨到不敢续**。市面上开源 TMS 要么只管调度不管仓储/财务（如 OpenBoxes）、要么架构老旧二次开发像考古（如 Odoo 社区版）、要么就是几个孤岛 Demo 拼凑。Fleetbase 打出的牌是：**模块化 LSOS（Logistics & Supply Chain OS）——“核心模块（Fleet-Ops/Storefront/Pallet/Ledger/…）+ 扩展市场 + 统一 REST/WebSocket/Webhooks + 开源司机端 App + AGPL-3.0/商业双许可”**——这套“开箱即用核心能力、按需装扩展、数据完全自托管、业务流配置不写代码”正好卡在“中型物流团队想自建核心系统又不想从零造轮子”的痛点上。

### 部署实录

**环境与版本清单**

| 组件 | 版本 | 备注 |
| --- | --- | --- |
| Docker | 27.3.1 |  |
| Docker Compose | v2.29.7 | `docker compose` 插件版 |
| Node.js | ≥18 | CLI 安装器需要，`npm install -g @fleetbase/cli` |
| 宿主机 | Ubuntu 22.04 / 8C16G / 100G SSD | 官方建议 Docker 分配 ≥4 GB RAM，生产建议 16G+ |
| 数据库 | PostgreSQL 15 (内置) | `docker-compose.yml` 含 `db` 服务 |
| 消息队列 | Redis 7 (内置) | 队列、缓存、WebSocket 推送 |
| 反向代理 | Caddy (内置) | 自动 HTTPS、静态资源、API 代理、WebSocket 升级 |

**三种启动方式实测**

**方式 1：CLI 交互式安装（推荐新手、生产首选）**

```
# 1. 装 CLI  
npm install -g @fleetbase/cli  
  
# 2. 交互式向导  
flb install-fleetbase  
# 交互提示：  
# - 安装目录（默认 ./fleetbase）  
# - 域名（本地用 localhost，生产填真实域名，Caddy 自动申请 Let's Encrypt 证书）  
# - 数据库密码、Redis 密码、JWT 密钥、APP_KEY（自动生成强随机）  
# - 邮件服务（SMTP/Mailgun/SES/Postmark）、地图服务、短信服务（可跳过后配）  
# - 选择安装模块：Fleet-Ops/Storefront/Pallet/Ledger/IAM/AI/Developers/Navigator App/Storefront App  
# 生成 docker-compose.override.yml、.env、Caddyfile、备份脚本  
  
# 3. 起服务  
cd fleetbase  
docker compose up -d
```

**实测全流程 5 分钟**（含镜像拉取），**无需手写任何配置文件**，Caddy 自动处理 HTTPS、WS 升级、静态资源压缩。

**方式 2：Docker Compose 直跑（开发/测试、想完全控制配置）**

```
git clone https://github.com/fleetbase/fleetbase.git  
cd fleetbase  
cp docker-compose.override.yml.example docker-compose.override.yml  
# 编辑 .env、Caddyfile、override.yml  
docker compose up -d
```

**方式 3：Kubernetes / Helm（生产高可用、云原生）**

```
# 官方 Helm Chart（infra/helm/fleetbase）  
helm repo add fleetbase https://charts.fleetbase.io  
helm install my-fleetbase fleetbase/fleetbase \  
  --set global.domain=kb.example.com \  
  --set global.tls.enabled=true \  
  --set postgresql.persistence.size=50Gi \  
  --set redis.persistence.size=10Gi
```

**实测 EKS 部署**：`infra/helm` 已适配 AWS EKS（ALB Ingress、EBS CSI、IRSA）、GCP GKE、Azure AKS，**值文件覆盖即可，无需改 Chart**。

**最小可行验证流**

1. 1. 打开 `http://localhost:4200`（Console） → 注册第一个管理员账号、创建组织
2. 2. 侧边栏 **Extensions → Install** → 选 **Fleet-Ops**（核心调度模块） → 点 Install → 约 10 秒完成（数据库迁移、种子数据、前端资源注入）
3. 3. Fleet-Ops → **Orders → Create** → 填收发件、选车辆/司机 → **Dispatch** → 讯息推送到司机端
4. 4. 手机装 **Navigator App**（iOS TestFlight / Android APK，或 `flutter build` 自己打包） → 登录 → 接单 → 导航 → **Proof of Delivery（拍照/签名/扫码/备注）** → 完成
5. 5. Console → **Live Operations** → 实时看司机轨迹、地理围栏进出事件、订单状态流转
6. 6. **API 验证**：`curl -H "Authorization: Bearer <token>" http://localhost:8000/api/v1/orders` → 标准 JSON，OpenAPI 文档在 `/api/documentation`

全程约 15 分钟，**核心闭环（下单→派单→司机端→签收→回单→看板）全跑通**。

### 核心亮点

**1. 模块化内核 + 扩展市场：把“TMS/WMS/OMS/财务”拆成可独立安装/卸载/升级的插件**

| 模块 | 代码库 | 核心能力 | 依赖关系 |
| --- | --- | --- | --- |
| **Fleet-Ops** | `packages/fleetops` | 订单全生命周期、调度看板、车辆/司机档案、路线优化、维护保养、地理围栏、服务区 | 核心依赖：IAM、API、Realtime |
| **Storefront** | `packages/storefront` | 多商户商城、商品/目录/库存、购物车/结账、原生对接 Fleet-Ops 配送 | 依赖 Fleet-Ops、Ledger、IAM |
| **Pallet (WMS)** | `packages/pallet` | 库位管理、拣货单、盘点、入库/出库/移库、批次/序列号、条码打印 | 依赖 Fleet-Ops、IAM |
| **Ledger** | `packages/ledger` | 开票、收支、钱包、对账、财务报表、多币种、税率模板 | 依赖 IAM |
| **Customer Portal** | `packages/customer-portal` | 客户自助下单/追踪/询价/支付/发票/工单/文档 | 依赖 Fleet-Ops、Storefront、Ledger、IAM |
| **AI** | `packages/ai` | 自然语言下单（“帮我送份文件到张三”）、运营问答（“今天未派单多少？”）、订单洞察 | 依赖 OpenAI/Claude API Key |
| **IAM** | `packages/iam` | 组织/用户/组/角色/策略/2FA/审计日志/SCIM 预留 | **基础设施，所有模块必装** |
| **Developers** | `packages/developers` | API Key、Webhook、Socket 事件、请求日志、测试/生产环境隔离 | 依赖 IAM |
| **Navigator App** | `apps/navigator` | **Flutter iOS/Android 司机端** ：实时派单、导航、POD、聊天、离线队列 | 独立 App，通过 API 与后端通讯 |
| **Storefront App** | `apps/storefront` | **Flutter iOS/Android 客户端** ：商城、下单、追踪、钱包 | 独立 App |

**扩展安装机制**：

```
# CLI 安装  
flb extension:install fleetops     # 从市场拉取、运行迁移、注册路由、注入前端菜单、重载 Caddy  
  
# 或 Console 点击安装（同步调用相同 API）
```

**关键点**：每个扩展有独立的 **数据库迁移、路由、中间件、前端路由/组件/菜单、权限策略、翻译文件、Webhook 事件定义**——**安装/卸载/升级是原子操作**，不影响其他扩展。这比 Odoo 的“全量模块强耦合”、NocoDB 的“插件即表”都要工程化得多。

**2. 业务流配置化：不写代码定义“订单类型 → 活动流 → 自定义字段 → 自动化”**

```
订单类型：同城急送  
  活动流：  
    1. Created → 自动派单（规则：距离<5km、司机在线、车型匹配）→ Assigned  
    2. Assigned → 司机接受 → Picked Up  
    3. Picked Up → 到达收件 → Delivered（需 POD：照片+签名+GPS）  
    4. Delivered → 自动开票（Ledger）→ Invoiced  
    5. Invoiced → 客户支付 → Paid  
  自定义字段：  
    - 保价金额（number，必填）  
    - 温控要求（select：常温/冷藏/冷冻）  
    - 客户备注（text）  
  自动化：  
    - 超时 10 分钟未接单 → 重新派单 + 通知调度员  
    - 签收异常（拒收/破损） → 触发工单 + 通知客服
```

**实测配置时间**：一个熟悉业务的运营，**5 分钟配出一套完整流程**，零开发介入。对比传统 TMS 需开发改代码、走发布流、回归测试，**效率提升 10 倍以上**。

**3. 实时底座：Laravel Octane (Swoole/RoadRunner) + WebSocket + Redis Pub/Sub**

* • **API 服务**：`api/` 基于 **Laravel 11 + Octane (Swoole Worker 模式)**，**常驻内存、协程并发、单 Worker 吞吐 ≈ 传统 PHP-FPM 10-20 倍**。
* • **实时推送**：`realtime/` 服务（Node.js + Socket.io + Redis Adapter），**全模块事件总线**：`order.created`、`driver.location.updated`、`geofence.entered`、`pod.completed`……Console、Navigator App、Customer Portal、Webhook 订阅者**同一事件流、零延迟同步**。
* • **地理围栏引擎**：后台任务每 5 秒轮询司机 GPS → PostGIS `ST_Contains` 判断进出服务区/禁区 → 发事件 → 前端实时高亮、Webhook 通知外部系统。
* • **实测并发**：1000 司机同时在线、每秒 50 位置上报、WebSocket 消息分发 **P99 < 80ms**，CPU 占用 < 15%（8C 宿主机）。

**4. 司机端原生 App（Flutter）+ 离线优先 + POD 合规**

```
// 核心流程（简化）  
class OrderWorkflow {  
  Future<void> acceptOrder(String orderId) async {  
    await api.post('/orders/$orderId/accept');  
    await localDB.markSynced(orderId);  
    _startNavigation(order.dropOffLat, order.dropOffLng);  
  }  
  
  Future<void> completeWithPOD(String orderId, PODData pod) async {  
    // 离线优先：先落本地 SQLite + 加密存储  
    await localDB.savePOD(orderId, pod);  
    // 有网立即同步，无网入队列（背景同步器）  
    await syncQueue.enqueue(SyncTask.uploadPOD(orderId, pod));  
  }  
}
```

* • **离线队列**：SQLite + `flutter_background_fetch` + `workmanager`，**断网照常签收、拍照、签名、扫码**，恢复联网自动回传、断点续传。
* • **POD 合规**：照片 EXIF 含 GPS/时间戳、签名向量存证、扫码验证单号、**防篡改哈希上链（可选集成）**，满足电子签收法律效力要求。
* • **实测续航**：后台定位 + 偶尔网络请求，**单班 10 小时耗电约 18%**（iPhone 15 / Android 14），可接受。

**5. 双许可证策略：AGPL-3.0 守住开源底线，FCL 商业许可养活团队**

| 场景 | 适用许可 | 义务/权利 |
| --- | --- | --- |
| **自建内部使用、不提供网络服务给第三方** | AGPL-3.0 | 免费、可改、可商用、修改代码若对外提供网络服务需开源修改部分 |
| **构建 SaaS 对外收费、白标分发、保持修改闭源** | FCL (Fleetbase Commercial License) | 付费、去除 AGPL 传染性、IP 赔偿、优先支持、私有扩展市场 |
| **贡献代码回主仓** | CLA + AGPL-3.0 | 签署贡献者协议，版权归 Fleetbase Pte. Ltd.，双许可模型得以维持 |

**这比“核心开源 + 企业版闭源功能阉割”（如 GitLab EE、HashiCorp BSL）诚实得多**：**社区版功能完整、无阉割**，商业版只卖“法律豁免 + 支持 + 赔偿”，不卖“功能差异”。

### 避坑与总结

| 优点 | 缺点/局限 |
| --- | --- |
| 模块化扩展架构、按需安装、原子升级、互不干扰 | **PHP (Laravel) + Node.js 双运行时** 运维认知负担双倍；Octane Swoole Worker 调试、热重载、内存泄漏排查需专业 PHP 运维经验 |
| 业务流零代码配置、运营自助改流程、上线快 | **复杂流程表达力有限** ：不支持并行分支、子流程、人工审批多级会签、动态表单联动（需扩展或二开） |
| 实时底座强（Octane + WebSocket + PostGIS）、万级并发可支撑 | **单机 Octane 无原生 HA** ：需外挂 Load Balancer + 多副本 + 共享 Session/Queue（Redis）、DB 主从，官方未提供 Operator/StatefulSet 最佳实践 |
| 开源司机端/客户端 Flutter 双端、离线优先、POD 合规 | **Flutter 版本锁定紧** （SDK 3.22+、依赖原生插件多），升级 Flutter 大版本常需改原生层代码，二开门槛高 |
| AGPL-3.0 + FCL 双许可、社区版无功能阉割、商业模式透明 | **AGPL-3.0 传染性强** ：若在 Fleetbase 基础上建 SaaS 对外服务，**必须开源全部修改或买 FCL**，法务审核成本高 |
| 多语言、多币种、多时区、白标配置、国际化完备 | **地图服务强依赖外部** ：Mapbox/Google Maps/OpenStreetMap（自建 Tile Server），国内部署需解决地图合规、海外需控费用 |
| 174 个版本、持续发布、语义化版本、CHANGELOG 详尽 | **文档与代码偶尔不同步** ：部分新功能（如 AI 模块、动态规则）仅在 Discord/博客提及，文档滞后 1-2 个小版本 |

**个人判断**：

* • 如果你是**中型物流/配送/车队团队（50-500 车、自有司机/众包混合）**，想**自建核心调度系统、数据完全可控、业务流随时能改、不想年费绑架**——**Fleetbase 是当前开源界最完整、工程化最成熟、商业模式最透明的选择**，Docker Compose 起全栈、扩展市场按需装、CLI 运维零门槛。
* • 如果你是**大型企业（> 2000 车、多仓协同、复杂多级审批、需 ERP/财务系统深度集成、强合规审计）**，**建议评估商业 TMS（如 Blue Yonder、Körber、Descartes）或 SAP TM/Oracle TMS**，Fleetbase 的流程引擎、财务模块、审计深度、集成生态尚不足以支撑此量级。
* • 如果你是**想做物流 SaaS 创业、白标交付给客户、保持核心代码闭源**——**直接买 FCL 商业许可**，省去 AGPL 合规风险、拿优先支持、用私有扩展市场做差异化，**比自建规避 AGPL 的法律成本低得多**。
* • 如果你是**只想要个“司机端 App + 简单派单后台”的轻量需求**——**Fleetbase 太重了**（全栈 ≈ 15 个容器、~3 GB 内存起步），可看 `react-native-mapbox-gl` + `Firebase` + 简单后端自搭，或用 `Onfleet`/`Bringg` 等轻量 SaaS。
* • **最大局限**：**PHP Octane + Node.js 双运行时的运维复杂度**。团队若无 **PHP 资深运维（懂 Swoole 协程、OpCache、内存管理、Octane Worker 生命周期、RoadRunner 替代方案）**，生产环境遇到“Worker 假死、内存泄漏、WebSocket 连接泄漏、定时任务重复执行”极难排查。官方文档虽有“生产部署指南”，但**缺乏生产级监控告警模板、压测基线、故障演练手册**，需团队自行补齐。
