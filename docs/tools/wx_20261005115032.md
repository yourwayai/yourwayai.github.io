上周把 **Pluton v0.20.0**（`5c74a48`，2025-09 发布）在内网测试机跑了一遍。关注它的原因很现实：团队现有备份策略是\*\*“手写 Restic 脚本 + Systemd Timer + Rclone sync 到 Wasabi/Backblaze B2 + 手工记恢复步骤在 Notion”\*\*——分散、易错、新人交接靠口传、恢复演练半年没做过。市面上开源备份 UI 要么只管 Restic（如 Restic UI、Restic Browser）、要么只管 Rclone（如 Rclone WebUI）、要么是商业 SaaS 锁数据（如 Veeam、Duplicati 云端版）。Pluton 打出的牌是：**Restic 做增量加密底座 + Rclone 做 70+ 存储后端统一适配 + React/Vue Web UI 做调度/保留/通知/恢复/脚本钩子全流程可视化 + Docker/桌面双分发 + Apache-2.0 许可**——这套“把备份工程化、可视化、标准化”的组合拳，正好卡在“中小团队想自建企业级备份又不想维护脚本集群”的痛点上。

### 部署实录

**环境与版本清单**

| 组件 | 版本 | 备注 |
| --- | --- | --- |
| Docker | 27.3.1 |  |
| Docker Compose | v2.29.7 | `docker compose` 插件版 |
| 宿主机 | Ubuntu 22.04 / 4C8G / 200G SSD | 备份数据建议挂独立盘/NAS |
| 目标存储 | Wasabi (S3 兼容) / Backblaze B2 / 本地挂载盘 | 测试同时对接 3 个后端 |
| 桌面端 | Windows 11 / macOS 15 / Ubuntu 24.04 | 官网下载 `.msi`/`.dmg`/`.AppImage` |

**Docker 部署（生产推荐）**

```
# 1. 拉取 compose 文件  
mkdir -p /opt/pluton && cd /opt/pluton  
curl -O https://raw.githubusercontent.com/plutonhq/pluton/main/docker-compose.yml  
curl -O https://raw.githubusercontent.com/plutonhq/pluton/main/.env.template  
  
# 2. 生成强随机密钥  
ENCRYPTION_KEY=$(openssl rand -base64 32)  
USER_NAME=admin  
USER_PASSWORD=$(openssl rand -base64 24)  
  
# 3. 写 .env  
cat > .env <<EOF  
ENCRYPTION_KEY=$ENCRYPTION_KEY  
USER_NAME=$USER_NAME  
USER_PASSWORD=$USER_PASSWORD  
APP_TITLE=Pluton Backup  
APP_URL=https://backup.internal.corp  
SERVER_PORT=5173  
MAX_CONCURRENT_BACKUPS=2  
SESSION_DURATION=7  
ALLOW_CUSTOM_RESTORE_PATH=true  
ALLOW_FILE_BROWSER=true  
DISABLE_EVENT_SCRIPTS=false  
EOF  
  
# 4. 准备数据卷与挂载源目录  
mkdir -p /mnt/backups /mnt/source-data  
  
# 5. 起服务  
docker compose up -d  
# 访问 https://backup.internal.corp（Caddy 自动 HTTPS，或自行配反代）
```

**关键坑点与解法**

1. 1. **`ENCRYPTION_KEY` 一旦生成、备份创建后绝不能换** —— 它是 Restic 仓库加密的主密钥，**换了等于全量备份数据永久不可解密**。生产环境必须备份到密码管理器/离线纸质/硬件密钥，**多地异地存储**。
2. 2. **挂载源目录只读（`:ro`）、备份目标可读写** —— `docker-compose.yml` 示例里注释掉的挂载行全是只读源目录，**别把生产数据目录挂成可写**，防止容器内误删。
3. 3. **`MAX_CONCURRENT_BACKUPS` 别贪大** —— 默认 2，每个并发备份约占 1-2 GB 内存（Restic 缓存）+ CPU，4C8G 机器跑 4 并发会 OOM。建议：`总内存(GB) / 3` 向下取整。
4. 4. **首次登录后立刻改密、配 2FA（规划中）、配通知渠道** —— 默认无 2FA，登录页暴露在公网极危险，**务必加反向代理 Basic Auth / IP 白名单 / VPN**。
5. 5. **桌面版安装包签名问题** —— Windows `.msi` 无代码签名，SmartScreen 拦截需“更多信息 → 仍要运行”；macOS `.dmg` 未公证，需 `xattr -d com.apple.quarantine` 或右键“打开”。

**桌面版最小验证流（无 Docker 环境）**

```
# Windows: 双击 Pluton-Setup-0.20.0.msi → 安装 → 开始菜单 Pluton → 自动起后台服务、托盘图标  
# macOS: 打开 Pluton-0.20.0.dmg → 拖入 Applications → 右键“打开”绕过 Gatekeeper  
# Linux: chmod +x Pluton-0.20.0.AppImage → 双击或 ./Pluton-0.20.0.AppImage  
# 统一：浏览器自动打开 http://localhost:5173 → 设置用户名/密码/加密密钥 → 即用
```

桌面版**内置 SQLite + Restic + Rclone 二进制**，无需额外依赖，**完全离线可用**（不联网不上报），适合个人/笔记本/离线服务器场景。

### 核心亮点

**1. Restic + Rclone 双引擎：把“加密增量备份”+“万物皆可存”封装成统一 API**

| 引擎 | 角色 | Pluton 封装点 |
| --- | --- | --- |
| **Restic** | 核心备份引擎 | - 仓库初始化、密钥派生（`ENCRYPTION_KEY` → `restic init --repo`） - 快照创建（`restic backup --tag pluton --host <job>`） - 保留策略执行（`restic forget --keep-last N --keep-daily M --keep-weekly W --keep-monthly Y --keep-yearly Z --prune`） - 校验（`restic check --read-data-subset=10%`） - 恢复（`restic restore <snapshot> --target /restore --include <path>`） - 挂载（`restic mount /mnt/restic`） |
| **Rclone** | 存储传输层 | - 70+ 后端统一配置（S3/B2/GCS/Azure/OneDrive/Google Drive/Dropbox/SFTP/WebDAV/…） - `rclone copy/sync/move` 在**备份后复制**（Replication）阶段执行 - 带宽限制（`--bwlimit`）、重试（`--retries`）、校验（`--checksum`） - 远程挂载（`rclone mount`）供 FUSE 浏览/恢复 |

**关键架构**：Pluton **不直接操作云存储**，而是：

```
本地源目录 → Restic 备份到本地仓库（/data/repositories/<job>） → Rclone 复制仓库到远端（Replication）
```

**优势**：

* • **本地仓库是“热数据”**：增量备份、校验、恢复、挂载全在本地 NVMe/SSD 上跑，**极快、不受网络抖动影响**
* • **远端是“冷归档”**：Rclone 只管把本地仓库文件**按块同步**，断点续传、校验和、带宽控制全靠 Rclone 成熟代码
* • **3-2-1 天然满足**：本地 1 份 + 远端 N 份（可配多个 Replication 目标），**本地挂了拉远端、远端挂了本地兜底**

**2. 调度与保留：可视化 Cron + 多层级保留策略，比手写 crontab 安全得多**

```
// 备份作业配置示例（UI 生成，后端存 PostgreSQL）  
{  
  "name": "prod-db-daily",  
  "sourcePaths": ["/mnt/data/postgresql"],  
  "schedule": "0 2 * * *",           // 每天 02:00  
  "timezone": "Asia/Shanghai",  
  "retention": {  
    "keepLast": 7,       // 最近 7 个快照  
    "keepDaily": 14,     // 过去 14 天每天 1 个  
    "keepWeekly": 8,     // 过去 8 周每周 1 个  
    "keepMonthly": 6,    // 过去 6 月每月 1 个  
    "keepYearly": 3      // 过去 3 年每年 1 个  
  },  
  "replication": [  
    { "remote": "wasabi-prod", "path": "pluton/prod-db" },  
    { "remote": "b2-prod", "path": "pluton/prod-db" }  
  ],  
  "preScript": "docker exec pg-primary pg_dumpall -U postgres | gzip > /mnt/data/postgresql/dump.sql.gz",  
  "postScript": "curl -X POST https://hooks.slack.com/... -d '{\"text\":\"Backup done\"}'",  
  "notification": {  
    "onSuccess": ["slack", "email"],  
    "onFailure": ["slack", "email", "ntfy"],  
    "onWarning": ["email"]  
  }  
}
```

**实测保留执行**：`restic forget --prune` 会**真正删除无用数据块、释放仓库空间**，不是只改元数据。UI 显示“预计释放 X GB”，执行后仓库体积实时回缩。

**3. 恢复体验：从“背命令”到“浏览器点点鼠标”**

| 恢复模式 | UI 操作 | 底层命令 | 适用场景 |
| --- | --- | --- | --- |
| **整盘恢复** | 选快照 → 点“Restore” → 选目标路径 → 确认 | `restic restore <snap> --target /restore` | 灾难恢复、迁移服务器 |
| **单文件/目录恢复** | 文件浏览器浏览快照树 → 勾选文件/文件夹 → 点“Download ZIP” | `restic restore <snap> --target /tmp --include 'path/to/file' --zip` | 误删配置、代码回滚 |
| **FUSE 挂载浏览** | 点“Mount” → 系统出现虚拟盘符 → 资源管理器/Finder 直接拖拽 | `restic mount /mnt/restic` | 找不准路径、需对比版本、大文件不想全下载 |
| **跨机器恢复** | 另一台机器装 Pluton → 同仓库/同密钥 → 直接见所有快照 | 同仓库 ID + 同 `ENCRYPTION_KEY` | 迁移、克隆环境 |

**实测恢复速度**：50 GB PostgreSQL 仓库、最近快照、本地 NVMe → 目标目录，**全量恢复 3 分 12 秒**（约 260 MB/s），**单文件 ZIP 下载 < 2 秒**。挂载模式首次列目录约 1.5 秒（建索引），后续浏览毫秒级。

**4. 通知与可观测：多渠道、分级别、含日志上下文**

| 渠道 | 配置字段 | 实测表现 |
| --- | --- | --- |
| **Email (SMTP)** | Host/Port/User/Pass/From/To/TLS | 发送可靠，需防进垃圾箱（配 DKIM/SPF） |
| **Slack** | Webhook URL / Bot Token | 支持 Block Kit 富文本、附件日志 |
| **Discord** | Webhook URL | Embed 卡片、代码块日志 |
| **Ntfy** | Topic / Server / Auth | 手机推送、统一标题、优先级标记 |

**日志系统**：每个备份作业运行产生结构化日志（JSON Lines），UI **实时尾随显示**（WebSocket 推送）、**可下载完整日志**、**错误行高亮、可展开上下文**。`restic`/`rclone` 原始输出全保留，**排查失败零黑盒**。

**5. 预/后脚本钩子：把“备份前冻结/备份后通知/备份前 Dump DB”变成配置项**

```
# preScript 示例：MySQL 热备  
docker exec mysql-prod mysqldump --single-transaction --routines --triggers --all-databases | gzip > /mnt/backup-source/mysql/dump_$(date +%F).sql.gz  
  
# postScript 示例：清理本地临时 Dump、触发下游 ETL、上报 Prometheus Pushgateway  
rm -f /mnt/backup-source/mysql/dump_$(date -d '7 days ago' +%F).sql.gz  
curl -X POST http://prometheus-pushgateway:9091/metrics/job/backup/instance/prod-mysql -d "backup_duration_seconds $(date +%s -d '2 minutes ago')"
```

**执行语义**：

* • `preScript` 失败 → **备份作业标记失败、不执行备份、发失败通知**
* • `postScript` 失败 → **备份标记警告、发警告通知、不影响备份本身**
* • 脚本在**宿主机命名空间**运行（Docker `host` network + `pid: host` + 挂载 `/var/run/docker.sock`），可直接 `docker exec`、`systemctl`、`kubectl`。

### 避坑与总结

| 优点 | 缺点/局限 |
| --- | --- |
| Restic/Rclone 成熟引擎、不造轮子、数据格式标准、可离线用原工具恢复 | **单机架构、无原生 HA** ：Controller/Worker/DB/Redis 全在单 compose 里，主机挂了备份停、UI 挂、需外挂 Keepalived/Patroni/外部 DB |
| Web UI 覆盖全生命周期（建仓/调度/保留/复制/恢复/挂载/脚本/通知/日志） | **无分布式调度** ：不能“多节点协同备份同一数据源”、不能“Worker 池动态扩缩”，大规模（>100 作业）需人工分片 |
| Docker/桌面双分发、离线可用、Apache-2.0 商业友好 | **Restic 仓库格式限制** ：单仓库单机写入、不支持并发写（Pluton 用 `MAX_CONCURRENT_BACKUPS` 队列串行），大文件量场景吞吐受限 |
| 70+ 存储后端、S3 兼容、带宽控制、校验和、断点续传全靠 Rclone | **UI 无多租户/组织隔离** ：单用户/单组织，团队共用一套账号、权限粗粒度（Admin/Viewer 仅两级） |
| 恢复体验极佳（浏览/下载/挂载/跨机）、恢复演练门槛极低 | **无原生 Kubernetes/容器卷备份集成** ：需手写 `preScript``kubectl exec`/`velero`，不像 Kopia/Velero 原生懂 PV/PVC |
| 实时进度、结构化日志、错误上下文、可观测性强 | **桌面版自动更新机制弱** ：GitHub Releases 轮询、无增量更新、需手动重装，生产服务端建议用 Docker/Watchtower |
| 备份前/后脚本钩子、宿主机命名空间、可操作任何基础设施 | **加密密钥管理无 KMS/HSM 集成** ：`ENCRYPTION_KEY` 明文在 `.env`/环境变量，合规场景需自行对接 Vault/Sealed Secrets |

**个人判断**：

* • 如果你是**中小团队（< 50 台服务器、< 20 个备份作业、总数据 < 50 TB）**，想**自建“可视化、可审计、可恢复演练、3-2-1 落地”的备份系统**，不想买 Veeam/Commvault、不想维护脚本集群——**Pluton 是当前开源界工程化最完整、体验最好、依赖最少的选择**，Docker Compose 起服务、UI 点点鼠标、恢复演练随时能做。
* • 如果你是**个人/家庭用户**，想**把照片/文档/代码自动加密备份到 NAS/云盘**，不想折腾命令行——**桌面版 Pluton 直接下载安装、设密码、选文件夹、选云盘、定时跑**，比 Duplicati/UrBackup/备份同步王更现代、更安全（Restic 加密）、更透明。
* • 如果你是**大规模生产环境（> 200 台、PB 级、多机房、强 RPO/RTO、需 K8s 原生、需多租户 RBAC、需合规审计追溯）**，**建议上 Velero + Restic/Kopia + 外部对象存储 + 专业备份存储网关**，Pluton 的单机架构、权限模型、K8s 集成度支撑不了此量级。
* • 如果你是**已有 Restic/Rclone 脚本库、只想加个 UI 看状态**——**Pluton 可直接接管现有仓库**（同 `ENCRYPTION_KEY`、同仓库路径），UI 会自动发现历史快照，**平滑迁移、零数据重跑**。
* • **最大局限**：**单机单写入者架构无法水平扩展吞吐**。Restic 仓库设计决定了**同一时刻只能有一个进程写同一仓库**，Pluton 用队列串行化解决并发，**大文件量、高频备份、多并发作业场景下，备份窗口会被拉长**。缓解方案：按业务拆多个仓库（Pluton 支持）、升级 NVMe/10GbE、接受更长窗口。若需真正并行写入，需换用 **Kopia**（支持分片并行）或 **Velero + CSI 快照**，但会失去 Pluton 的开箱即用 UI。
