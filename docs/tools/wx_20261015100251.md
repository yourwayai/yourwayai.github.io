# 还在用Markdown充数？实测GenOffice让Claude Code直接生成能在Word里改的.docx、能在Excel里算的.xlsx

手里有个需求：让 Claude Code 直接帮我生成一份真正的 `.docx` 文件——不是 Markdown、不是 HTML、不是只能看不能改的导出件，而是 Word 打开后能直接改、带修订记录、样式不乱的原生格式。以前这事儿挺麻烦，要么用 python-docx 自己拼 XML，要么让模型输出 Markdown 再用 Pandoc 转，格式全丢。前几天在 GitHub 上看到 **GenOffice**（`genspark-ai/genoffice`，8.7k Star，Apache-2.0），号称“世界上第一个全功能开源 AI Office 套件”，自带桌面端、CLI、MCP Server，还能给 Claude Code、Codex、Cursor 装技能，让代理直接在本机创建、编辑真 Office 文件。我下载了 macOS arm64 版（v0.11.0，`.dmg` 签名安装），在 M2 MacBook Pro 上跑了两周，记录一下实测情况。

---

### 装上手：三分钟从下载到能用

去官网或 Releases 页下对应平台的安装包：macOS 有 arm64 和 x64 两个 `.dmg`，Windows 有 x64 和 arm64 两个 `.exe`，Linux 提供 `.deb`、`.rpm`、`.AppImage` 三种。我用的是 macOS arm64，双击装进 Applications，首启会弹“允许来自身份不明开发者”的提示，右键打开一次就行。

启动后是个标签页式的 Shell，左侧六个应用入口：Docs、Sheets、Slides、PDF、Markdown、HTML，加一个全局搜索。右侧是 AI 面板，默认登录 Genspark 就能用内置模型（Claude、GPT、Gemini 族），不想登录也行，Settings → AI 里塭自己的 Key：Claude、OpenAI、Gemini、DeepSeek、Kimi、GLM、Qwen、Doubao、MiniMax、Grok、Mistral、OpenRouter、Requesty、Opper、Cheaper Inference，甚至任意 OpenAI 兼容端点（本地 Ollama、vLLM 都行）。我配了 Anthropic Key 和 OpenRouter Key，切模型只需下拉选。

文件打开、编辑、保存、转换全在本地跑。只有 AI 调用会出网，且走你配的提供商。这点我挺喜欢——文档不出设备，隐私可控。

---

### 核心亮点一：字节级保真的 docx 编辑，改动只落在动过的块上

GenOffice 的 Docs 引擎不是把 docx 转成中间格式再转回去，而是直接解析 `word/document.xml` 成块树，每个块锚定原始 XML。你手动改或让 AI 改，只把脏块重新序列化成 OOXML 片段，拼回原文档，其余块**字节级原样保留**。这就意味着：样式、注释、修订、公式、墨迹、页眉页脚、双栏版面、Word 的行级分页度量，全都能原样往返。

我试了个真实场景：同事发来一份 40 页的技术规范 `.docx`，带几十个 Track Changes、嵌套表格、交叉引用。拖进 GenOffice Docs，版面跟 Word 里一模一样。让 AI “把第 3 章的概述改成要点式、新增一节‘部署检查清单’”，AI 读了相关块，改完呈现为快照，开着 Track Changes 时落地就是 Word 风格的修订，一键回滚。存盘后丢回 Word，修订记录全在，样式没崩，交叉引用没断。这才是我要的“能给正式流程用”的程度。

---

### 核心亮点二：Sheets 不是贴数字，是真公式、真透视表、真条件格式

表格是我最担心的——太多“AI 表格”只会把算好的数字贴进单元格。GenOffice 自研了 Rust 侧车（`@genoffice/sheets`，基于 `calamine` 读、`IronCalc` 算），跑在 Node 里通过 NAPI 调用。打开 `.xlsx` 时它把公式、透视表、切片器、条件格式、公式追踪全解析进内存，编辑时只重算受影响区域。

实测：给一句 “按地区和品类汇总销售额，插入 SUMIFS，加一列柱状图”，Agent 在 Summary 工作表里真写了 `=SUMIFS(...)`，图表绑定的是动态区域，不是死数据。改源数据，图表跟着变。保存回 `.xlsx`，Excel 打开公式能算、图表能动、透视表能刷新。这背后是自研 OOXML 引擎 + Rust 计算层，不是套个现成库糊弄。

---

### 核心亮点三：Slides 从一句提示词到可交付的 .pptx，中间全程可审计

Slides 的工作流是分阶段的：`deck_start` 定样式表与大纲 → `deck_page` 逐页生成规格 → 每页 `slides check` 审计溢出/重叠 → `deck_build` 组装 `.pptx` → `slides_render` 出每页 PNG 让模型“看”效果 → `deck_replace` 修问题页。全程 CLI 可复现，Agent 只负责思考，构建和检查交给本地引擎。

我让 Claude Code（装了 GenOffice 技能）“做个 10 页融资路演Deck，主题：家用储能，封面要真实照片”。Agent 先`guide(slides, design)` 拿布局库，`search` 查 IEA/BNEF/IRENA 数据，`search(images)` + `media(ask="是真实照片吗")` 筛图，再走上面那套流程。38 次工具调用、约 13 分钟，出来 11 页 `.pptx`，版式统一、字体一致、图片全是实拍图。打开 GenOffice Slides 或 PowerPoint，母版、布局、智能参考线、非破坏性裁剪全能用，还能让面板继续改风格、改文案、调顺序。

---

### 核心亮点四：PDF 真·文本编辑 + 本地转 Word/Excel/PPT，扫描件走系统 OCR

PDF 应用基于 PDFium（`@embedpdf/pdfium`），编辑文本时把内容流重写，保留原字体，不是加个注释层遮上去。转换器 `pdf2docx`/`pdf2xlsx`/`pdf2pptx` 全在本地跑，扫描件自动调用系统 OCR（macOS Vision、Windows OCR、Linux Tesseract）。

我扔进一份 60 页的扫描版合同 PDF，选“PDF → Word”，约 90 秒出 `.docx`，标题行、款项表格、正文段落结构基本还原，个别手写批注识别不全（这是 OCR 上限）。在 PDF 里直接改文字、改字号、删图片，存回 PDF，原排版没乱。这替代 Acrobat Pro 对于大部分“改几个字、转个格式”的场景绰绰有余。

---

### 核心亮点五：HTML 应用是“先出设计简报、再生成单文件、再可视化微调”

HTML 应用不像那些“一键生成页面”玩具。你描述页面用途和受众，AI 先给设计简报——Hook、配色、排版风格、风格方向，确认后再生成单个自包含 `.html`。生成后点任意元素可重设样式、双击改文本、切 CodeMirror 源码视图。同一份简报，一句 “Restyle：暖纸色、编辑衬线、向日葵橙强调色”，Token 一换，页面跟着变，代码没重写。

我试了“个人仪表盘”启动器：左侧导轨、问候、工时闪烁卡片、发票清单、利用率图表，全是真 HTML/CSS/JS，扔给前端同事直接能接手开发。还有“数据报告”启动器：衬线报头、一条大数字、分隔统计行、内联 SVG 图表、方法论备注，读起来像篇专业宽版报道。

---

### 核心亮点六：本地全文检索 + TypeSafe Jev 重排序，找的是“答案”不是“关键词”

工作区文件夹下所有 `.docx/.xlsx/.pptx/.pdf/.md/.html` 会在后台建 SQLite 全文索引（含 CJK 分词），默认离线。开启 “Settings → AI Media & Search → Local file search → Jev search reranking”，前 20 条本地命中会发给 TypeSafe Jev（System One 判断模型，单次调用给每文档一个校准相关性分），按分重排。索引不出设备，只发摘要。

实测搜 “笔记本电脑刷新策略”，全文检索前三全是“浏览器缓存刷新策略”“品牌刷新计划”“仪表盘刷新调度”，Jev 重排后把“设备三年更换周期标准”排第一。那条文档里根本没“刷新策略”四个字，但语义上最贴切。开关默认关，需自己配 OpenRouter 或 TypeSafe 直连 Key。

---

### 核心亮点七：CLI 与 MCP——让编码代理变成“文档工人”

装完桌面端，`genoffice` CLI 就可用（macOS 在 `/Applications/GenOffice.app/Contents/Resources/cli/genoffice`）。常用命令：

```
genoffice info report.docx --json           # 标题与块结构  
genoffice convert report.md --to pdf        # 互转：md/html/docx/xlsx/pptx ↔ pdf  
genoffice create --type docx --from notes.md --out notes.docx  
genoffice create --type xlsx --from table.json --out sales.xlsx  # 公式保持活的  
genoffice docs read report.docx --range 0-9 --json  # 再配合 docs apply --ops edits.json 原地改  
genoffice render report.docx --out shots/   # 每页一张 PNG  
genoffice open sales.xlsx                   # 把结果交给编辑器打开
```

每条命令单行摘要或单 JSON 对象，编辑是原子的：拒绝的操作不落盘，返回带引导的错误。

**Agent 技能**：Settings → Integrations 一键把技能写入本机检测到的 Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot、OpenCode、Windsurf。或`npx skills add genspark-ai/genoffice`。技能教会 Agent 何时调 `genoffice`、改前先读、改后自检。

**MCP Server**：两种接入。A）`genoffice mcp`（stdio，推荐），助手自启，GenOffice 甚至不用开窗口；29 个工具 + 分阶段Deck流（`deck_start → deck_page → deck_build → deck_replace`）。B）App 内 HTTP Server（`http://127.0.0.1:3093/mcp`），驱动可见的 Word 编辑器标签页，你看着文档长出来。C）`genoffice mcp --http` 把 stdio 工具集暴露为 Streamable HTTP，适合容器/沙箱/局域网共享机，带文件上传下载、Token 保护、路径限制。

我给 Claude Code 加了 MCP（`claude mcp add --transport stdio genoffice -- genoffice mcp`），提示词 “基于最新数据做个 8 页 2026 年可再生能源投资简报，封面和关键页配真实照片”，全程 38 次调用、约 13 分钟，Agent 从未碰 Shell，搜数据、找图、验图、写大纲、逐页生成、审计、渲染、修三页、出 `.pptx`。云端只走搜索和媒体，其余全本地。

### 避坑与总结

| 项 | 实测表现 | 备注 |
| --- | --- | --- |
| **安装体积** | macOS arm64 `.dmg` 约 380 MB，安装后约 1.2 GB | Electron + Rust sidecar + 打包字体 |
| **冷启动** | Shell 約 3 秒，单应用再 1-2 秒 | 首次建索引会占 CPU 一小会儿 |
| **内存占用** | 单应用 400-600 MB，六应用全开约 2.5 GB | 16 GB 以上机型无感，8 GB 机型建议按需开 |
| **大文件表现** | 100 页 docx / 5 万行 xlsx / 80 页 pptx 均能打开 | 解析耗时随块数线性增长，Sheets 大表首算约 2-3 秒 |
| **格式兼容** | Word/Excel/PowerPoint 2013+ 产出的文件基本完美往返 | 极老版本二进制格式（.doc/.xls/.ppt）不支持 |
| **AI 成本** | 取决于你配的提供商；Genspark 登录走代理计费 | 本地模型（Ollama/vLLM）可零成本跑轻量任务 |
| **局限性** | **无实时协作/多人同时编辑** ；**无宏/VBA 支持**；**移动端无原生应用**（Web 端规划中）；**复杂版面（如密集浮动图文环绕）AI 生成仍偶尔溢出**，需人工微调；**Linux Wayland 下 PDF 编辑偶发光标偏移**（已知 Issue #1423）；**CLI/MCP 依赖桌面端安装的引擎**，无独立无头二进制。 |  |

---

我个人觉得：如果你常在本地处理 Office 文件，且想把 AI 融入“改文档、做表格、出幻灯片、转 PDF”的真实流程里，而不是止步于“给我一段 Markdown”，GenOffice 是目前**最完整、最诚实、最可落地**的开源方案。它没吹牛“替代 Office 365”，而是把“原生格式、字节级保真、本地优先、Agent 可驱动”这四件难事实打实做到了一起。

比较适合：需要给甲方/领导/客户交付 `.docx/.xlsx/.pptx` 的自由职业者、咨询顾问、产品经理、研究员；想让编码代理直接产出真 Office 制品的开发者；对数据不出设备有硬性要求的团队。

不太适合：必须实时协作的团队（飞书/腾讯文档/Office 365 协作体验它没法比）；离不开 VBA/宏的老旧流程；只需轻量记笔记的用户（Obsidian/Notion 更轻）。

把它当“可被代理驱动的本地专业办公引擎”用，心态最稳。v0.11 已经能跑通大部分日常流程，后续迭代（实时协作、Web 端、移动端、更多导入格式）在 CONTRIBUTING.md 和 Issues 里都能看到规划。值得 Star 持续关注。
