# 不想开 VPN、不想上云？实测在公司飞书里直接 @ 本地 Claude Code 写代码、跑测试、改配置

有个很具体的痛点：我想在飞书群里直接 @ 机器人，让它帮我跑本地的测试、改配置文件、甚至重构一个模块，但代码得跑在**我的开发机上**，不能上传到云端、不能走公网代理。以前折腾过 Slack Bot + ngrok、Discord Bridge + Cloudflare Tunnel、企业微信应用 + 内网穿透，要么配置繁琐，要么稳定性差，要么公司网络策略直接拦截。

前几天在 GitHub 上看到 **lark-coding-agent-bridge**，号称“轻量级桥接飞书/ Lark 与本地 Claude Code 或 Codex CLI”，一条命令安装、扫码绑定 PersonalAgent 应用、后台服务一键托管。我下载了最新主分支代码（Node.js 20.12+，TypeScript 99.8%），在 MacBook Pro M2（macOS 14.6）和一台 Ubuntu 22.04 服务器上分别跑通，记录一下实测情况。

---

### 装上手：三步从零到能用

前置条件：本机已安装并登录 `claude`（Claude Code）或 `codex`（Codex CLI）。没装的先去官网按文档装好、跑通 `claude --version` 或 `codex --version`。

```
# 全局安装  
npm i -g lark-channel-bridge  
# 或 pnpm add -g lark-channel-bridge  
  
# 首次运行：引导扫码绑定飞书应用  
lark-channel-bridge run
```

终端会渲染一个 QR 码，用飞书 App 扫一下，选“创建 PersonalAgent 应用”或选已有应用，授权后配置自动写入 `~/.lark-channel/config.json`。不需要提前选项目目录，桥会创建一个受管的默认工作目录；启动后在飞书里发 `/cd /path/to/project` 切到真实项目。

首跑建议用 `run` 前台调试，确认能收发消息后 `Ctrl-C` 停掉，改用系统托管的后台服务：

```
lark-channel-bridge start     # 安装并启动守护进程  
lark-channel-bridge status    # 查看状态  
lark-channel-bridge stop      # 停止
```

macOS 用 `launchd`（用户级 Agent `ai.lark-channel-bridge.bot.<profile>`），Linux 用 `systemd --user`，Windows 用任务计划程序包装 `.cmd`。守护进程日志在 `~/.lark-channel/profiles/<profile>/logs/daemon/`。多 Profile 支持 Claude 和 Codex 同时跑：

```
lark-channel-bridge profile create claude --agent claude  
lark-channel-bridge profile create codex --agent codex  
lark-channel-bridge start --profile claude  
lark-channel-bridge start --profile codex
```

每个 Profile 独立保存应用凭证、会话、工作目录、日志，互不干扰。

---

### 核心亮点一：飞书端“发消息 = 给本地 CLI 传参”，流式卡片实时看进度

在飞书私聊直接发消息，群里 `@机器人` 发消息，桥把文本转发给本地 `claude` 或 `codex` 子进程。子进程的 stdout/stderr 按行流式回传，飞书端渲染成**流式卡片**：文本逐字出现、工具调用（读文件、跑命令、改代码）实时展开、完成后自动折叠。你不用盯着终端，手机上就能看到 Agent “在想什么、在跑什么命令、改了哪几行”。

更有意思的是 **COT 过程消息**（Chain of Thought）：`/config` 里开启后，桥会把“思考过程 + 工具调用摘要”单独发一条过程卡片，最终答案再发一条正式回复。过程卡片方便溯源、排查；最终答案干净可读。`brief` 模式只出工具摘要，`detailed` 模式连工具参数和截断输出都带上。我平时开 `brief`，调疑难 Bug 时切 `detailed`。

---

### 核心亮点二：会话隔离做得很细，群聊、话题、文档评论互不串

每个**私聊、群聊、话题组、云文档评论线程**各自维护一个会话上下文。你在群 A 让 Agent 写 Python，群 B 让它改 Go，互不污染。快速连发的消息会自动合批处理；跑任务期间新来的消息进队列，等当前 Run 结束再处理。`/new`、`/cd`、`/ws use`、`/stop` 等指令能打断当前任务、重置上下文。

`/ws`（Workspace）是我用得最多的：`/ws save backend` 存当前目录，`/ws use backend` 一键切回，`/ws list` 看所有存过的工作区。配合 `/cd` 临时切目录，完全不需要在终端敲 `cd`。

---

### 核心亮点三：图片、文件直接拖给机器人，本地落盘给 Agent 用

飞书端拖图片、发文件，桥自动下载到 `~/.lark-channel/profiles/<profile>/media/`，把本地路径塞进发给 CLI 的上下文。Agent 能直接读图（`claude` 支持视觉）、解析 CSV/JSON/日志、甚至把截图里的报错栈转成代码修复建议。发完文件在飞书说“帮我看看这个报错是啥原因”，Agent 真能读到文件内容。

---

### 核心亮点四：权限模型既安全又不卡手，三层列表 + 两个超级身份

默认**私有**：只有创建者（扫码那人）能私聊、能在任意群 @、能跑所有指令。想让同事用？三张名单：

* • **允许用户**：`/invite user @同事` → 同事能私聊 Bot
* • **允许群聊**：群里发 `/invite group` → 该群所有人能 @ Bot
* • **管理员**：`/invite admin @同事` → 能改配置、能在任意群用、能跑管理指令

两个**无视所有名单**的身份：

1. 1. **创建者**：永远拥有最高权限，永远不会被自己锁在外面。转移飞书应用所有权，Bot 自动跟着新 Owner。
2. 2. **管理员**：越过“允许群聊”名单，在任何群都能用。

陌生人 @ 机器人？默认**纯静默**，不回“权限不足”、不暴露存在。唯一例外：群未开放时被 @，Bot 会友好提示一句“管理员可运行 `/invite group` 开启”。改名单、改配置**无需重启**，下一条消息生效。

---

### 核心亮点五：权限模式映射到 CLI 原生模式，想锁死也方便

桥把自己的 `permissions.defaultAccess / maxAccess` 映射到 CLI 原生权限模式：

| 桥配置 | Claude Code | Codex CLI |
| --- | --- | --- |
| `full` （默认） | `bypassPermissions` | `danger-full-access` |
| `workspace` | `acceptEdits` | `workspace-write` |
| `read-only` | `plan` | `read-only` |

新 Profile 默认 `full`，保证登录授权、文件写入、本地工具全通。想收紧，改配置或 `/config` 里调。老配置里的 `sandbox` 字段会自动迁移。

---

### 核心亮点六：云文档评论里 @ 机器人，直接在评论线程里回复

支持的云文档类型里，评论 @ Bot，桥在同一评论线程回复。会话键复用文档维度，无文档工作目录记录时回落到用户主目录。不需要额外绑定文档、维护白名单。

---

### 核心亮点七：看门狗、诊断、遥测——生产可用的工程细节

* • **空闲看门狗**：`/timeout 10` 设置当前会话 10 分钟无输出自动杀进程、卡片标注自动终止原因；`/timeout off` 关闭；`/timeout default` 清除会话覆盖。全局默认关。
* • **诊断**：`/doctor [描述]` 跑低敏诊断，不上传数据。
* • **可选遥测**：设 `LARK_CHANNEL_TELEMETRY_MODULE` 指向自定义 Adapter 工厂，拿到所有 `log.*` 事件、错误、指标，推给你的监控系统。模块缺失、工厂报错、Adapter 抛异常全降级为 noop，**遥测绝不阻塞主流程**。

---

### 避坑与总结

| 项 | 实测表现 | 备注 |
| --- | --- | --- |
| **安装体积** | 全局安装约 45 MB（含依赖） | TypeScript 编译产物 + 少量运行时 |
| **启动耗时** | `run` 冷启 2-3 秒出 QR；`start` 守护进程约 1 秒拉起 | 首次扫码绑定约 30 秒 |
| **内存占用** | 桥进程约 60-80 MB，Claude/Codex 子进程另算 | 16 GB 机型无感 |
| **消息延迟** | 局域网飞书 → 本地 CLI 约 200-400 ms；流式卡片首帧约 500 ms | 取决于飞书 WebSocket 延迟 |
| **长任务稳定性** | 跑 30 分钟重构任务，中途切网络/合盖/锁屏，恢复后自动续跑 | 依赖 `START_STICKY` 与飞书重连机制 |
| **多账号隔离** | Profile 间会话、工作区、密钥、日志完全隔离 | 可同时跑 Claude + Codex 两个 Bot |
| **局限性** | **依赖飞书 PersonalAgent 应用** （需管理员权限或自建应用）；**无 Web UI 管理后台**（全靠斜杠指令/配置文件）；**文件系统非沙箱**，Agent 实际权限取决于 CLI 进程权限模式；**Windows 守护进程需手动注册任务计划**，不如 macOS/Linux 优雅；**飞书国际版需加 `--tenant lark`**；**云文档评论仅支持部分文档类型**（见 FAQ）。 |  |

---

我个人觉得：如果你（或你们团队）已经在用飞书、已经在本地跑 Claude Code/Codex、又不想把代码传到云端、又想随时随地在手机上发需求、看进度、收结果，这东西是**目前折腾成本最低、工程完成度最高**的方案。它没搞花哨的 Web 面板、没强行上云、没把简单问题复杂化，就是把“本地 CLI ↔ 飞书消息”这条路铺平、铺实、铺稳。

比较适合：常在会议/通勤/远程时想掌控本地开发机的个人开发者；想在内网群里让同事也能用上本地 Agent 的小团队；对数据不出本地有硬性要求、又不想自建复杂网关的合规敏感环境。

不太适合：完全不用飞书的团队；需要可视化管理后台、审计日志、RBAC 矩阵的大企业；只想在网页端聊天、不想装桌面客户端的用户（飞书 PersonalAgent 必须在 App 端交互）。

把它当“给本地编码代理装个飞书前置、再配个 systemd 守护”用，心态最稳。主分支更新频繁，值得 Star 跟进。
