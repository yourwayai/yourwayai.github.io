前几天在 GitHub 看到 WordCraft，一个用纯 Rust 写的 Word 替代品。这类项目我一般扫一眼就关——功能清单列得吓人，实际打开个 .docx 都是花的。这次多看了两眼，是因为 README 敢把数字写出来：「188 页的文档重新排版只要 1.4 ms」。真假后面说，至少它没藏着。另外查了下 GitHub API，仓库创建于 2026-10-07，到现在 13.5k Star、3.5k Fork，热度是真的。

### 部署实录

README 给的路径很直接：

```
git clone https://github.com/storytold/wordcraft  
cd wordcraft  
cargo run --release -p wordcraft -- --sample    # 带示例文档启动桌面版  
cargo run --release -p wordcraft -- report.docx # 直接打开一个文档
```

不想编译也有现成包：macOS 是签名加公证过的 universal DMG，Windows 覆盖 x64/arm64/x86 的 MSI 和便携版，Linux 有 AppImage、deb、rpm、Flatpak，连 RISC-V 和 FreeBSD 都有 tarball。Arch 用户 `yay -S wordcraft-bin` 就行。

真机编译我没有条件验证——88,700 行 Rust 加一个 wasm 构建，具体耗时我不清楚，这里不编数字。

浏览器版是另一条路：`cd apps/wordcraft-web && trunk serve`，然后开 http://127.0.0.1:8771/?sample。同一套代码编译成 WebAssembly（一种能在浏览器里跑的高性能字节码），没有套 Electron（把整个 Chrome 内核塞进去的那种跨平台方案）。

有一个已经写进 README 的坑值得先知道：Windows 版默认只初始化 DirectX 12，部分 AMD 驱动（atio6axx.dll）会在窗口出现前把进程搞崩。官方解法是先设 `$env:WGPU_BACKEND = "vulkan"` 再启动。

### 什么都能命令化

WordCraft 内部所有操作都是带 ID 的命令，功能区、快捷键、命令行、JSON 控制通道和 MCP 服务器（Model Context Protocol，让 AI 通过标准协议调用外部工具的规范）走的是同一批。简单来说，你在界面上点的每一步，底层都是一次 execute。

它对 Agent 场景的意义主要在这里。README 给的接法：

```
claude mcp add wordcraft -- wordcraft-cli mcp
```

也可以驱动跑起来的应用：`wordcraft --control 7981` 起服务，再 `wordcraft-cli mcp --connect 127.0.0.1:7981`。工具包括 inspect\_document、render\_page、type\_text、screenshot、click、key 这些。我觉得比较巧妙的是 inspect\_document——AI 改完文档可以不看截图，直接读结构自检。另外它能用 `--automation-read-root` 和 `--automation-write-root` 把 Agent 可读写的目录圈死，这点比多数「AI 办公」方案严谨。

### 文件格式这一层

.docx（Word 的默认格式，本质是 OOXML 压缩包）读写是基本盘，还能打开 Word 97-2003 的 .doc，导出带可选文字、链接和书签的 PDF；.odt、.rtf、.html、.md、.tex 双向转换。命令行一条 `wordcraft-cli convert report.docx report.pdf` 就完事。对文档流水线来说，这等于一个无头（headless，即不依赖图形界面）的 docx 处理器。

顺带一个极客细节：README 里所有截图都是 `cargo run -p wordcraft-ui-egui --example ui_shot` 离屏渲染出来的——它用 UI 测试工具给自己截屏。界面基于 egui（Rust 的即时模式 GUI 框架）加 vello\_cpu 光栅化，官方口径是段落布局有缓存，188 页文档里打字只需重排约 1.4 ms（README 数据，非我实测）。命令数这里较个真：README 写 422，ROADMAP 写 433，两份文档更新日期差两天，按新的 README 算是 420 多条。

### 避坑与总结

丑话说前面。官方 ROADMAP 的自我评估：距离「真正替代所有 Word 工作」约 60%，主流职业用户约 55%，基础用户约 63%。明确没到位的包括：

1. 1. .docx 从未在真实世界文件上测过，这是原文表述
2. 2. 图表、SmartArt、OLE 对象会被静默丢弃
3. 3. 分页与 Word 有差异：缺 Aptos 度量字体、栏位平衡、脚注延续
4. 4. 内容控件会丢失
5. 5. 有启动崩溃和卡死的现场记录
6. 6. 原生打印 2026-10-12 才通过 craft-print 落地，v0.7.0 才带打印机选择

配套数字也很诚实：外部用户提交的 120 个 issue 里 4 个好评、0 个说「我从 Word 迁过来了」，约 21 个核心路径 bug 还开着。官方把到 beta 的距离标为 150–230 小时（按他们的 Agent 工时口径估算）。所以它现在的定位很清楚：核心流程能跑通、全平台签名发布，但没到能替班的程度。

我的判断分场景：如果你受够了把 .docx 在几个工具之间倒腾，或者想让 AI 直接操作文档、批量处理格式，它现在就能用，MCP 那层是现货；如果你每天靠 Word 和同事来回改稿、收发的都是带图表的企业文档，再等等，它现在还接不住。

把它当「命令行 + Agent 可驱动的 .docx 工作台」用，心态最稳。
