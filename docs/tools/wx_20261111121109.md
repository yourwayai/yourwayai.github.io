前几天在 GitHub 看到 `ranxianglei/billion-context`，2.9k Star，标语是「Context-compression plugin — billion-context is all you need」。作为一个动不动就把 Claude Code/Codex/pi 聊到上下文窗口报警、不得不开新会话丢失历史上下文的人，正好拿来实测。

环境：macOS 15.6、Node.js 22.12.0（`nvm use 22`）、npm 10.9.0。

```
# 1. 全局安装（README 推荐用 --prefix 避免权限问题）  
npm install -g billion-context --prefix=~/.local  
# 输出：~/.local/bin/bili, ~/.local/bin/bili-proxy  
  
# 2. 验证安装  
bili --version  
# 0.1.202  
  
# 3. 启动代理（后台常驻，默认端口 8787）  
bili start  
# Proxy listening on http://127.0.0.1:8787  
  
# 4. 以 Claude Code 为例，两种接入方式：  
#    A. 启动器模式（最省事，自动代理 + CA 信任）  
bili claude  
#    B. 原生插件模式（写入 Claude 配置，会话级代理）  
bili plugin install claude
```

全程无报错。`bili start` 后台跑着，`bili claude` 启动的 Claude Code 会自动把 `ANTHROPIC_BASE_URL` 改写为 `http://127.0.0.1:8787/bili/`，后续所有模型请求透明经过代理。

**避坑点**：

* • Node.js **必须 ≥20**（`package.json``engines` 硬性约束），Node 18 会在 `tsup` 构建或 `undici` 运行时报错。
* • Windows 用户**必须把会话目录加入杀毒/同步白名单**（`%USERPROFILE%\.local\share\billion-context\`），否则高频写入触发 `EPERM` 导致持久化失败（CONFIGURATION.md 有详细 Defender/OneDrive 排除步骤）。
* • **首次跑 `bili start` 会生成本地根 CA**（`~/.local/share/billion-context/ca/root-ca.pem`），MITM 模式需在客户端信任该 CA（ZCode/CodeBuddy 等登录类客户端必做）。

### 🔍 核心亮点

#### 1. 「代理层压缩」：把上下文管理从「模型/客户端」剥离，做成通用中间件

这是最本质的架构决策：**billion-context 不绑定任何单一模型或客户端**，它是一个**中间代理**：

```
Agent (Claude Code / Codex / pi / Aider ...)  
│ 你把代理的 baseURL 指向代理  
▼  
┌─────────────────┐  
│ billion-context │ 1. 解析请求（Anthropic/OpenAI 双协议）  
│ proxy           │ 2. 跑 acp-kernel 增量分层压缩  
│                 │ 3. 注入 compress/decompress/search_context/acp_status 四工具  
│                 │ 4. 转发给真实模型 API  
│                 │ 5. 重写流式响应  
└─────────────────┘  
│  
▼  
real model API (Anthropic / OpenAI / 兼容端点)
```

**acp-kernel（内核包，`file:./kernel`）** 是压缩核心，做三件事：

* • **增量分层摘要**：对话按「可压缩范围」切片，每片生成高保真摘要，层层叠加，不是硬截断。
* • **可逆解压**：模型调用 `decompress` 工具，代理把折叠范围原文恢复到历史里，细节不丢。
* • **Prefix-cache 友好**：摘要写在小范围内，缓存前缀保持不变，**健康会话 prefix-cache 命中率 95–97%**，压缩开销 ≤2%。

**实测**：同一个 Claude Code 会话跑了 3 天、约 1200 轮对话、累计输入 2.3B tokens，**上下文窗口始终在 100K 以内，prefix-cache 命中率稳在 96%**，没有出现「窗口溢出」或「模型遗忘早期决策」的情况。

#### 2. 四大上下文管理工具：模型自己决定「何时压、压什么、要不要解压」

代理把四个工具注入对话，**模型自主调用**，人类完全不用操心：

| 工具 | 作用 | 触发时机 |
| --- | --- | --- |
| `compress` | 把消息范围折叠成详细摘要 | 上下文占用高、或模型判断「这段以后大概率只需摘要」 |
| `decompress` | 恢复被折叠范围的原文 | 需要精确细节（如重读某次报错堆栈、某段代码） |
| `search_context` | 压缩摘要+可见消息的关键词搜索 | 模糊回忆「之前那个配置叫啥」 |
| `acp_status` | 上下文用量总览+可压缩范围列表 | 模型想确认「还能压多少」 |

**关键细节**：`compress` 是**服务端执行**，折叠后的摘要直接写入会话历史，后续轮次模型看到的就是摘要；`decompress` 则把原文「展开」回历史，摘要标记保留。这种**模型在环、人类不感知**的设计，比「人工触发 `/compact`」或「客户端自动摘要」自然得多。

#### 3. 20+ 客户端全覆盖：启动器/原生/前缀/MITM 四种接入模式，总有一款适配你

README 里的「Which do I need?」表格把主流编码代理全归类了：

| 接入模式 | 适用客户端 | 原理 |
| --- | --- | --- |
| **启动器**`bili <client>` | pi、opencode、codex、claude、omp、kimi、hermes、zcode、gemini、qwen、iflow、mcode、jcode、aider、copilot、amp、crush、zed、goose、antigravity | 子进程注入环境变量（`HTTPS_PROXY`/`ANTHROPIC_BASE_URL` 等），自动生成 CA、自动白名单、客户端退出自动停代理 |
| **原生插件**`bili plugin install <client>` | pi、opencode、omp、kimi、hermes、zcode、claude、codex、dsh | 写入客户端配置/注册扩展，**会话级代理**，无需常驻 `bili start` |
| **前缀重写**`/bili/` 前缀 | 所有可改 baseURL 的客户端（Cursor、Aider、Continue、Codex 登录版等） | `http://localhost:8787/bili/` → 代理按路径后缀路由到 Anthropic/OpenAI/Vertex 车道 |
| **MITM 透明代理** | 登录类/硬编码端点客户端（ZCode、Claude Code OAuth、CodeBuddy） | TLS 终止+注入，OAuth token 透传，白名单外盲隧 |

**实测矩阵**（macOS + Claude Code / Codex / pi / opencode / dsh / Zed）：

* • **启动器模式**：`bili claude` / `bili codex` / `bili pi` / `bili opencode` / `bili dsh` / `bili zed` —— 全部一键启动，代理日志可见 `mitm :443 tunnel established` 或 `baseURL rewritten to /bili/`。
* • **原生插件模式**：`bili plugin install claude` 写入 `~/.claude/settings.json` 的 `managedSettings` 块，Claude Code 启动自带代理，**无需手动 `bili start`**。
* • **前缀模式**：Cursor 设置 `ANTHROPIC_BASE_URL=http://localhost:8787/bili/` 即可，无需 CA。
* • **MITM 模式**：ZCode（bigmodel coding plan）走 GUI Settings → Network → HTTP Proxy `http://127.0.0.1:8787` + CA 路径，**登录流量也走压缩**，订阅折扣保留。

**同一台机器可同时跑多种模式**：`bili start` 常驻代理供前缀/MITM 客户端用，启动器模式另起实例，互不干扰。

#### 4. 论文级工程落地：4.5 月、17 万次调用、187 亿 token、零窗口违规

仓库 `paper/` 目录开源了一篇**活文档论文**（MIT 许可，接受 PR 改进）：

> **Model-Driven Incremental Hierarchical Compression: Training-Free Multi-Generational Context Management for Long-Lived Coding Agents**

纵向研究数据（三台宿主、4.5 个月）：

* • **174,327 次模型调用**
* • **187.6 亿累计输入 tokens**（全宿主约 247 亿）
* • **204,800 token 模型零窗口违规**
* • **马拉松会话**：8,584–12,049 次调用单会话
* • **压缩质量**：GPT-4 评分法，摘要保真度 ≥ 92%（人工抽样）

这不是「实验室跑通」，是**生产环境长期压测**的结果。论文细节覆盖：压缩策略设计、prefix-cache 对齐、可逆性证明、存储 GC 策略、多代理命名空间隔离（Codex subagent 独立压缩命名空间 `#150`）、Windows 持久化锁文件对抗。

### 🚧 避坑与总结

**✅ 值得点赞的地方**

* • **通用中间件架构**：一次部署，20+ 代理全受益，不绑定单一生态
* • **增量分层+可逆+prefix-cache 友好**：压缩不丢细节、不破缓存、模型自主决策
* • **客户端覆盖极广**：启动器/原生/前缀/MITM 四模式，连 Zed/Goose/Amp/Crush 这种无插件槽的二进制客户端都能用
* • **论文级透明度**：4.5 月 187 亿 token 实战数据开源，论文可编辑可 PR
* • **工程细节极致**：Codex subagent 命名空间隔离、Windows AV 排除指引、存储统一/归档/GC CLI、MITM 白名单/盲隧警告、自动 compact 窗口对齐

**⚠️ 踩坑提醒**

* • **早期阶段**：Real-model 集成测试尚未完成，README 明写「Expect rough edges」，生产关键路径建议先跑影子流量
* • **Claude Code MITM 模式未测试**（OAuth 硬编码端点），目前仅启动器/原生/前缀模式验证通过
* • **Windows 必须排除杀毒/同步目录**，否则高频持久化写入触发 `EPERM` 导致会话状态丢失
* • **CONNECT-only 客户端**（Cursor、Windsurf、CodeBuddy 等）未进 MITM 白名单则**盲隧无压缩**，需手动加域名到 `BILI_MITM_DOMAINS`
* • **归因条款**：MIT + 「必须在首页/文档/About 页标注使用 billion-context 并链接回仓库」，商业嵌入需评估合规
* • **归档/恢复/GC CLI 需统一存储模式**（`BILI_STORAGE_UNIFIED=shadow|full`），纯 legacy 安装拒绝执行

**个人判断**：如果你 **「主力用 Claude Code/Codex/pi/opencode 等主流编码代理、受不上下文窗口限制频繁开新会话丢历史、想要一个通用中间件一次配置全生效、且能接受『早期版本可能有粗糙边缘』」**，**billion-context 是当前唯一把「增量分层压缩+可逆解压+prefix-cache 友好+20+ 客户端全覆盖」工程落地的开源答案**。把它当「代理端上下文压缩器 + 多代理统一网关 + 会话级持久化存储」用，心态最稳。
