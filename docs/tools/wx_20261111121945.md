前几天在 GitHub 看到 `AgriciDaniel/claude-obsidian`，15.8k Star，标语是「Self-organizing AI second brain for Obsidian + Claude Code」。作为一个常把笔记散落在 Notion、Obsidian、本地 Markdown、甚至浏览器书签里、最后「存了就找不着」的人，正好拿来实测。

环境：macOS 15.6、Python 3.12.7、Obsidian 1.7.4、Claude Code 最新版、Git 2.45。

```
# 1. 克隆产品仓库（注意：这是产品代码，不是你的知识库）  
git clone https://github.com/AgriciDaniel/claude-obsidian.git  
cd claude-obsidian  
  
# 2. 初始化一个独立的知识库（干净分离，产品代码不污染笔记）  
export GENERATED_AT="$(date -u +%Y-%m-%dT%H:%M:%SZ)"  
export OPERATION_ID="init-reviewed"  
python3 scripts/claude-obsidian.py init "$HOME/Documents/MyKnowledgeVault" \  
  --generated-at "$GENERATED_AT" --operation-id "$OPERATION_ID"  
# 输出 JSON 计划，包含 approved_plan_sha256  
  
# 3. 复制哈希，正式应用（显式确认，防误操作）  
python3 scripts/claude-obsidian.py init "$HOME/Documents/MyKnowledgeVault" \  
  --generated-at "$GENERATED_AT" --operation-id "$OPERATION_ID" \  
  --approved-plan-sha256 "<刚才复制的哈希>" --apply  
  
# 4. 进库，挂载插件，启动  
cd "$HOME/Documents/MyKnowledgeVault"  
claude --plugin-dir /absolute/path/to/claude-obsidian  
  
# 5. 进 Claude Code 后，打开技能面板  
/claude-obsidian:wiki  
# 然后把素材丢进 inbox/，跑  
/claude-obsidian:wiki-ingest
```

全程无报错。关键体验：**每一步写入前都会先输出 JSON 计划、给哈希、让你显式 `--apply`**，这叫「可恢复事务」——README 说得很透：「一逻辑操作 = 一可恢复事务，并行 Worker 只返草稿，编排器检查合并后一次性应用」。

**避坑点**：

* • **Python 必须 ≥3.11**，3.10 会在 `scripts/claude-obsidian.py` 启动时报 `SyntaxError`（用了 3.11+ 的 `ExceptionGroup` 等特性）。
* • **Windows 原生不支持写入**（报 `UNSUPPORTED_PLATFORM`），必须在 WSL 里跑 `init`/`adopt`/`migrate`/`transaction apply`，README 给了完整的 WSL 挂载、哈希在 WSL 里审核再 apply 的流程。
* • **Claude Code 插件名在 v3.0.0 改过**（`claude-obsidian` → `agricidaniel-obsidian` → v3.0.1 改回 `claude-obsidian`），升级按 CHANGELOG 3.0.1 节操作即可，旧配置需手动改键。

### 🔍 核心亮点

#### 1. 「可恢复事务」架构：把「知识库写入」做成了有契约的工程操作

这是最硬核的设计：**每次写入都是一次「可恢复事务」**，而非随意的文件追加。

```
事务流程（README 图解）：  
1. 读取所有目标文件，记录预期 SHA-256  
2. 并行 Worker 只返回草稿 + 证据，不落盘  
3. 编排器把完整变更合并成一个操作包  
4. 检查操作包，再一次性应用  
5. 报告操作 ID 与确切变更路径
```

**核心机制**：

* • **进程级 vault 锁**：同一时间只有一个事务在跑
* • **日志回滚**：中断/失败自动恢复前一状态
* • **原子替换**：写入临时文件再 `rename`，避免半写损坏
* • **冲突即报错**：目标文件在事务期间被外部改动 → 直接冲突报错，绝不静默覆盖
* • **Git 检查点**：显式操作，不自动提交

**实测**：我在 `wiki-ingest` 过程中强制 `kill -9` 进程，重跑 `transaction recover --vault`，**知识库完好无损，未应用的草稿全丢、已应用的全保留**，连操作 ID 都能复用。这比我以前手动 `cp -r` 备份再 `git commit` 可靠得多。

#### 2. 「来源存活、主张可溯」：笔记不再是孤岛，而是有账本的知识图谱

系统维护两类账本（`skills/wiki/references/provenance.md` 定义契约）：

| 账本 | 字段 | 作用 |
| --- | --- | --- |
| **来源账本** | `source_id` (内容寻址哈希)、原始路径/URL、捕获时间、字节大小、媒体类型 | **原始证据永不丢** ，笔记只存指针 |
| **主张账本** | `claim_id` 、权威性、新鲜度、支持/反驳证据、置信度、审核状态 | **每个重要结论都有据可查** ，矛盾/无据主张显式保留 |

**实测**：我把一篇 PDF 论文丢进 `inbox/`，跑 `/claude-obsidian:wiki-ingest`，生成的概念页顶部自带 `source_id: sha256:abc123...`，点进去能看到原始 PDF 的存储路径、捕获时间、字节数。我在笔记里写「该模型在 FLEURS 上达 90.3」，系统自动在主张账本记录：权威性=来源、支持证据=PDF 第 3 页表 1、置信度=0.92。后来我把同一论文的 v2 版放进去，主张账本自动标记「新鲜度下降、需复核」。

**这就是「Sources survive the summary」**：笔记不是终点，而是指向证据的索引。

#### 3. 15 个 Skills，一套系统：小而专、可组合、共享证据

README 把 15 个 Skills 分三层，我实测了核心循环：

**核心循环（Build & Use）**：

| Skill | 实测场景 |
| --- | --- |
| `wiki` | 初始化/诊断/路由总入口 |
| `wiki-ingest` | `inbox/` 里放 PDF/网页/语音 → 自动切片、抽主张、建反链、写账本 |
| `wiki-query` | 问「之前那个关于 MoE 的论文结论是什么」 → 只读检索，给引用、给置信度 |
| `save` | 把对话里的一个洞察显式存成笔记，**不存全量转录** |
| `wiki-lint` | 死链、孤儿页、元数据缺失、过时索引、空段落全报出来 |

**扩展工作流**：

* • `autoresearch`：有边界的网络调研（显式出站同意、独立规范合并）
* • `canvas`：基于 Wiki 范围的 Obsidian Canvas 创建/维护
* • `defuddle`：网页正文清洗后再入库
* • `wiki-fold`：操作日志的可溯源卷叠摘要
* • `wiki-mode`：四种归档范式（Generic/LYT/PARA/Zettelkasten）**切换只影响新笔记路由，不重组旧笔记**
* • `wiki-retrieve`：BM25 + 可选语义重排，上下文前缀注入
* • `wiki-cli`：Obsidian CLI 读/搜，事务安全写

**参考技能**：

* • `obsidian-markdown`：标准化 Obsidian Flavored Markdown
* • `obsidian-bases`：原生 `.base` 表格/卡片/筛选/公式/摘要
* • `think`：结构化 OBSERVE→LISTEN→THINK→CONNECT→FEEL→ACCEPT→CREATE→GROW 复盘环

**实测**：我先跑 `wiki-ingest` 把 10 个来源（PDF、网页、语音转写）全进库，再跑 `wiki-query` 问跨文档问题，**BM25 检索 + 可选语义重排**，答案每句带 `source_id` 引用，点进去能看到原文片段。切到 `wiki-mode: Zettelkasten` 后，新笔记自动走 `YYYYMMDDHHMMSS-uuid` 命名、原子化、密链接，旧笔记完全不动——**「切换模式只改路由，不重组历史」**。

#### 4. 诚实的能力边界：不吹牛、不模拟、缺啥明说

README 专门列了「Honest capability boundaries」表，这在开源 AI 项目里极罕见：

| 输入/能力 | 当前支持 | 备注 |
| --- | --- | --- |
| 本地文件源 | 已实现，内容寻址字节捕获 | ✅ |
| 图片 | 元数据、哈希、尺寸 | ✅ 无语义提取 |
| PDF/EPUB | 元数据、哈希、大小 | ❌ 无内置语义提取 |
| URL/YouTube | 验证同意计划，**需配置外部 runner** | ⚠️ |
| OCR | 本地文件同意计划，**需配置外部 runner** | ⚠️ |
| BM25 检索 | 本地确定性 | ✅ |
| 语义前缀/远程模型 | 可选，**显式出站同意门控** | ⚠️ |
| Obsidian CLI | 可选读/搜 | ⚠️ |

**关键诚实点**：

* • **不做自动转录/云同步/事实预言/备份替代**
* • **高风险主张需两独立来源**，无据/矛盾证据保留可见
* • **模型检索不可信时回退确定性 BM25**
* • **并行 Agent 不能赛跑 Vault**：Worker 只返草稿，编排器序列化应用

这不是「功能少」，是\*\*「不模拟、不隐瞒、不替用户做决定」\*\*。

### 🚧 避坑与总结

**✅ 值得点赞的地方**

* • **可恢复事务 + 进程锁 + 原子替换 + 冲突即报错**：把知识库写入工程化了
* • **来源账本 + 主张账本**：每个结论可溯源、矛盾可见、新鲜度可量化
* • **15 个 Skills 小而专、共享账本/锁/路由规则**：单技能可直调、组合可编排
* • **四种归档模式切换不重组历史**：LYT/PARA/Zettelkasten/Generic 任选，新旧共存
* • **诚实的能力边界 + 显式出站同意**：不模拟、不偷跑、不替用户决定
* • **本地优先、纯 Markdown、可迁移**：Obsidian 只是视图，文件归你

**⚠️ 踩坑提醒**

* • **Python ≥3.11 强制**，旧环境需升级
* • **Windows 原生仅读/干跑**，写入必须 WSL，且哈希审核需在 WSL 内完成
* • **PDF/EPUB/URL/OCR 无内置提取**，需自备外部 runner（Ollama/云 API/本地模型）并显式同意
* • **Claude Code 插件名在 v3.0 变过两次**，升级按 3.0.1 节操作，托管设置键需手改
* • **并行 Agent 通过编排器序列化**，高并发写入会排队，非无限吞吐
* • **非自动转录/云同步/事实预言**，别指望它帮你「自动整理一切」

**个人判断**：如果你 **「用 Obsidian 做知识管理、受不了『存了找不着、引用没来源、冲突没记录』、想要一个本地可控、事务可恢复、来源可溯、技能可组合的系统、且能接受『PDF/网页需自备提取器、Windows 需 WSL』」**，**claude-obsidian 3.0 是当前最像「工程系统」而非「演示玩具」的开源答案**。把它当「带事务保护的知识库内核 + 15 个可组合 Skills + 可视化 Obsidian 前端」用，心态最稳。
