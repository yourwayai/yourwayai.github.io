# Nyxis v0.1.9：用 Lean 4 形式化证明「授权安全」的后端框架，让 AI 写的 Handler 也不敢越权

2026 年 10 月下旬，**NyxFoundation 发布 Nyxis v0.1.9**——一个用 **Lean 4** 编写的后端框架，其核心主张极其大胆：**「每个基于 Nyxis 的后端，都带有一个形式化证明：任何 HTTP 请求序列都无法让认证主体读取、修改、删除或授予超出其合法权限的数据。」** 这个证明由 **Lean 4 内核在每次 `lake build` 时自动检查**。

项目虽年轻（2026-10-26 创建、仅 2 次提交、v0.1.9），但已获 314 Star，且给出了两个官方样例：`bulletin-board`（含 Next.js 前端）与 `team-docs`（文档共享、角色、附件、邮件、外部 API）。

### 核心优势解析

#### 1. 「授权安全」从「代码审查」变成「数学证明」——这是核心范式转移

传统后端授权靠：

* • 代码审查（人眼易漏、随人员流动失效）
* • 测试用例（只能覆盖有限路径、无法穷尽组合）
* • 运行时检查（只能发现已部署的问题、无法保证未知路径）

Nyxis 的答案：**把「授权安全」编码为 Lean 4 定理，在编译期由内核机械验证。**

定理 `Nyxis.Runtime.authorization_safety` 陈述了 9 条保证（节选）：

1. 1. **每个数据库操作都在批准策略许可的效应内**——Handler 伪造不了 principal、时间、ID
2. 2. **状态仅通过记录的操作变更，每个决策针对当时状态**——`Authz.Coherent`
3. 3. **传给 Handler 的 (PK, row) 一定是当时可读的那一行**——不会把 A 行的主键配上 B 行的内容
4. 4. **列表返回的行数和内容仅由决策时刻的许可行决定**——limit/offset 作用于许可行
5. 5. **每条记录的决策动作要么是 Handler 调用的、要么是 `@references` 级联删除**
6. 6. **每个外部效应（签名 URL、邮件、外部 API）都在同一决策材料上被许可**
7. 7. **给 Handler 的签名 URL 必有对应的外部效应记录**
8. 8. **外部 API 调用（同步/异步）的目标、方法、路径来自声明，Body 由 Nyxis 从行列推导**
9. 9. **响应仅含允许的头、可从请求+阶段结果复现、内部授权读取无其他路径进响应**

**实测理解**：这不是「运行时拦截」，而是**编译期证明所有可能执行路径都满足上述性质**。Handler 代码可以是 AI 写的、可以有 Bug，但只要 `lake build` 通过，**授权层面的越权在数学上不可能发生**。

#### 2. Cedar Schema 双重身份：既是「表定义」又是「策略语言」

Nyxis 不搞 ORM，**Cedar Schema 直接做表定义**：

```
entity User = { "admin": Bool };  
entity Post = { "author": User, "title": String, "body": String, "published": Bool };  
@effect("update Post(title, body)")  
action "editPost" appliesTo { principal: [User], resource: [Post] };
```

* • `entity` = 表，`attribute` = 列
* • `@effect` 声明该动作的数据库效应（显式列列表，防止过度更新）
* • `action` 绑定 principal 与 resource 类型

策略同样用 Cedar：

```
@id("manage-post")  
permit (  
  principal is User,  
  action in [Action::"editPost", Action::"publishPost", Action::"deletePost"],  
  resource is Post  
) when { resource.author == principal || principal.admin };
```

**关键点**：Schema 和 Policy 是**开发者唯一要写和审核的东西**——Handler 可以全交给 AI，**授权逻辑集中在 Cedar，形式化验证覆盖全局**。

#### 3. Handler 只能「调用动作」，不能直连 DB——架构强制最小权限

Handler 类型是 `Nyxis.Handler`，它的**唯一效应**是调用授权层的 `action`：

```
Handler → 调用 action("editPost", {title: "...", body: "..."})  
           ↓  
      授权层：检查 Cedar 策略 → 通过则发布 effect → 运行时执行 SQL  
           ↓  
      返回结果给 Handler
```

Handler **不能**：

* • 直接执行 SQL
* • 直接读写数据库
* • 伪造 principal / 时间 / UUID（这些由 Nyxis 服务端生成并固定在请求上下文中）
* • 绕过授权层发起外部调用（文件存储、邮件、外部 API 全走授权层）

**实测理解**：这把「数据访问」从业务代码里彻底剥离了。AI 写 Handler 时，**只需关心「调用哪个 action、传什么参数」**，授权、事务、外部调用、审计日志全由框架托底。

#### 4. 效应系统统一了「数据库操作」与「外部副作用」

Nyxis 把所有副作用统一建模为 **Effect**：

| Effect 类型 | 示例 | 授权检查 |
| --- | --- | --- |
| `read` / `list` / `insert` / `update` / `delete` | 数据库 CRUD | Cedar 策略许可 |
| `StorageSign` | 签名 URL 上传/下载 | 同行读权限 + 策略许可 |
| `MailSend` | 邮件通知 | 同行读权限 + 策略许可 |
| `CallSend` (sync) / `call` (async) | 外部 API 调用 | 同行读权限 + 策略许可，目标/方法/路径来自声明 |

**统一性价值**：无论是改数据库、传文件、发邮件、调第三方 API，**全走同一套 Cedar 策略、同一套决策材料、同一套证明**。外部 API 甚至支持 `@external` 声明 + `call` 动作，**幂等键、目标 URL、方法、路径全在 Schema 里声明**，防止 SSRF、防止参数注入。

#### 5. 供应链安全：依赖锁死、SHA256 验证、无 Git 依赖

`lakefile.lean` 展示了极其严格的依赖管理：

```
require Cedar from git "https://github.com/cedar-policy/cedar-spec" @  
  "6d7fb269d5eec6ce4ae1d4aff9794feba0c0d5a9" / "cedar-lean"  
require leanPq from ".lake/vendor/lean-pq"  
require «jose-libcrypto» from ".lake/vendor/jose-libcrypto"
```

* • **所有依赖固定到具体 Commit SHA / SHA256 归档**
* • `python3 scripts/prepare-dependencies.py` 把依赖下载到 `.lake/vendor/`，**完全离线构建、无 Git 运行时依赖**
* • `postgresLinkArgs` / `cryptoShimLinkArgs` 手工处理 libpq / libcrypto 链接路径，**macOS/Linux 双平台链接参数手写**，防止系统库版本漂移
* • `lean-toolchain` 锁死 Lean 版本（`leanprover/lean4:v4.34.1-0052cc...`）

这套机制让「可复现构建」不再是口号，**证明依赖的代码版本与证明时一致**。

### 行业影响

**它与传统后端框架（Express/FastAPI/Django/Go 标准库）的区别在于**：

| 维度 | 传统框架 | **Nyxis** |
| --- | --- | --- |
| 授权实现 | 代码中手写中间件/装饰器 | **Cedar 策略 + Lean 形式化证明** |
| 授权验证 | 代码审查 + 测试 | **Lean 内核每次构建机械检查** |
| Handler 权限 | 可直连 DB、任意 IO | **仅能调用授权层 action** |
| 外部副作用 | 业务代码里随意发 | **统一 Effect、统一授权、统一证明** |
| 供应链 | package.json / Cargo.toml / go.mod | **Lean + Lake + 固定 SHA256 归档** |
| AI 编程友好度 | 需人工审核授权逻辑 | **只需审核 Cedar Schema/Policy，Handler 可全 AI 写** |

**行业信号**：

* • **形式化验证下沉到「应用层授权」**：过去主要在内核、密码学、编译器，Nyxis 把它带到了业务后端
* • **Cedar 成为「授权 SQL」**：AWS 开源的 Cedar 策略语言在 Nyxis 里成了「可执行的授权规范」
* • **AI 编程时代的「护栏」范式**：不限制 AI 写什么代码，**在架构层面用数学证明托底**——这可能是 AI 编程落地生产的关键路径之一
* • **Supabase 生态的新玩法**：把 Supabase Auth + PostgreSQL 变成「可证明安全的后端运行时」

**不凭空推测「替代谁」**：它不替代 Express/FastAPI（它们解决通用 Web 服务），不替代 Supabase（它是底层设施）。它的定位是 **「需要在 AI 编程时代、以数学确定性保证授权安全、愿接受 Lean 学习曲线与 Supabase 绑定的团队的首选框架」**。
